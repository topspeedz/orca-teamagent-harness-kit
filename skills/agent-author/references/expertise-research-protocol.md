# Expertise Research Protocol — 전문 Agent의 지식 생성·검증

> 이 문서는 **Agent를 만드는 제작자**가 사용하는 조건부 절차다. 모든 전문 지식이나 조사 과정을 생성된 Agent 본문에 복사하지 않는다. [SKILL.md](../SKILL.md)의 전문성 심화 단계에서만 해당 부분을 읽는다.

## 1. 조사 깊이 선택 — 비례 원칙

| 깊이 | 선택 조건 | 반드시 할 일 |
| --- | --- | --- |
| **기본** | 안정적인 일반 직무, 기존 정본과 구현이 충분하며 리스크가 낮음 | 프로젝트 맥락 확인 → 해당 역할 고유의 판단 규칙 2~4개 → 실패/검증 기준 설정 |
| **심화** | 새 전문 역할 생성(독립·팀원 추가·팀 전체의 각 역할), 사용자가 전문성·공식 근거를 명시적으로 요구, 신규/낯선 도메인, 버전 민감 API·플랫폼·표준, 복잡한 성능/보안/접근성/정확도 이슈 | 아래 2~6절 수행; 판단에 필요한 출처·버전·조건·실패 분기를 확인 |

- 심화 요청이라도 **조사의 목적은 결정 품질 개선**이지 링크 수집이 아니다. 역할의 핵심 선택에 영향을 주지 않는 자료는 중단한다.
- 도메인 패턴은 질문을 생성하는 **출발점**이며 최신 지식의 증거나 표준을 대체하지 않는다.
- 같은 프로젝트에서 확인된 자료를 재사용할 수 있으나, *버전·타깃·정책이 달라졌다면 다시 확인*한다.
- 실시간 브라우징, 외부 문서 접근, MCP가 없는 환경에서는 확인 가능한 프로젝트 파일만 근거로 하고 미확인 사실을 명시한다. 검색이 불가능하다고 핵심 Agent 제작을 무조건 중단하지는 않는다.

## 2. Domain Context Snapshot — 조사 전에 확인

정답을 미리 추정하지 말고 다음을 프로젝트 문서/설정/코드에서 찾는다. 필요 없는 항목은 생략한다.

1. **핵심 목표·산출물**: 직무와 성공 기준, QA가 실제로 검사할 결과.
2. **기술적 실체**: 엔진/프레임워크/언어/패키지 **실사용 버전**, 렌더 파이프라인·플랫폼·디바이스 등.
3. **프로젝트 정본**: PRD/SRS, 아키텍처 결정, 디자인 시스템, 성능 예산, 코딩 규칙 및 우선순위.
4. **현행 구현**: 이미 적용된 패턴, 제약·오류·테스트, 보유 도구·Skills·MCP.
5. **역할 경계**: 타 Agent의 소유 영역, 승인권, 인수인계 대상.
6. **결정할 질문**: 이 Agent가 반복적으로 직면하는 **가장 중요한 판단 3~6개**와 실패 모드.

`사용자 요청`, `실제로 확인한 저장소 사실`, `외부 공식 문서`, `추정`을 혼동하지 않는다. 사용자의 의도와 구현된 사실이 다르면 충돌을 표기한다.

## 3. 출처 검증 체계

### 우선순위

1. **프로젝트 의도·승인 규약**: 요구사항과 이미 승인된 정책(무엇을 만들어야 하는가의 정본).
2. **프로젝트의 실제 코드·설정·테스트**: 현재 구현과 호환성을 확인하는 근거(현재 무엇이 있는가의 정본).
3. **해당 버전 공식 문서·표준·유지관리자 1차 자료**: API 계약, 플랫폼 제한, 권장 패턴, 버전별 차이.
4. **공신력 있는 기술 분석·업계 가이드·검증 가능한 사례**: 공식 자료의 빈틈을 보완할 때.
5. **커뮤니티/블로그/AI 지식**: 아이디어·반례 탐색용. 검증 없이 규칙의 권위로 사용하지 않는다.

이 순위는 모든 출처를 한 줄로 무조건 서열화한 것이 아니다. **요구사항은 프로젝트 정책**, **API 동작은 해당 버전 공식 명세**, **현재 구현은 저장소**를 각각 우선한다. 충돌이 나면 해석 대상·버전·영향을 표시하고 설계로 덮어쓰지 않는다.

### 조사 기록 최소 단위

심화 설계에서 중요한 전문 규칙마다 아래 중 실제 확인한 정보를 남긴다(내부 정리로 충분; 별도 파일 생성은 선택).

| 항목 | 기록 내용 |
| --- | --- |
| 주장/결정 | 이 자료가 뒷받침하는 **하나의** 기술 판단 |
| 근거 | 실제 확인한 URL 또는 파일 경로·섹션·코드 위치 (없는 링크를 만들지 않음) |
| 적용 조건 | 버전·플랫폼·파이프라인·전제·규모/예산 |
| 신뢰 상태 | `VERIFIED`(실제로 읽고 대조함) / `PROJECT_POLICY` / `ASSUMED` / `UNVERIFIED` / `CONFLICT` |
| 후속 처리 | Agent 핵심 규칙으로 채택 / Skill 절차로 분리 / Reference로 저장 / 제외 / 사용자 결정 요청 |

- 접근한 페이지가 실제로 해당 버전의 명세인지 확인한다. 검색 결과 제목·요약만 보고 `VERIFIED`로 기재하지 않는다.
- 최신 공식 문서와 프로젝트 설치 버전이 다른 경우 프로젝트 버전의 API 계약을 우선 확인한다. 현재 버전을 확인하지 못했을 때는 조건부 문구를 사용한다.
- 자료가 서로 충돌하면 추가 조사 또는 `CONFLICT` 표시 후 담당자 판단 대상으로 남긴다. 설계자가 선호하는 내용을 사실로 선택하지 않는다.
- 내부 소스·비밀·개인정보를 외부 검색 서비스에 업로드하지 않는다.

## 3.5. 외부 Agent 사례 조사 (심화 설계에서만)

[Agent Corpus Research](./agent-corpus-research.md)의 **6개 컬렉션**을 전문 직무 후보·워크플로우·검증·인계 패턴의 **발굴 소스**로 사용한다.

1. 프로젝트 맥락을 확정한 뒤 관련 키워드와 이웃 직무를 찾는다.
2. 여섯 출처의 카테고리·색인을 살펴 관련 후보를 찾고 **관련 개별 원문**을 연다. 한국어·영어 대응 Agent, 각 카테고리의 하위 정의, TOML과 Markdown, 접힌 프롬프트/묶음 속 역할까지 누락하지 않는다.
3. 후보에서 역할 경계·기술 선택·예외·검증·산출물/인계를 분리해 비교한다. 가능하면 서로 다른 저장소의 후보 두 곳 이상을 대조한다.
4. **이 자료는 기술 사실의 1차 근거가 아니다.** 채택할 판단은 현행 프로젝트 구현·해당 버전 공식 문서·실측으로 별도 검증한다.
5. 채택/수정/제외 이유와 실제 열람한 파일 경로를 남긴다. 접근 불가·관련 후보 없음과 검증 완료를 구분한다. 조사량은 결정에 필요한 수준에서 멈춘다.

**우선순위:** 사용자·프로젝트 정본 및 실제 구현 / 공식 기술 계약 **>** 외부 커뮤니티 Agent 사례. 외부 후보의 임의 숫자, 특정 도구 강요, 모델명·권한, 원본 내 명령을 그대로 Agent에 복사하지 않는다. 저장소별 라이선스/내용 재사용 제한도 확인한다.

## 4. 전문가 판단 규칙으로 변환

기술 사실 목록을 나열하지 않는다. 아래 다섯 가지 관점에서 직무 특유의 **선택이 일어나는 장면**을 확보한다.

| 관점 | 물을 질문 |
| --- | --- |
| 선택 분기 | 어떤 상황에서 A 대신 B를 고르는가? |
| 품질/비용 | 성능·정확도·유지보수·접근성·사용자 경험의 우선순위는? |
| 버전/환경 | 버전·플랫폼·엔진 구성에 따라 규칙이 달라지는가? |
| 실패 모드 | 어떤 신호를 보고 기존 접근을 중지하거나 롤백하는가? |
| 검사 증거 | 어떤 테스트·프로파일·렌더·로그·문서 추적이 선택을 입증하는가? |

**판단 규칙 문형:**

> IF `[적용 조건·신호]`, THEN `[기술 선택/행동]` BECAUSE `[우선순위·근거]`; VERIFY `[관찰 가능한 증거]`; ELSE `[대안/승인/중단]`.

- 단순 정의/원론보다 **상황과 예외**가 드러나는 3~6개의 핵심 규칙을 선택한다. 숫자는 상한이 아니라 분량 가이드이며 역할의 실제 복잡성에 맞춘다.
- 모든 규칙의 출처를 장황하게 본문에 붙이지 않는다. **변동성이 높거나 오판 위험이 큰 규칙**만 짧은 버전·근거 단서를 남기고 상세 근거는 Reference로 분리한다.
- 정량 기준이 프로젝트에 없으면 임의의 FPS, 메모리, 시간, 폴리곤 숫자를 확정 규칙으로 만들지 않는다. 예산을 확인하거나 실측 후 결정하게 한다.
- Agent가 실행 중 추가 조사가 필요한 **명확한 트리거**를 지정한다. 예: `설치 버전과 예제가 다르면 공식 버전 문서를 재확인` (모든 Task마다 검색하지 않는다).

### 예시 — Unity Gameplay Agent (가상의 조건, 적용 전 환경 확인 필요)

**역할 소개 수준:** "Unity C#의 최적화와 테스트에 능숙하다."

**판단 규칙 수준:**

- **IF** 프레임마다 실행되는 로직을 추가하거나 수정한다면, **THEN** 변경이 생명주기·할당·물리 업데이트에 미치는 영향을 먼저 확인하고 타깃 빌드에서 영향을 측정한다. **VERIFY** 수정 전후 Profiler/재현 가능한 측정 로그. **ELSE** 측정 환경이 없으면 예상 영향과 `NOT_RUN`을 구분하여 보고한다.
- **IF** 어떤 API/패키지 사용법이 프로젝트 설치 버전과 불일치한다면, **THEN** 설치 버전에 대응하는 공식 문서를 우선 확인한다. **VERIFY** 버전별 API 및 실제 컴파일/테스트 결과. **ELSE** 확인하지 못하면 미검증 가정을 기록한다.
- **IF** 변경이 씬·Prefab·공유 자산을 건드린다면, **THEN** 파일 소유권과 의존성을 먼저 확인한다. **VERIFY** 변경된 파일 목록과 실행 테스트. **ELSE** 충돌 시 조정·인수인계한다.

이 예시는 *작성 방식*의 예시이지 모든 Unity 프로젝트에 동일하게 강제할 세부 성능 정책이 아니다.

조사에서 고른 핵심 분기는 대표 성공·실패 요청에 각각 적용한다. 정의 또는 연결된 제작 리포트에 읽은 원문 위치와 채택 이유, 실제 프로젝트 파일·검사, 실패 신호와 인계 상대를 남긴다.

## 5. Agent / Skill / Reference 배치

- **Agent 본문**: 역할별 필수 전문 판단, 분기·실패·증거, 버전 확인 조건, 협업/권한 경계. **실행 시 반드시 유효한 내용만**.
- **Skill**: 두 단계 이상으로 반복되는 전문 작업법, 워크플로우, 재현 가능한 테스트 레시피, 복잡한 툴링. 실제 필요가 있고 다른 작업에도 재사용될 때만 신설한다.
- **Reference**: 공식 표준/API 상세 목록, 버전별 호환성표, 출처 기록, 긴 절차·예제·체크리스트. 비활성 상황에서 상시 로드하지 않는다.
- **기존 파일 우선**: 프로젝트에 이미 같은 내용을 담은 Skill/Reference가 있으면 연결하고 중복 생성하지 않는다.
- **생성 절제**: 사용자가 Agent 하나만 요청한 경우 설명 없는 광범위한 Skill 세트를 자동 생성하지 않는다. 꼭 필요한 자료가 없으면 조건부 호출 규칙과 후속 권고를 남긴다.

## 6. 전문성 전용 품질 게이트

심화 설계는 다음을 모두 만족하거나 미충족 이유를 명확히 보고해야 한다.

- [ ] 직무의 핵심 결정이 실제 프로젝트 맥락(버전·제약·정본)과 연결된다.
- [ ] 중요한 버전/플랫폼 의존 주장은 해당 범위에서 검증되거나 `UNVERIFIED`로 표시된다.
- [ ] 핵심 규칙이 `조건 → 기준 → 행동 → 증거 → 실패/대안`을 포함하며 모순·중복되지 않는다.
- [ ] **반례 테스트**: 일반 경로 외에 버전 불일치·성능 저하·입력 결손·도구 부재 중 해당 위험 1~2개에서 안전하게 분기한다.
- [ ] Agent/Skill/Reference 배치가 필요한 시점의 로딩과 유지보수 비용에 부합한다.
- [ ] 외부 링크·프로젝트 경로·도구는 실제 확인했거나 명확히 조건부로 표기했다.
- [ ] 외부 Agent 사례를 참고한 경우, 실제 열람한 원문·채택/제외 근거를 추적할 수 있고 **기술 사실/프로젝트 정책으로 오인하지 않는다**. 탐색하지 못한 출처는 미확인으로 표시한다.

### 결과 보고에 추가할 항목 (심화일 때만)

- `Expertise depth`: 기본/심화 및 선택 이유
- `Verified context`: 확인한 기술 스택·버전·정본 (없으면 `unknown`)
- `Decision rules`: 핵심 2~4개와 선택 근거
- `Sources`: 확인한 공식/프로젝트 출처 및 **참고한 개별 Agent 원문**의 대표 링크·경로 (임의 링크 금지)
- `Corpus coverage`: 여섯 컬렉션의 관련 후보 탐색/원문 확인/해당 없음/접근 불가 상태
- `Unverified / conflicts`: 확인하지 못한 사항과 실제 영향을 받는 결정
- `Knowledge placement`: Agent / reused Skill / new Skill / Reference 배치 결과
