# team-dev

개발 팀은 의존성 없는 Node 프로젝트에서 `node --test`로 통과하는 코드를 만든다. 팀장은 spec 첫 줄이 `[역할: developer · 리드]`인 워커이며 `team-lead`와 이 스킬을 로드한다.

## 에이전트 구성

| 에이전트 | 맡는 일 | 역할 스킬 | 모델 표의 작업 단위 |
| --- | --- | --- | --- |
| `developer` | 테스트 작성, 구현, 자체 검증 | 없음 | 구현 |
| `developer` | 한 파일 안의 작은 수정, 결함 재현이 쉬운 수정 | 없음 | 단순 수정 |

- 작업 단위는 모델 표에 있는 이름만 쓴다. 없으면 표에 줄을 먼저 넣는다.

## 작업 흐름

| 순서 | 작업 | 담당 | 의존 | 산출물 파일 |
| --- | --- | --- | --- | --- |
| 01 | 테스트 작성: 완료 기준마다 테스트를 쓰고 `node --test`로 실패를 확인한다 | `developer` | — | `01_developer_test_v1.md` |
| 02 | 구현: 01의 테스트를 통과시키는 코드를 쓴다 | `developer` | 01 | `02_developer_impl_v1.md` |
| 03 | 자체 검증: `node --test` 전체를 돌리고 결과를 `## 검증`에 적는다 | `developer` | 02 | `03_developer_verify_v1.md` |

- 순서 `NN`은 산출물 파일 이름의 `NN`이 된다. 도착 순서가 아니다.
- 01의 리포트에는 처음 실패한 테스트 출력을 붙인다. 실패를 보지 못한 테스트는 02로 넘기지 않는다.

## 팀원 간 소통

- 기본은 팀장을 거친다. 팀원은 산출물 파일과 팀장의 `ask`/`reply`로 주고받는다.
- 아래 **직접 소통 짝 표**에 있는 짝만 서로 직접 메시지를 보낼 수 있다(`send --to dispatch:<상대 id>`). 팀장은 팀원을 띄운 뒤 짝의 Dispatch ID를 서로에게 알려 준다.
- 직접 주고받아 정한 내용은 보낸 쪽이 자기 리포트의 `## 직접 소통` 절에 적는다. 팀장은 그 절로 결정을 파악하고 한도를 감독한다.

### 직접 소통 짝 표

| 짝 | 방향 | 용도 | 한도 |
| --- | --- | --- | --- |
| `developer`(모듈 A) ↔ `developer`(모듈 B) | 양방향 | 두 모듈 사이 함수 이름과 인자 형식 질문 | 질문 3회, 넘으면 팀장에게 |

- **한도 칸은 비울 수 없다.** 짝을 더하면 한도를 함께 적는다.

## 작업 규모별 모드

| 모드 | 언제 | 투입 |
| --- | --- | --- |
| 풀 | 서로 다른 모듈을 고치는 구현 Task가 3개 이상이다 | 모듈마다 `developer` 하나. 팀장을 띄우고 각자 01→02→03을 한다 |
| 축소 | 구현 Task가 1~2개다 | `developer` 하나가 01→02→03. 코디네이터가 직접 띄운다 |
| 단일 | 한 파일 안의 작은 수정이나 결함 하나 | `developer`(단순 수정) 하나가 재현 테스트, 수정, 통과를 한 Task로 한다 |

## 산출물

- 경로: `_workspace/dev/<phase>/NN_developer_<산출물>_v<N>.md`. 지시서는 `_workspace/dev/<phase>/spec/`.
- 이미 넘긴 파일은 고쳐 쓰지 않는다. 다시 쓰면 다음 버전 `_v<N+1>`을 만든다. `final`, `fix1`, `-2` 같은 접미사를 쓰지 않는다.
- 코드와 테스트는 `src/`, `test/`에 둔다. 리포트에는 바꾼 파일 목록만 적는다.
- 이 팀이 최신으로 유지하는 문서: 없음.

## 오류 처리

| 상황 | 대응 |
| --- | --- |
| 완료 기준이 모호해 테스트를 쓸 수 없다 | 멈추고 `ask`로 묻는다. 기준을 임의로 정하지 않는다 |
| 01에서 테스트가 처음부터 통과한다 | 이미 구현된 것이다. 리포트에 적고 02를 건너뛴다. 기준이 맞는지 `ask`로 확인한다 |
| 03에서 실패가 남는다 | 그 줄을 `## 검증`에 ❌로 적고 `--outcome failed`로 보고한다 |
| 팀원 실패 | 새로 띄워 1회 재시도. 그래도 실패하면 그 산출물 없이 통합 보고에 누락을 적는다 |

## 테스트 시나리오

- 정상: "할 일 목록에 마감일 정렬 추가" → 축소 모드 → 01 정렬 테스트 실패 확인 → 02 구현 → 03 `node --test` 전부 통과 → `03_developer_verify_v1.md`의 `## 검증`이 모두 ✅.
- 기존 파일 활용: `team-qa`의 결함 표에 `A-H-1` High 하나가 있다 → 단일 모드 → 그 QA 리포트를 "먼저 읽을 것"에 넣고 `A-H-1` 재현 테스트, 원인 수정, 통과를 한 Task로 한다. 기존 테스트는 다시 쓰지 않는다.
- 오류: 완료 기준이 "빠르게 동작한다"뿐이다 → 오류 처리 표대로 01에서 멈추고 `ask` → 기준이 정해지면 01을 새로 띄운다.
