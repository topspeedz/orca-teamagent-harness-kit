## 1. 의도

검증을 켤지 말지만 조건으로 바꿔서는 줄지 않는다. 방향은 기반 문서와 같다. **판단 검증은 변경분에 한 번만 쓰고, 결함은 하나씩 닫고, 쌓이는 것은 테스트뿐이게 한다.**

만드는 방식은 **먼저 재고, 작은 것부터 바꾸고, 다시 잰다**이다. 2절의 기준선이 첫 측정이고, 그 결과로 3절(1a)의 내용을 정했다.

## 3. 1a: 있는 규칙을 스크립트가 지키게 하고, 검증의 크기를 보이게 한다

기준선은 규칙이 모자라서가 아니라 규칙을 벗어나서 커졌다고 가리킨다. 그래서 1a의 중심은 문구가 아니라 기동 경로의 거부다. 승인과 등록의 구조는 건드리지 않고, 띄우기 전에 spec을 검사하는 것만 더한다.

### 3.1 수정 루프의 입구

- 수정 Task의 spec에는 `결함 ID:` 줄이 있어야 한다. 적힌 ID는 장부의 결함 원장(3.8)에서 High여야 한다. 아니면 기동을 거부한다.
- 사용자가 Medium 이하를 이번에 고치라고 정했으면, 그 원문을 장부의 `## 결정`에 적은 ID만 예외로 받는다.
- "완료 기준 미달"로 고치려면 그 결함을 High로 적어야 한다. Medium인 채로는 수정에 들어가지 못한다.
- 열린 High가 0이면 수정 라운드를 시작하지 않는다. 문서 불일치는 수정 루프가 아니라 6단계에서 다룬다.
- 수정 Task와 재검 Task의 spec은 끝 검증이 정산된 뒤에 쓰고 그때 등록한다. 등록된 spec은 바꿀 수 없어서, 결함이 정해지기 전에는 `결함 ID:` 줄을 쓸 수 없기 때문이다.
- 계획에 있는 수정 Task와 재검 Task는 고칠 것이 없으면 건너뛴다. 기동 스크립트에 `skip` 명령을 더한다. 등록과 종료를 한 번에 하고, 뒤 Task를 스스로 준비 상태로 올리고, 사유를 대응표와 장부에 남긴다. 지금의 `fail`과 짝이다.
- `skip`은 계획에서 수정·재검으로 표시된 Task, 시험 갱신 Task(3.3), 문서 동기화와 회고 Task(3.10)에만 쓸 수 있다.
- 3회째를 사용자에게 물을 때는 남은 High 목록에 더해, 라운드별 High 수와 지금까지 검증·수정에 쓴 워커 수와 시간을 싣는다. 비용을 보고 정하게 한다.

### 3.2 수정 뒤의 검증은 결함 ID만 본다

사용자가 큰 문제로 짚었다(2026-11-25). 기준선에서 전 범위를 다시 본 길은 둘이었다. 계획이 수정 뒤에 다음 검증을 세워 둔 것과, 실행 중에 새 검증을 이름만 바꿔 띄운 것이다. 작업 단위 이름으로 막으면 둘 다 빠져나간다. 그래서 두 자리에서 막는다.

**계획을 검토할 때**

- 재검이 아닌 검증 Task는 수정 Task 뒤에 걸 수 없다. 끝 검증은 한 묶음으로 계획하고, 모두 구현에만 의존한다. 그래야 결함이 한 라운드에 모여 나온다.
- 계획에 수정 Task의 사슬이 2단을 넘으면 안 된다. 상한 2회를 계획이 미리 넘기지 못하게 한다.
- 어느 Task가 검증이고 수정이고 재검인지는 DAG 입력의 `rounds`(검증에서 수정으로 가는 회차 표기, 지금은 선택 항목)로 안다. 수정 Task가 있는 계획은 `rounds`를 적어야 한다. 이 표기는 승인 기록에도 들어가서 띄울 때의 검사가 읽는다. 표기가 없는 옛 승인은 지금처럼 통과한다.
- 두 규칙을 어기는 계획은 `review` 명령이 거부한다. 꼭 필요하면 계획서에 사유를 적고, 창구가 승인 질문에 그 Task를 따로 보여 준다. 사용자가 승인한 Task만 예외로 통과한다.

**띄울 때**

- 그 phase의 결함 원장에 라운드가 1 이상 적혀 있으면, 그 뒤에 새로 띄우는 검증 Task는 작업 단위 이름과 관계없이 `결함 ID:` 줄과 수정 diff(3.7)가 있어야 한다. 팀장이 팀원을 띄울 때도 같다. 없으면 기동을 거부한다.
- 팀장을 거쳐 띄우는 것은 막지 않는다(결정 D). 팀장의 spec과 팀원의 spec 둘 다 결함 ID가 있어야 한다.
- 완료 기준은 양식의 고정 문장("결함 ID마다 원래 재현 절차를 다시 돌린다")만 쓴다. 증거도 그 결함의 것만 다시 모은다.
- 새로 열 수 있는 지적은 수정 diff가 만든 문제뿐이다. 범위 밖에서 본 것은 인박스 후보로만 적는다.
- 수정으로 검증 대상이 통째로 바뀌어 전 범위를 다시 봐야 한다고 판단되면 띄우지 않고 사용자에게 올린다. 질문에는 다시 볼 범위와 지금까지 검증·수정에 쓴 워커 수와 시간을 싣는다. 승인 원문이 장부의 `## 결정`에 있는 Task만 통과한다.

### 3.3 전체 테스트의 자리

기준선에서 두 가지가 반대 방향으로 나왔다. 수정 Task의 완료 기준에 전체 테스트를 넣었더니 이룰 수 없는 기준이 됐고(디자인 시스템 적용), 전체 테스트를 끝 QA까지 아무도 돌리지 않았더니 밀린 시험 갱신 13건이 High로 쏟아졌다(돈 경제 전환). 둘 다 "누가 언제 한 번 돌리는가"가 정해지지 않아서다.

- **구현이 모두 정산되면 코디네이터가 전체 테스트를 한 번 돌린다. 끝 검증은 그 결과를 처리한 뒤에 뜬다.**
- 실패를 받는 자리로 계획에 **시험 갱신 Task**를 하나 둔다. 구현 Task 전부에 의존하고, 담당은 계획이 구현 쪽에서 정한다. 끝 검증 Task는 이 Task에 의존한다. 끝난 구현 Task를 다시 띄우는 길은 재시도 1회뿐이고 실패로 세어지므로 쓰지 않는다.
- 시험 갱신 Task가 준비되면 코디네이터가 전체 테스트를 돌린다. 통과하면 `skip`으로 닫는다. 실패가 있으면 실패 목록을 spec에 넣어 띄운다.
- 담당은 실패마다 둘 중 하나로 처리한다. **옛 기대값**이면 시험을 고치고, 기대값이 바뀐 근거가 된 계획이나 수락 기준의 줄을 리포트에 적는다. 근거를 댈 수 없으면 고치지 않고 **High로 보고**한다. 그 시험이 증거다.
- 옛 기대값을 고친 것은 결함이 아니다. 결함 원장에 올리지 않고 수정 라운드에 세지 않는다.
- 끝 검증 전에 전체 테스트를 다시 돌리지는 않는다. 남은 것은 최종 테스트가 본다.
- 구현 Task와 수정 Task의 spec 완료 기준에는 전체 테스트를 넣지 않는다. `AGENTS.md`의 `명령` 절에서 전체 테스트 명령에 표시를 두고, 완료 기준에 그 명령이 있으면 기동을 거부한다. 표시가 없는 프로젝트에서는 이 검사를 건너뛴다.
- 끝 QA의 spec에는 "전체 테스트는 이미 돌았다. 결과는 이 경로에 있다"를 넣는다. QA는 전체 테스트를 다시 돌리지 않는다.

### 3.4 계획 승인 때 검증의 크기

- 계획서 끝의 병렬도 수치 옆에 **검증 워커 ÷ 구현 워커**를 적는다. 교차 검토(PM, Planner)와 문서 확인도 검증 워커로 센다.
- 0.5를 넘으면 Planner가 이유를 적는다. 창구가 계획 승인 질문에 비율과 이유를 싣는다.
- 1a에서는 보여 주기만 하고 막지 않는다.

### 3.5 팀원이 한 명뿐인 팀장: 바꾸지 않는다

사용자 결정(2026-11-25): "D는 놔둬줘 언제 팀원이 추가될지 몰라서". 팀장을 거치는 기준은 지금대로 둔다. 2절의 관찰(7번)은 기록으로만 남긴다.

### 3.6 High의 증거

기준선에서는 주된 원인이 아니었다. 3.8의 "확정" 집계에 필요해서 넣는다.

High가 되려면 아래 둘 중 하나여야 한다. 아니면 Medium이다.

1. **실패가 관찰된 것.** 실패하는 테스트, 또는 재현 절차와 관찰 결과(명령 출력, 화면은 캡처). 결함을 낸 쪽이 낼 때 관찰해 붙인다.
2. **닫힌 목록에 드는 것.** spec의 수락 기준 위반, 그리고 `R = 3`의 정의(보안 경계, 데이터 손실, 서비스 중단)에 드는 것뿐이다. 실패 시나리오(어떤 입력과 상태에서 어떤 잘못된 결과가 나오는가)를 함께 낸다.

- `qa-inspector`가 내는 실패 테스트는 리포트 폴더에 둔다. 수정 워커가 테스트 폴더로 옮겨 통과시키고, 받은 테스트를 고치지 않는다.
- 확정 결함은 실패가 관찰된 것만 센다. 2번으로만 올라온 High는 고치되 "인용"으로 따로 센다.
- 실패하는 시험이 증거가 되려면 그 시험의 기대값이 지금의 수락 기준과 맞아야 한다. 옛 기대값으로 깨진 시험은 3.3대로 다룬다.
- 코드 읽기로 낸 High를 끝 QA가 다시 찾지 않게, QA의 spec에 이미 열린 결함 ID를 넣는다.

리뷰는 코디네이터가 수정 전 코드에서 테스트가 실패하는지 확인하라고 했다. 워커가 커밋하지 않고 폴더를 같이 써서 수정 뒤에는 수정 전 코드가 없다. 낸 쪽이 관찰하고 수정 쪽이 테스트를 못 고치게 하는 것으로 같은 의도를 채운다.

### 3.7 스냅샷 스크립트 (신규)

워커가 커밋하지 않으므로 "수정 diff"를 만들 방법이 필요하다. 임시 인덱스로 작업 폴더를 찍는다. 실제 인덱스와 작업 폴더는 건드리지 않고, 새 파일과 삭제가 잡히고, `.gitignore`의 경로는 빠진다(이 PC의 빈 저장소에서 확인했다).

```bash
snap() { GIT_INDEX_FILE="$(git rev-parse --git-dir)/snap-index" \
  sh -c 'git read-tree HEAD && git add -A && git write-tree'; }
git diff "$S1" "$S2" -- <경로>     # 두 시점 사이의 변경
git ls-tree -r "$S2"               # 파일별 해시
```

- 코디네이터가 Task를 정산할 때와 수정을 정산할 때 찍고, 나온 값을 장부에 적는다.
- 병렬로 도는 동안 찍은 두 스냅샷의 차이에는 다른 Task의 편집이 섞인다. 그 Task의 편집 범위로 좁혀서 쓴다.
- 에셋이 큰 저장소에서 걸리는 시간은 재지 않았다. 만들 때 잰다.

### 3.8 기록과 측정

- 장부에 **결함 원장**을 둔다: `ID | 제기한 검증 | 심각도 | 증거(관찰, 인용, 없음) | 라운드 | 상태(확정, 인용, 기각, 이월)`. 3.1의 검사가 이 표를 읽는다.
- **원장은 스크립트가 쓴다.** 코디네이터가 심각도를 손으로 적으면 3.1의 검사는 코디네이터가 적은 것을 다시 확인할 뿐이다. 스크립트가 검증 리포트의 결함 표에서 줄을 만든다. 그래서 코드 리뷰와 QA 리포트의 결함 표를 같은 칸(`ID | 심각도 | 증거 | 위치`)으로 맞춘다. 코디네이터가 고칠 수 있는 것은 상태 칸뿐이다.
- 수정 라운드 수는 손으로 적지 않는다. 스크립트가 수정 Task를 띄운 회차로 센다. 상한 검사도 그 값을 쓴다.
- `retro-measure.mjs`의 표에 2절의 항목을 열로 더한다. 회고 워커가 뜨지 않아도 코디네이터가 이 스크립트를 돌려 표를 남긴다.

### 3.9 작은 규칙

- **점검표.** 줄을 더하지 않는다. QA 리포트의 `## 점검표 후보`는 결함에 딸렸으면 그 수정 Task가 테스트로 만들고, 아니면 `product-manager`가 인박스에 "게이트 후보"로 옮긴다. QA는 spec이 넘긴 그 Task의 경계면만 대조한다.
- **"이미 아는 것".** 검증 워커의 spec에는 인박스 항목 가운데 그 Task 편집 범위의 파일을 가리키는 것만 넣는다.
- **작업 단위의 뜻.** spec 양식에 작업 단위의 뜻을 한 줄 넣는다. 워커는 이름을 지시로 읽는다.

### 3.10 기획의 교차 검토와 마감 워커를 조건부로

사용자 결정(2026-11-25): 1b에서 1a로 당긴다. 한 작업에서 구현 Task가 3개인데 기획 검토가 4번 떴고, 문서 동기화는 "영향 없음"으로 끝났다.

| 검증 | 켜는 조건 |
| --- | --- |
| Planner의 요구사항 검토 | 묶음 후보 항목에 `U ≥ 2` 또는 `R = 3`이 있다 |
| PM의 계획 대조 | 계획의 Task에 `R = 3`이 있다 |
| 문서 동기화(doc-steward) | 묶음의 BL이 `(계획됨)` 요구사항 줄, 계약 ID, 화면 ID에 연결돼 있다 |
| 회고 워커 | 측정 표에 실패나 재시도가 있다. 또는 수정 루프가 2회에 닿았다. 또는 마지막 회고 뒤 phase가 5번 지났다 |

- 점수는 백로그 항목의 `모델 근거` 줄과 계획의 Task에 이미 적는 값을 본다. 점수가 없으면 지금처럼 켠 것으로 본다.
- 문서 동기화의 조건은 표와 다르게 잡는다. 장부의 `## 라이브 문서 확인`에 행이 있으면 켜고, `필수 라이브 문서: 없음`이면 건너뛴다. 거의 모든 BL이 `(계획됨)` 요구사항 줄에 연결돼 있어서, 표의 조건으로는 건너뛸 일이 없다.
- **기획의 검토 둘.** 창구가 직접 띄우는 것이라 조건이 안 맞으면 띄우지 않는다. PM의 항목화 리포트와 계획서에 `켬` 또는 `끔`과 근거를 한 줄로 적는다. 계획 대조가 꺼졌으면 `review` 해시는 창구가 만든다. 계획이 새 버전으로 바뀌어도 조건이 안 맞으면 다시 띄우지 않는다.
- **문서 동기화와 회고 워커.** 지금처럼 계획에 넣고, 조건이 안 맞으면 `skip`으로 닫는다. 문서 동기화를 건너뛰면 장부에 `필수 라이브 문서: 없음`을 적어 `phase-documents.mjs`를 통과한다. 회고 워커를 건너뛰어도 측정 표는 코디네이터가 남긴다(3.8).
- 사용자는 어느 것이든 켤 수 있다. 원문을 브리프의 `## 사용자 결정`에 적는다.

## 4. 1b: Task 단위 재편

1a 뒤 측정을 보고 시작한다.

- **계획서의 `## 검증` 절을 Task 행으로 쓴다.** QA 흐름마다 "테스트로 못 덮는 이유"를 적는다. 이유를 못 적는 흐름은 구현 Task의 테스트로 쓴다.

```markdown
| Task | R | V | 리뷰 | QA 흐름 | 테스트로 못 덮는 이유 |
| --- | --- | --- | --- | --- | --- |
| T1 세션 저장소 스키마 변경 | 2 | 1 | Task 리뷰, T2 시작 전 | 없음 | |
| T2 로그인 잠금 | 1 | 2 | 없음 | 5회 실패 뒤 잠금, 시간이 지나면 해제 | 실제 시간 경과와 화면 상태가 얽힘 |
```

- **리뷰는 코드당 한 번.** `R ≥ 2`인 Task는 Task 리뷰를 한 번 받는다. 파일별 해시를 적어 두고, 통합 리뷰는 "리뷰 뒤 해시가 바뀐 파일"만 본다.
- **QA 워커 수는 흐름 수로 정한다.** 흐름 5개까지 워커 1명이다. QA Task마다 팀장을 따로 띄우지 않는다.
- **닫기 확인.** 재현 테스트가 없는 결함만, 결함을 낸 역할의 워커 한 명이 그 라운드의 결함을 묶어 본다.
- **횡단 QA.** 프로젝트에 자동 검사 명령이 있는 보안·접근성은 최종 테스트의 게이트로 돌린다.
- **예산을 강제한다.** 3.4의 비율이 0.5를 넘으면 계획 승인 화면에 초과분을 따로 표시하고 승인받는다.
1b를 시작하기 전에 8절의 결정이 필요하다.

## 5. 그 뒤

- **자동 조정.** 최근 5회 실행에서 확정 결함이 0이면 그 검증의 조건을 한 칸 좁힌다. Task 리뷰의 한 칸은 `R ≥ 2`에서 `R = 3`이고, QA의 한 칸은 `V ≥ 2`에서 `V = 3`이다. `R = 3`과 `V = 3`보다 더 좁히지 않는다. 통합 리뷰는 자동으로 조정하지 않는다. 사용자가 되돌릴 수 있다.
- **탈출.** 사용자나 다음 phase가 잡은 결함 가운데 꺼져 있던 검증의 범위였던 것이다. 최종 테스트가 잡은 것은 세지 않는다.
- **사실로 켜기.** 위험 경로를 건드렸는지, 기존 테스트를 고쳤는지, 재시도가 있었는지로 리뷰를 켜는 것은 탈출이 실제로 기록된 뒤에 한다. 지금 넣으면 근거 없이 검증을 늘리는 것이다.
- **규칙 만료.** 회고가 워커용 규칙을 더할 때는 근거 사건을 달고, 5 phase 동안 적중이 없으면 만료한다.

## 6. 기반 문서와 킷의 대조

| 기반 문서의 가정이나 규칙 | 킷의 실제 | 이 설계에서 |
| --- | --- | --- |
| 수정 뒤 끝 리뷰와 QA 워커 전부가 다시 뜬다 | 규칙으로는 그렇지 않다. 전체 테스트가 재현 테스트로 확인하고, 재현 테스트가 없는 결함만 그 결함 ID로 재검한다 | 기준선에서 세 작업 중 둘이 규칙과 다르게 돌았다. 3.2로 막는다 |
| 닫기 확인 워커가 라운드마다 뜬다 | 재현 테스트가 있으면 워커 없이 전체 테스트로 닫힌다 | 더 가벼운 지금 규칙을 남긴다 |
| 리뷰 원장에 리뷰한 커밋을 적는다 | 워커는 커밋하지 않는다 | 스냅샷과 파일별 해시를 적는다(3.7) |
| 구현 Task가 끝날 때 저장소 전체 게이트를 돌린다 | 작업 폴더를 같이 써서 다른 Task가 편집 중일 때는 전체 검사가 깨진다 | 구현이 모두 정산된 직후 한 번, 그리고 최종 테스트에서 돈다(3.3) |
| QA 체크리스트를 phase 끝에 버린다 | 쌓이는 것은 경계면 점검표이고 40줄 안팎이다 | 3.9. 주된 원인은 아니다 |
| 구현 Task마다 리뷰와 예산을 본다 | Task가 2개 이상인 팀은 팀장 Task 하나로 등록되고 코디네이터는 통합 보고만 본다 | 결정 A |
| 구현 뒤에 정해지는 검증을 띄운다 | 기동 스크립트는 승인된 계획의 Task만 등록하고, 앞 Task가 등록돼 있지 않으면 뒤 Task를 등록하지 못한다 | 결정 B |

## 8. 사용자가 정할 것

### 정해진 것 (2026-11-25)

- **D. 팀원이 한 명뿐인 팀장.** 그대로 둔다. 사용자 원문: "D는 놔둬줘 언제 팀원이 추가될지 몰라서".
- **E. 기동 스크립트의 `skip` 명령.** 더한다. 사용자 원문: "E는 그렇게해줘".

### 1b 전에 정할 것

**A. 검증의 단위.**
- 추천: 코디네이터가 등록하는 DAG의 Task. 팀장이 맡은 팀은 Task 하나로 본다.
- 다른 길: 팀 안의 팀원 Task까지 본다. 모든 팀의 팀장 규칙이 바뀐다.

**B. 조건이 안 맞는 검증을 건너뛰는 길.**
- 길 1(추천): 띄울 수 있는 검증을 조건부 Task로 계획하고, 조건이 안 맞으면 결정 E의 `skip`으로 건너뛴다.
- 길 2: 지금처럼 검증 팀장이 맡아 필요한 것만 띄운다.

**C. 뒤 Task가 기다리는 리뷰에서 High가 나왔을 때.**
- 추천: 뒤 Task를 세운다. 수정의 재현 테스트가 통과하면 푼다.
- 다른 길: 지금처럼 정하지 않는다.

## 11. 작성자가 정한 것

1. 기준선을 보고 1a의 중심을 문구 세 군데에서 기동 경로의 거부 넷(3.1~3.4)으로 바꿨다. 리뷰가 "규칙을 따르지 않은 것이면 스크립트 차단이 답"이라고 한 경우에 해당한다고 봤다.
2. 그래서 1a도 기동 스크립트를 고친다. spec 검사와 `skip` 명령을 더하고, 승인과 등록은 그대로 둔다.
3. 프로토타입 반영 작업을 보고 `skip`(3.1)을 1a에 넣었다. 사용자가 승인했다(8절 E). 팀원이 한 명뿐인 팀장은 사용자가 그대로 두라고 했다(8절 D).
4. 검증 워커 ÷ 구현 워커를 1b에서 1a로 당겼다. 1a에서는 보여 주기만 한다.
5. 코디네이터가 수정 전 코드에서 실패를 확인하는 대신, 낸 쪽이 관찰하고 수정 쪽이 테스트를 못 고치게 했다(3.6).
6. kiwoo는 작업을 지정받지 않아 가장 최근 것을 골랐다.
7. 작업 단위 이름은 모델 표와 스크립트가 쓰고 있어 그대로 두고, spec 양식에 뜻을 적는다.
8. 버전은 1a에서 0.4.0으로 올린다.
9. 돈 경제 전환 작업을 보고 전체 테스트를 끝 검증 앞에 한 번 돌리게 했다(3.3). 끝 검증이 그만큼 늦게 뜬다. 1차 설계에 넣었다가 뺀 것을 기록을 보고 다시 넣었다.
10. 사용자가 수정 뒤의 전 범위 검증을 큰 문제로 짚어 3.2를 넓혔다. 계획 검토 스크립트에 검사 둘을 더한다. 수정 Task는 DAG 입력의 `rounds` 표기로 알아본다.
11. 기획의 교차 검토와 문서 동기화·회고 워커의 조건부를 1b에서 1a로 당겼다(3.10). 사용자가 승인했다(2026-11-25, "응").
12. 마지막 점검(2026-11-25)을 반영했다. 결함 원장을 스크립트가 쓰게 했고(3.8), 전체 테스트의 실패를 받는 시험 갱신 Task를 두었고(3.3), 수정 뒤 검증의 팀장 금지를 뺐고(결정 D와 부딪쳐서), 문서 동기화의 조건을 장부의 행으로 바꿨다(3.10).
13. 승인 없이 phase 폴더 밖의 spec으로 띄우는 길은 이 검사의 대상이 아니다.

## 12. 열어 둔 값

- 검증 워커 ÷ 구현 워커의 0.5, "흐름 5개까지 워커 1명", 최근 5회, 만료 5 phase는 근거가 약한 출발값이다. 측정한 뒤 조정한다.
- QA 한 번의 증거 수집량(한 작업에서 PNG 12,170장)을 줄이는 규칙은 넣지 않았다. 어느 프로젝트에나 맞는 말로 쓸 방법을 찾지 못했다.
- 검증 도구 자체의 결함으로 라운드가 돈 경우(한 작업에서 High 7건)를 따로 다룰지는 정하지 않았다.
- 인박스 항목의 만료 기간은 정하지 않았다.
- 전체 테스트가 오래 걸리는 프로젝트에서는 3.3이 끝 검증을 그 시간만큼 늦춘다(한 작업에서 전체 한 번에 20분 남짓). 그 시간이 밀린 시험 갱신을 QA와 수정 루프로 처리하는 것보다 짧다고 봤으나, 다시 재서 확인한다.
