# 지식 단위 에이전트 설계

- 날짜: 2026-11-26
- 상태: 사용자 승인 대기
- 대상 버전: 0.6.0 (명단 형식이 바뀌어 이전 판과 호환되지 않는다)
- 기반: Anthropic "Building agents: When to fold subagents into your main agent loop"(2026-10-22)와 2절의 문서들

## 1. 의도

역할을 직함대로 잘게 나눈 에이전트와 팀장 계층을 걷어내고, **지식이 공유돼야 하는 단위마다 에이전트 하나**를 둔다. 전문성은 에이전트를 늘려서가 아니라 그 에이전트가 필요할 때 읽는 스킬로 준다.

사용자 원문(2026-11-26):

- "근래의 모델능력향상으로 그걸 걷어내는게 목표였는데"
- "팀 멀티에이전트 걷어내고 최신 트렌드에 맞게 안트로픽 공식문서나 openAI문서 들 참고해서 콘웨이의 법칙에 따른 agent 세분화의 단점을 걷어내고 효율적으로 돌아가게 하는 구조로"
- "기존의 에이전트가 여러개인건 동일하되, 팀장은 없어져도 될 것 같고, 너무 역할을 세분화했던걸 하나의 지식이 공유가되어야하는 단위로 뭉쳐야 된다는얘기야."
- "리서치의 같은 경우에는 리서치 에이전트가 있고, 리서치는 멀티에이전트의 장점이 아직 있다 보니까 서브에이전트들로 문서 조사시키는방식은 여전히 유용하니까 그렇게 가져가면좋겠고"
- "프론트 에이전트(UI UX 개발 테스트코드) 각각에 대해 스킬로 가지고 있는 공용 프론트엔드 에이전트와, 백엔드 에이전트(데이터베이스 백엔드 성능 보안), 검증 전용 에이전트(qa, 유닛테스트, 브라우저보기 등등) 이렇게 나누자는거"

## 2. 근거

원문을 열어 인용과 날짜를 확인한 것만 적었다.

| 기준 | 출처 |
| --- | --- |
| 팀이나 문제 유형마다 서브에이전트를 주면 에이전트 구조가 조직도의 사본이 된다("Conway's law at work") | Anthropic, [When to fold subagents into your main agent loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop), 2026-10-22 |

| 서로의 출력에 이어 붙거나 같은 데이터를 만지는 전문가는 합친다 | 같은 글 |

| 하네스에서 무엇을 뺄 수 있는지 모델이 좋아질 때마다 다시 시험한다 | Anthropic [2026-04-02](https://claude.com/blog/harnessing-claudes-intelligence), [2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps) |

| 절차는 스킬, 반드시 일어나야 하는 일은 훅, 병렬이나 격리가 필요한 곁일은 서브에이전트 | Anthropic [2026-06-18](https://claude.com/resources/articles/steering-claude-code-skills-hooks-rules-subagents-and-more) |

OpenAI 문서에는 조직도를 옮기지 말라는 명시 문장이 없다. 분리 기준이 역할이 아니라 계약(지시·도구·정책)이라는 점만 같다.

## 3. 구조

```
지금 (0.5.1)

창구
├ product-manager
├ planner
└ 코디네이터
    ├ 실행 팀장 ─ 팀원 (qa-inspector, code-reviewer, 프로젝트가 추가한 역할들)
    ├ doc-steward
    └ harness-engineer

바꾼 뒤 (0.6.0)

창구
├ product-manager     PM. 요구·백로그·설계·계획 (스킬)
└ 코디네이터
    ├ research        조사. 세션 안 서브에이전트로 나눠 조사
    ├ frontend        UX · UI · 개발 · 테스트 코드 (스킬)
    ├ backend         데이터베이스 · 백엔드 · 성능 · 보안 (스킬)
    ├ verifier        코드 리뷰 · QA(유닛 테스트, 브라우저 확인) (스킬)
    ├ doc-steward
    └ harness-engineer
```

`research`, `frontend`, `backend`, `verifier`는 모두 코디네이터 바로 아래의 같은 층이다. 어느 것도 다른 것의 서브에이전트가 아니다.

### 3.1 에이전트 단위

| 에이전트 | 공유하는 지식 | 스킬 | 따로 두는 이유 |
| --- | --- | --- | --- |
| `product-manager` | 요구와 계획 | `requirements-write`, `backlog-management`, `product-review`, `phase-planning`, `plan-orchestrate`의 설계·계획 절 | 사용자 결정을 모으는 대화가 실행과 다른 컨텍스트다 |
| `research` | 질문과 출처 | `research`(새로 만든다) | 독립 조사. 읽은 것이 다른 컨텍스트를 채우지 않게 하고 병렬로 돌린다 |
| `frontend` | 화면 하나를 만드는 데 드는 것 전부 | UX 설계, UI 설계, 프론트엔드 개발, 테스트 코드 | 백엔드와 인터페이스로만 만난다 |
| `backend` | 데이터와 서버 | 데이터베이스, 백엔드 개발, 성능, 보안 | 프론트엔드와 인터페이스로만 만난다 |
| `verifier` | 결과가 맞는지 판정하는 법 | `change-review`(코드를 읽는 검토), `qa-verification`(실행해서 하는 검증: 유닛 테스트, 브라우저 확인) | 블랙박스 검증. 만든 쪽의 판단을 물려받지 않는다 |

- PM과 Planner는 `product-manager` 하나가 된다(사용자 결정). `planner` 역할은 없어지고 그 스킬은 PM이 쓴다.
- 에이전트 정의 파일은 지금 양식(`docs/harness/templates/agent.md`)을 그대로 쓴다. `- 로드할 스킬:` 줄이 그 에이전트의 스킬 목록이다.
- 모든 에이전트는 위 스킬에 더해 `docs-management`를 공통으로 쓴다(3.8).
- 같은 에이전트를 여러 개 띄울 수 있다. 편집 범위가 겹치지 않는 일 단위마다 하나씩이다. 종류는 늘리지 않는다.
- `frontend`와 `backend`는 만드는 단위의 기본값이다. 프로젝트의 기술이 다르면 이름과 스킬을 바꾸거나 더한다(3.4, 3.7).

### 3.2 일이 흐르는 길

- **기획은 PM 한 세션이 잇는다.** 요구사항 정리, 요구사항 검토, 백로그 항목화, 설계, 계획, 계획과 수락 기준의 대조를 같은 컨텍스트에서 한다. 초반의 요구사항 검토는 PM의 일이다. 그 지식이 PM에게 있다(사용자 결정). PM과 Planner가 서로 하던 교차 검토 단계는 없어지고, 사용자 승인이 그 자리의 확인이다.
- 백로그 항목 하나는 **만드는 에이전트 하나가 처음부터 끝까지** 맡는다. 세부 설계, 구현, 테스트 코드를 같은 컨텍스트에서 한다. 직함별 단계로 넘기지 않는다.
- 인계는 두 번이다. 계획에서 만드는 에이전트로, 만드는 에이전트에서 `verifier`로.
- `verifier`는 지금의 `code-reviewer`와 `qa-inspector`를 합친 에이전트다. **스킬은 둘로 나뉜 채 둔다.** 코드를 읽는 검토(`change-review`)와 실행해서 하는 검증(`qa-verification`)은 다른 일이다(사용자 결정). Task의 spec이 어느 스킬을 쓰는지 적는다.
  - 중간 검토는 `change-review`만 쓰는 `verifier` Task다(작업 단위 `중간 변경 리뷰`).
  - 끝 검증은 영역마다 `verifier` Task 하나가 두 스킬을 모두 쓴다. 지금의 `일반 변경 리뷰` Task와 `흐름 검증` Task가 하나가 된다. 영역이 여럿이면 영역마다 하나씩 띄우고 결함 ID 접두어는 지금처럼 Task마다 다르게 준다.
  - 결과가 수락 기준을 채우는지의 대조는 지금처럼 `verifier`가 한다(`qa-verification`의 수락 기준 대조).
  - 그 Task의 배정은 해당하는 작업 단위 가운데 가장 높은 값이다. 보안이나 돈이 걸린 변경이면 그 고정 값을 쓴다.
  - 재검은 지금과 같다.
- 팀장이 없다. 계획이 Task를 일 단위로 나누고, 코디네이터가 그 Task를 에이전트에 직접 배정한다.

### 3.3 조사 에이전트

- `research`는 질문을 서로 독립인 하위 질문으로 나누고, **세션 안의 서브에이전트**(Claude Code의 Agent 도구, Codex의 subagent)에 병렬로 맡긴 뒤 출처와 인용을 확인해 요약 리포트 하나를 돌려준다.
- 서브에이전트는 Orca 워커가 아니다. 워커가 Orca 워커를 띄우지 않는다는 규칙은 그대로다.
- 일을 나눠 맡기는 팬아웃은 `research`만 한다. 다른 에이전트가 스크린샷, 큰 파일, 로그를 서브에이전트에 맡겨 요약만 받는 지금의 규칙(훅의 워커 규칙 ③)은 그대로다.
- 띄우는 곳은 둘이다. 창구가 설계 전에 기획의 입력으로 띄우고, 코디네이터가 계획의 조사 Task로 띄운다.
- 읽기 전용이다. 산출물은 조사 리포트뿐이다.
- `research` 스킬에 넣을 것: 질문을 나누는 법, 서브에이전트에 줄 지시의 네 가지(목표, 출력 형식, 볼 출처, 범위의 끝), 원문을 열어 확인하지 못한 것은 "미확인"으로 적는 규칙, 리포트 양식.

### 3.4 새 에이전트를 만드는 기준

기본은 스킬을 더하는 것이다. 에이전트를 새로 만드는 것은 아래 가운데 하나가 사실일 때뿐이다(2절의 2026-10-22 글).

1. 기존 에이전트에 넣으면 컨텍스트가 불어나 성능이 떨어지는 것이 관찰됐다.
2. 다른 일과 병렬로 돌고, 끝나면 그 컨텍스트를 버려도 된다.
3. 도구나 지시가 기존 에이전트의 것과 부딪친다(다른 런타임, 혼자 써야 하는 자원, 다른 권한).

서로의 출력에 이어 붙거나 같은 파일을 만지는 일은 한 에이전트에 둔다. 직함이 다르다는 것은 이유가 아니다.

### 3.5 모델 배정: 워커를 띄울 때마다 산정식을 쓴다

사용자 원문(2026-11-26): "agent worker생성시마다 모델산정식은 잘활용되서 생성해줬으면 좋겠어", "planner 모델은 유저가 정하게 해줘 일단 나는 fable/xhigh"

- 에이전트가 넓어졌으므로 점수는 에이전트가 아니라 **Task에 붙는다.** 같은 `frontend`라도 문구 한 줄 수정과 새 화면은 다른 모델과 effort를 받는다.
- `research`, `frontend`, `backend`, `verifier`의 모델 표 행은 모두 산정 행이다. 고정 행은 사용자가 고정이라고 정한 것(코디네이터, 보안·돈이 걸린 변경 리뷰 등)뿐이다.
- PM이 계획을 쓸 때 Task마다 C·U·R·V의 값과 근거를 적고, `model-routing.mjs plan`이 model과 effort를 계산한다. 지금의 산정식과 Codex 치환표를 그대로 쓴다.
- **기동 스크립트는 산정 행의 Task를 점수 없이 띄우지 않는다.** 점수가 없으면 기본값으로 넘어가지 않고 기동을 거부한다. 재시도는 F를 올려 다시 산정한다.
- 기동 직전 재평가(사용자가 위임한 Task)는 지금 방식 그대로다.
- **PM의 기획 세션은 사용자가 정한 값 하나로 뜬다.** setup의 질문에서 model과 effort를 함께 고르고, 그 값이 모델 표의 PM 기획 행에 적힌다. 기본값은 fable/xhigh다. 요구에서 계획까지 한 세션이 이으므로 값이 하나여야 한다. phase 끝의 완료 처리는 따로 뜨는 Task라 행을 따로 둔다.
- `research`가 세션 안에서 띄우는 서브에이전트는 Orca 워커가 아니라 이 식의 대상이 아니다. `research` 스킬이 훑는 일에는 가벼운 모델을 쓰라고 적는다.

### 3.6 기존 스킬과의 연결

사용자 원문(2026-11-26): "지금까지 잘만들어진 스킬들은 잘 연동돼서 사용했으면 좋겠어 예를들면 waterfall-timeline, dag-swimlane, phase-planning, docs-management등"

스킬은 지우지 않고 새 구조에 잇는다. 고치는 것은 팀과 팀장을 전제한 문구와 코드뿐이다.

| 스킬 | 누가 언제 쓰나 | 고치는 것 |
| --- | --- | --- |
| `phase-planning` | PM이 Task를 나누고 DAG를 쓸 때 | 일 단위로 나누는 규칙을 넣고 계층 패턴을 지운다 |
| `dag-swimlane` | PM이 승인 전 그림을, 코디네이터가 진행 그림을 그릴 때 | 레인을 팀이 아니라 에이전트 단위로 그린다. 팀장 표시를 지운다 |
| `waterfall-timeline` | PM이 T+ 예상을, 코디네이터가 진행을 보일 때 | `from-orca.mjs`의 팀장 판정과 옛 역할 이름을 고친다 |
| `docs-management` | 모든 에이전트(공통)와 `doc-steward` | 문서별 담당을 지식 단위로 옮긴다(3.8) |
| `backlog-management`, `requirements-write`, `product-review` | PM | 소유 역할 이름. `product-review`는 다른 역할이 검토한다는 전제를 지우고 PM이 자기 단계로 한다 |
| `change-review`, `qa-verification` | `verifier` | 소유 역할 이름. 본문은 그대로 |
| `harness-retro` | `harness-engineer` | 측정 지표(7절) |
| `coordinator`, `plan-orchestrate` | 코디네이터, 창구 | 4.2 |

### 3.7 에이전트를 만드는 도구

사용자 원문(2026-11-26): "특히 agent를 만들어주는 agent-author등 반드시 team-lead 기반으로 돌아가게만들어지는 양식은 거둬내야될것같구", "(스킬 본문을 프로젝트가 채우는 것은) Agent author라는 스킬이 할수있게끔 하는것이 좋을것같아."

**팀장 전제를 걷어낸다.**

- 양식 `team-skill.md`(팀 스킬)를 없앤다.
- `team-composition.md`의 "실행팀은 팀장이 되는 에이전트와 팀 스킬이 있어야 한다"는 절차를 없앤다.
- `agent-definition.mjs`의 "실행팀의 명시적 팀장 누락", "실행팀 스킬 누락" 검사와 명단의 팀장 칸 검사를 없앤다.
- `registration.check.mjs`가 고정해 둔 팀 명단과 옛 역할 이름을 새 것으로 바꾼다.

**`agent-author`가 하는 일은 셋이다.**

1. **스킬 더하기(기본).** 기존 에이전트에 스킬을 더할 수 있는지 먼저 본다.
2. **스킬 본문 채우기.** 에이전트의 스킬을 프로젝트의 기술과 지난 작업을 보고 쓴다. 키트가 틀만 주는 `frontend`와 `backend`의 스킬 여덟 개가 첫 대상이다. setup 7단계가 이 절차를 부른다.
3. **에이전트 만들기.** 3.4의 기준 가운데 하나가 사실일 때만 한다. 맡는 단위, 스킬 목록, 편집 범위, 모델 표의 산정 행을 함께 등록한다.

여기에 0.5.1 프로젝트의 옛 역할을 단위로 합치는 절차가 더해진다(4.4).

### 3.8 문서 담당: 그 지식을 가진 에이전트가 맡는다

사용자 원문(2026-11-26): "지식이 하나의 에이전트로 뭉치는 만큼, doc-steward가 전체로 문서를 검증도 하고 수정도 하지만, agent별로 그 문서에 맞는 지식을 갖고있는사람이 doc-management라는 스킬을 공통으로 사용해서 문서 담당도 지정했으면 좋겠어."

- **모든 에이전트가 `docs-management`를 공통 스킬로 쓴다.** 자기 문서를 쓰거나 고칠 때 읽는다. 일곱 에이전트의 스킬 목록에 모두 넣는다.
- **문서마다 그 지식을 가진 에이전트를 담당으로 지정한다.** 지금처럼 역할 파일의 `## 문서 책임` 표에 적는다. 키트의 기본 배정은 아래 표다.

| 문서 | 담당 |
| --- | --- |
| PRD, SRS, 백로그, WBS, 제품·범위 결정 기록 | `product-manager` |
| UI 명세와 화면 문서 | `frontend` |
| 아키텍처, API와 데이터 계약, 코드 지도, 운영 절차 | `backend` (화면 쪽 구조와 계약은 `frontend`) |
| 테스트 케이스, 요구사항 추적표 | `verifier` |
| 하네스 변경 이력 | `harness-engineer` |
| 문서 색인, 문서 사이의 연결 | `doc-steward` |

- **만든 에이전트가 제품의 사실을 바꾸면 같은 Task 안에서 자기 문서를 고친다.** 그 지식이 그 컨텍스트에 있다. 다른 역할에 넘겨 나중에 쓰게 하지 않는다.
- **`doc-steward`는 전체를 본다.** 코드, 테스트와 문서가 맞는지, 색인과 연결이 맞는지 확인하고 색인과 연결은 직접 고친다. 내용이 틀렸으면 담당 에이전트에게 돌려보낸다. 조건이 맞을 때만 뜨는 것은 지금과 같다.
- 프로젝트가 에이전트나 스킬을 더하면 `agent-author`가 문서 담당도 함께 등록한다. 담당이 없는 문서는 색인의 `작성자 배정 대기`에 남는다(지금 방식).

### 3.9 검증 수렴 규칙을 그대로 가져온다

사용자 원문(2026-11-26): "지난 검증과정에서의 워크플로우 개선한것도 반영됐으면 좋겠어(지나친검증의 문제점을 해결한거)"

`2026-11-25-verification-slim-design.md`의 1a가 0.5.x에 들어가 있다. 에이전트 이름이 바뀌어도 이 규칙들은 하나도 빠지지 않는다.

| 지금의 규칙 | 새 구조에서 |
| --- | --- |
| 고치는 것은 결함 원장의 High뿐이다. High는 증거(`관찰`, `인용`)가 있어야 한다 | 그대로. `verifier` 리포트의 결함 표가 원장이 된다 |
| 수정 Task는 `결함 ID:` 줄 없이는 뜨지 않는다. 고칠 것이 없으면 `skip`으로 닫는다 | 그대로 |
| 수정 뒤의 검증은 결함 ID와 `수정 diff:`만 본다. 재검은 재현 테스트가 없는 결함만 한다 | 그대로 |
| 구현이 끝나면 코디네이터가 전체 테스트를 한 번 돌린다. 실패는 시험 갱신 Task가 받고, 끝 검증은 다시 돌리지 않는다 | 그대로. 시험 갱신 Task는 그 코드를 만든 에이전트가 맡는다 |
| 재검이 아닌 검증 Task는 수정 Task 뒤에 걸 수 없다 | 그대로 |
| 수정 루프는 2회다. 3회째는 쓴 워커 수와 시간을 보이고 사용자에게 묻는다 | 그대로 |
| 계획 승인 때 검증 워커 ÷ 구현 워커를 보인다 | 그대로. 기획의 교차 검토가 없어져 세는 대상이 준다 |
| 문서 동기화와 회고는 조건이 맞을 때만 띄운다 | 그대로 |
| 기획의 교차 검토는 조건이 맞을 때만 띄운다 | 없어진다. PM 한 세션이 자기 단계로 한다 |
| 팀원이 한 명뿐인 팀장은 그대로 둔다(당시 결정) | 팀장이 없어져 해소된다 |

그 설계의 기준선에서 규칙으로는 못 줄였던 것 가운데 이번 구조가 줄이는 것은 셋이다.

- **Task마다 팀장이 팀원 한 명을 띄웠다**(일 9개에 워커 18, QA 팀장 8에 팀원 8). 팀장이 없으므로 일 하나에 워커 하나다.
- **같은 결함을 두 번 찾았다**(코드 읽기로 낸 High 5건 가운데 4건을 끝 QA가 다시 재현). 끝 검증 Task 하나가 읽고 실행하므로 한 번만 적는다.
- **기획 단계 10회 기동 가운데 검토가 4회였다.** PM 한 세션이 잇는다.

그 설계의 1b(계획의 검증 절을 Task 행으로 쓰기, 리뷰는 코드당 한 번, 예산 강제, 자동 조정)는 이번에 넣지 않는다. 0.6.0을 잰 뒤에 본다.

### 3.10 역할 양식과 스킬 양식

사용자 원문(2026-11-26): "팀이 없어지면서 사라지게 되는 몇가지 Agent항목을 보충할만한것이 없는지 조사한번만해줘서 넣어줘( 지금의 구조에서 있으면 좋을 Agent 양식 항목들 추천해서 개선 혹은 추가)"

팀 스킬 양식(`team-skill.md`)과 팀 명단이 없어지면서 거기에 적던 것이 갈 자리가 필요하다. 조사한 결과 이렇게 옮긴다.

| 사라지는 것 | 새 자리 |
| --- | --- |
| 팀 스킬의 에이전트 구성 표(맡는 일, 역할 스킬, 작업 단위) | 역할 양식의 `## 작업 단위와 스킬` 표 |
| 팀 스킬의 작업 흐름 표(순서, 산출물) | 같은 표의 `돌려주는 것` 칸과 스킬의 절차 |
| 팀 스킬의 직접 소통 짝 표에 있던 한도 | 역할 양식 `## 직접 협업` 표의 `한도` 칸 |
| 팀 스킬의 테스트 시나리오 | 스킬 양식의 `## 대표 사례` |
| 팀 스킬의 작업 규모별 모드 | 없앤다. 코디네이터가 일 단위로 배정한다 |
| 팀 명단의 팀장, 팀 스킬, 구분 | 없앤다 |

역할 양식(`docs/harness/templates/agent.md`)에 더하는 것은 다섯이다.

| 항목 | 내용 | 근거 |
| --- | --- | --- |
| `## 작업 단위와 스킬` | 표 `작업 단위 \| 쓰는 스킬 \| 돌려주는 것`. 에이전트가 넓어져서 어느 일에 어느 스킬을 쓰는지를 에이전트가 갖는다 | 접은 뒤에는 "맞는 스킬을 읽었는지"를 본다(Anthropic 2026-10-22). 맡긴 일은 압축된 결과로 돌려준다(같은 글) |
| `## 경계` | 맡지 않는 일과 넘기는 곳 | 좋은 에이전트의 지침은 옆 일로 번지지 않게 막는다(OpenAI Codex subagents 문서) |
| `## 따로 두는 이유` | 3.4의 세 기준 가운데 무엇인지, 근거, 다시 볼 때 | 3.4의 기준. 글이 적으라고 한 것은 아니고, 기준이 사라졌을 때 다시 합칠 수 있게 하려는 작성자의 추천이다 |
| `## 직접 협업`의 `한도` 칸 | 협의가 몇 번을 넘으면 배정자에게 올리는지 | 에이전트가 끝없이 도는 것을 막는 한도를 명시한다(Anthropic 2025-06-13) |
| 작업 원칙의 `- 런타임과 자원:`, `- 서브에이전트:` 줄 | 런타임, 혼자 써야 하는 자원, 필요한 MCP. 서브에이전트에 맡기는 일 | 도구와 권한은 그 일에 맞게 좁힌다(Claude Code subagents 문서, OpenAI 같은 문서) |

- 머리말은 지금처럼 `name`과 `description` 두 줄이다. Claude Code가 받는 `tools`, `model`, `skills` 같은 머리말 칸은 쓰지 않는다. 같은 파일에서 Codex 정의를 만들고, 모델과 effort는 모델 표와 산정식이 정하기 때문이다.
- `- 작업 단위:` 줄은 `## 작업 단위와 스킬` 표로 바뀐다.

**스킬 양식을 새로 둔다**(`docs/harness/templates/skill.md`). 팀 스킬 양식이 없어지면 스킬을 쓰는 양식이 없다. 절은 넷이다: 머리말(무엇을 하는 절차인지, 언제 읽는지, 쓰지 않는 경우), 절차, 하지 않는 것, 대표 사례(정상 하나와 실패 하나).

- 대표 사례를 에이전트가 아니라 스킬에 두는 것은 2026-10-22 글을 따른 것이다. 그 글은 전문가마다 평가를 따로 갖는 것을 실패 유형으로 들고, 평가를 스킬과 함께 두라고 한다.
- 스킬이 길어지면 참조 파일로 나눈다(Anthropic 2025-10-16).

### 3.11 구조도의 세 탭

사용자 원문(2026-11-26): "구조도(agent-toggle) 쪽에 문서 담당자 탭이랑 주로 협업하는관계를 다루는 탭에 대한 내용이 없는것같아. 거기도 신경써줘."

구조도에는 탭이 셋 있다. 구조도, 직접 협업, 문서 소유권이다. 팀이 없어져도 뒤의 둘은 역할 파일의 `## 직접 협업` 표와 `## 문서 책임` 표에서 만들어지므로 자료는 그대로다. 바뀌는 것은 이렇다.

| 탭 | 바꾸는 것 |
| --- | --- |
| 구조도 | 이름을 "에이전트 구조도"로. 팀 패널마다 있던 "업무 관계 보기"를 전체에 하나로 둔다. 실선은 코디네이터(PM은 창구)의 배정과 보고, 점선은 직접 협업이다 |
| 직접 협업 | 양쪽이 켜진 상대만 보이는 것은 그대로다. 행에 `한도`를 함께 보인다(3.10). 프론트엔드와 백엔드처럼 인터페이스로 만나는 쌍이 여기에 나온다 |
| 문서 담당 | 이름을 "문서 소유권"에서 "문서 담당"으로. 둘째 칸의 제목을 "담당 에이전트"로. 표 위에 "모든 에이전트가 `docs-management`로 자기 문서를 쓰고, 전체 정합성은 `doc-steward`가 확인한다"를 한 줄로 보인다. 담당 에이전트가 꺼져 있으면 "담당 꺼짐", 담당이 없으면 "담당 없음"을 그 행에 보인다 |

- 에이전트 카드를 눌렀을 때의 상세에는 양식에 더한 절(`따로 두는 이유`, `작업 단위와 스킬`, `경계`)이 함께 나온다.

### 4.2 새로 만들거나 고쳐 쓰는 것

| 대상 | 내용 |
| --- | --- |
| 역할 `research`, `frontend`, `backend`, `verifier` | 3.1의 단위 |
| 역할 `product-manager` | `planner`의 일(요구사항 검토, 설계, 계획과 DAG)을 받아 다시 쓴다 |
| 스킬 `research` | 3.3 |
| 스킬 `frontend`와 `backend`의 여덟 개 | 키트는 이름과 틀만 준다. 본문은 `agent-author`가 채운다(3.7). 설치 직후에도 역할 검사기가 통과해야 한다 |
| 스킬 `coordinator` | 팀 배정을 에이전트 배정으로. "항목 하나는 만드는 에이전트 하나가 끝까지"와 3.4의 기준을 적는다 |
| 스킬 `plan-orchestrate` | PM과 Planner 두 세션을 PM 한 세션으로. 교차 검토 단계를 지운다 |
| 스킬 `product-review` | PM의 스킬로 둔다. 요구사항 검토와 계획 대조를 PM이 자기 단계로 한다 |
| `phase-routing.mjs` | `intake`는 `product-manager`만 가리키고 `reviewer` 값을 없앤다. `team` 대신 `agent --agent <이름>`이 `direct`나 `wait`(꺼진 에이전트)를 돌려준다 |

### 4.4 0.5.1을 쓰던 프로젝트: 전부 새 구조로 옮긴다

사용자 원문(2026-11-26): "0.5.1을 쓰던 프로젝트에서도 싹다 이 방식으로 바뀌길 원해 다바꿀거야, 어차피 쓰는사람 나혼자야"

setup을 다시 돌리면 그 프로젝트를 새 구조로 옮긴다. 순서는 이렇다.

1. **키트가 깔았던 파일을 바꾼다.** 물러난 파일(`team-lead`와 `team-qa` 스킬, `team-skill.md`, 역할 `planner`·`code-reviewer`·`qa-inspector`)을 지우고 새 파일을 깐다. 프로젝트가 고쳐 쓴 파일은 지우거나 덮어쓰기 전에 목록으로 보여 주고 승인받는다.
2. **새 명단과 기본 에이전트를 깐다.** `agents.md`와 `research`, `frontend`, `backend`, `verifier`, 다시 쓴 `product-manager`.
3. **프로젝트가 추가한 역할을 단위로 합친다.** `agent-author`가 옛 명단(`team-org.md`)과 역할 파일을 읽고, 3.4의 기준으로 역할마다 어느 단위에 합칠지와 따로 남길지를 표로 추천한다. 사용자가 고른 대로 역할 파일의 지식을 그 단위의 스킬로 옮기고, 모델 표의 행과 문서 책임을 옮긴 뒤, 옛 역할 파일과 팀 스킬과 `team-org.md`를 지운다.
4. **검증한다.** 남은 에이전트가 모두 `agent-definition.mjs`를 통과하고, 프로젝트 문서에 남은 옛 역할 이름을 목록으로 보여 준다.

- 3번은 지식을 옮기는 일이라 스크립트가 아니라 `agent-author`의 절차다. 1, 2, 4번은 `setup.mjs`가 한다.
- 플러그인을 올린 뒤 아직 옮기지 않은 프로젝트에서 `agent-toggle`, `agent-author`, 기동 스크립트는 "setup을 다시 돌려 옮기라"는 안내로 멈춘다.
- 7단계에서 이름을 바꾸거나 뺀 기본 에이전트는 다시 돌려도 되살리지 않는다. 고른 결과를 설치 기록에 남긴다.

### 4.5 그대로 두는 것

**병렬 규칙은 그대로다.** 코디네이터는 지금처럼 Task를 의존, 편집 범위, 혼자 쓰는 자원과 함께 등록하고, `launchable`이 빈 슬롯 안에서 겹치지 않는 Task를 골라 띄운다. 깰 때마다 `launchable`을 돌리고, 대기 중인 Task를 당기고, 폭은 계획과 `launchable`이 정한다. PM이 계획을 쓸 때 보는 `parallel-rules.md`의 규칙과 임계 경로·병렬도 수치, 회고의 병렬 지표도 그대로다. 바뀌는 말은 하나다. "한 팀의 동시 워커는 4명 이하"가 "같은 에이전트의 동시 워커는 4명 이하"가 된다(사용자 확인 2026-11-26).

그 밖에 그대로 두는 것: 창구와 코디네이터, 훅 5개(`worker-intake-context`는 4.2대로 문구만 고친다), 대기(`wait`)와 정산(`settle`), 리포트 판정, 결함 원장, 테스트 장부, 승인 지점, 수정 루프 2회, 모델 산정식과 Codex 치환표, 3.6의 스킬 전부, `doc-steward`와 `harness-engineer`라는 역할, 플러그인 이름.

## 7. 무엇으로 효과를 보나

## 11. 만드는 사람에게 남긴 것

- PM의 model과 effort를 묻는 setup 질문의 선택지.

## 12. 되돌리기

플러그인을 0.5.1로 되돌려 setup을 다시 돌린다. 키트 저장소는 0.6.0 머지 커밋을 되돌린다. 4.4로 옮긴 프로젝트는 옮기기 전 커밋으로 되돌린다. 그래서 옮기기 전에 작업 트리를 커밋해 둔다.
