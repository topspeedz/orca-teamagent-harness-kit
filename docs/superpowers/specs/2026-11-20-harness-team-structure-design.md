# Orca 하네스의 역할 구성과 실시간 팀 구조도

2026-11-20 · 전체 설계 승인 완료 · 대상은 플러그인의 설치 템플릿, setup, agent-author와 사용자가 지정한 agent-toggle 스킬이다.

## 목적과 선택한 접근

한 프로젝트에서 창구가 일을 맡기는 경로, 워커가 읽는 작업 지침, 사용자가 보는 팀 구조도가 같은 관계를 나타내게 한다. 새 프로젝트에서 역할이 부족하면 setup이 필요한 역할을 추천하고, 나중에 agent-author로 추가한 역할도 같은 방식으로 일한다. 제품 문서의 첫 내용은 해당 분야를 담당한 사람이 작성한다.

| 검토한 접근 | 장점과 비용 | 결정 |
| --- | --- | --- |
| A. 팀 명단, 역할 정의, 모델 표를 연결 | 기존 파일을 읽는 워커와 구조도가 같은 근거를 사용한다. Markdown 작성 양식과 읽는 쪽이 함께 바뀌어야 한다. | 사용자 선택 |
| B. 단일 조직 명세에서 나머지 파일을 생성 | 한 파일에서 전체 관계를 편집하고 검사하기 쉽다. 기존 프로젝트의 이관과 생성된 파일의 수정 정책이 필요하다. | 대안으로 검토 |

## 역할과 실제 기동 경로

| 역할 | 배정·보고 | 책임 |
| --- | --- | --- |
| 사용자 창구 | 사용자와 대화하고 승인 전 운영 역할을 Orca로 기동 | plan-orchestrate로 접수·분기하고 그림과 승인 질문을 전달한다. |
| product-manager | 팀장 없는 운영팀. 승인 전에는 창구에 보고 | prd-write, srs-write, backlog-management로 제품 요구, 수락 기준, 백로그와 묶음을 작성한다. Planner의 계획을 제품 범위와 대조한다. |
| planner | PM과 동료. 실행 승인 전에는 창구가, 승인 뒤에는 팀장이 자기 팀에 배정된 Task의 복잡한 내부 분해를 위해 직접 기동 | superpowers의 설계·계획 절차와 phase-planning으로 기술 선택, Task 분해, 파일 쓰기 범위, 의존성, 병렬 배정, 검증 순서와 예상 그림 입력을 작성한다. 새 제품 결정은 PM과 창구에 돌려보낸다. |
| coordinator | 실행 승인 뒤 창구가 기동 | 승인된 계획으로 팀장에게 배정하고 보고·질문·수정 루프를 관리한다. 완료 처리에 필요한 운영 역할과 독립 역할을 직접 호출한다. |
| 실행 팀 | 코디네이터 ↔ 팀장 ↔ 팀원. 팀장이 ON이고 해당 팀의 Task가 단순한 1개뿐이면 코디네이터 ↔ 팀원 직접 배정·보고 가능 | 팀장은 팀 내부 Task를 배정하고 통합 보고한다. QA 팀은 qa-inspector와 code-reviewer의 기존 책임을 유지한다. |
| doc-steward | 코디네이터 직속, 무소속, 필수 | 개발·QA가 끝나면 docs-management로 코드·테스트·문서 정합성을 확인한다. 색인과 연결을 정리하고, 내용 결함은 원작성자에게 돌려보낸다. |
| harness-engineer | 코디네이터 직속, 무소속, 필수 | 문서 확인 뒤 매 phase harness-retro를 수행한다. 장부에서 지연·재작업·인계 누락을 확인하고 근거가 있을 때 하네스를 개선한다. 변경할 근거가 없어도 회고 결과를 남긴다. |

운영팀에는 팀장 워커를 만들지 않는다. PM에서 Planner로 넘긴다는 것은 브리프와 산출물을 통한 업무 인계다. 창구가 단계별 담당자를 기동하므로 PM이나 Planner를 서로의 상급자로 표시하지 않는다. 실행 이후에도 지정된 협업 상대끼리 팀을 넘어 사실 확인과 기술 협의를 할 수 있다. 새 Task 배정이나 범위 변경은 팀장·코디네이터에게 올리고 제품 범위 결정은 창구로 전달한다.

실행 spec에는 해당 Task의 협의 상대와 수신 경로를 싣는다. 상대가 기동되어 있으면 현행 Orca 메시지 경로로 질의·회신하고, 꺼져 있거나 호출할 수 없으면 배정자에게 돌려보낸다. 협의 결과로 정본이나 계획이 바뀌면 원작성자가 근거를 남긴다. 기존 사용자 승인·대기 규약은 유지한다.

실행 승인 뒤 한 팀이 맡을 Task가 2개 이상이거나 1개여도 분해에 전문 판단이 필요하면 팀장을 거친다. 팀장이 OFF이면 Task 수와 관계없이 해당 팀은 배정 대기다. 팀장은 이미 배정받은 Task를 승인 범위 안에서 나누는 데 깊은 설계가 필요하면 Planner를 직접 호출한다. Planner는 분해안을 팀장에게 돌려주고, 팀장이 팀원에게 배정한다. 구조도에는 이 호출을 팀장의 임시 작업 배정으로 표시하고 Planner의 소속은 운영팀으로 표시한다. 승인 범위 변경이나 다른 팀 배정이 필요하면 팀장이 배정 전에 코디네이터에게 올린다.

## 세 가지 접수 경로

| 요청 | 먼저 하는 일 | 계획·승인 |
| --- | --- | --- |
| 새 요구사항 여러 개 | PM이 원문과 PRD·SRS·백로그 ID를 대조해 항목화한다. Planner가 누락과 계획 가능성을 검토한다. | 사용자가 전체 요청의 반영 여부와 이번 묶음을 확인한 뒤 Planner가 설계·계획한다. |
| 사용자가 백로그 ID 지정 | 창구가 지정한 묶음을 Planner에게 바로 전달한다. | PM의 항목화·묶음 선정 절차를 반복하지 않는다. 없는 ID, 완료된 항목, 범위를 넓혀야 하는 선행 조건은 구체적으로 올린다. |
| 기존 백로그에서 한 phase를 위임 | PM이 진행 가능한 항목의 우선순위·선행 조건·연관성을 바탕으로 한 가지 목표와 묶음을 고르고, 선택 이유를 적는다. | 묶음 승인을 따로 묻지 않고 Planner에게 넘긴다. 실행 승인 화면에서 사용자가 목표·선정 이유·항목을 함께 확인하고 바꿀 수 있다. |

제품 백로그의 단위는 사용자가 확인할 수 있는 결과와 수락 기준이다. 실행 Task에는 해당 백로그 ID와 실제 선후행 관계, 런타임·모델·effort, 쓰기 범위와 검증 방법을 기록한다. 하나의 항목을 여러 워커가 맡거나 여러 항목이 하나의 선행 계약을 공유할 수 있다.

plan-orchestrate에서 사용자가 ID를 명시한 경우에는 기존 ‘해법이 정해진 작업’ 단축 규칙보다 지정 ID 경로를 먼저 적용한다. 작은 항목도 Planner가 첫 담당자다. 이 분기 변경을 plan-orchestrate 밖의 일반적인 단일 파일 수정에 확대하지 않는다.

창구는 dag-swimlane과 waterfall-timeline으로 설계의 팀 단위 흐름과 계획의 Task 단위 흐름을 보여 준다. 시작 전 DAG는 대기 상태, 워터폴은 T+ 예상 모드다. 새 요구·명시 ID 경로는 현행 설계·계획 승인 절차를 따른다. 묶음 선정을 위임한 경로는 중간 승인을 따로 요구하지 않고 최종 예상 그림으로 실행을 승인받는다. 사용자가 범위를 바꾸면 영향을 받는 계획과 그림, 리뷰를 갱신한다. 승인 뒤에는 코디네이터가 같은 Run의 장부로 진행 상태를 갱신한다.

## 기본 스킬과 모델 배정

별도 prd-writer와 pm-reviewer 에이전트는 새 설치 기본 명단에서 뺀다. PM과 Planner는 공용 리뷰 스킬을 사용한다. 작성자 자가 점검은 상대 역할의 검토와 구분한다. PM이 요구사항을 새로 썼다면 Planner가 원문 누락과 실행 가능성을 본다. Planner가 계획을 쓰면 PM이 승인 범위와 수락 기준을 대조한다. 검토 기록은 검토한 문서 버전·백로그 ID·결과·열린 쟁점을 남긴다. 동일 버전의 검토를 반복하지 않는다.

setup의 초기 질문과 기존 QA, coordinator, dag-swimlane, waterfall-timeline, plan-orchestrate, phase-planning, harness-retro는 유지한다. 문서 관리 역할과 스킬의 설치 이름은 기존 doc-steward와 docs-management를 기준으로 한다.

새 설치에서 PM과 Planner의 작업별 기본값은 다음과 같다. 런타임은 Claude이며, 사용자는 기존 모델 표 설문에서 각 행을 조정할 수 있다.

| 역할 | 작업 | 기본 모델 | 기본 effort |
| --- | --- | --- | --- |
| PM | PRD·SRS 작성 | Opus | max |
| PM | 수락 기준 작성·백로그 항목화·묶음 선정 | Opus | high |
| PM | 계획 대조 | Opus | medium |
| PM | 백로그 완료 처리·장부 정리 | Opus | medium |
| Planner | 요구사항 검토 | Opus | high |
| Planner | 기술 설계 | Fable | setup에서 선택한 high 또는 max |
| Planner | 실행 계획·DAG 작성 | Fable | setup에서 선택한 high 또는 max |

설치 시 Planner effort 질문의 답은 기술 설계와 실행 계획 두 행에만 적용한다. 두 작업은 이후에도 각각 Opus 또는 Fable과 high 또는 max를 선택할 수 있다. 같은 역할의 모델은 역할 이름을 유지한 채 작업 행에서 선택한다. 기존 프로젝트에서는 사용자가 지정한 작업별 설정을 보존한다.

모델 표에 저장한 작업별 설정은 다음 계획에서 사용한다. 실행 승인 시점의 Task별 배정(런타임·모델·effort)은 아직 등록하거나 기동하지 않은 Task에도 적용한다. 사용자가 현재 Run의 배정을 바꾸도록 요청하면 해당 Task의 배정과 DAG를 갱신하고 다시 승인받은 뒤 새 값으로 기동한다.

## setup의 문서·담당자 설계

1. 설치 시 코드 지도와 12개 번호 폴더의 초안 13개를 준비한다. 경로 기준은 [현재 설치 경로표](../../../skills/setup/references/document-drafts.json)다. API·DB 계약, ADR, 런북은 이름이 정해지기 전까지 각 폴더의 draft.md를 쓴다. 실제 기록이 있는 기존 파일과 색인에 지정된 다른 경로의 정본은 보존한다.
2. 제품 문서 작성 양식 12개의 정본은 `docs/harness/templates/product-docs/`에 둔다. setup이 만드는 초안 13개와 docs-management가 이 양식들을 함께 참조한다. API·DB 계약 초안은 같은 `contract.md`를 쓴다. 기존 프로젝트의 `.claude/skills/docs-management/references/forms/` 링크도 계속 열린다. 설치 초안, 작성법, 실제 제품 사실은 구분한다.
3. setup은 정해진 라이브 문서별로 경로·양식을 확인하고, 해당 내용을 결정하거나 실제로 구현·검증하는 역할을 작성 담당으로 제안한다. 지정된 에이전트만 그 문서의 내용을 처음 작성하고 이후 변경도 반영한다. PRD·SRS는 PM이 맡는다. 여러 분야가 한 파일을 공유하면 절별 작성자를 명시한다. 색인은 doc-steward가 관리한다.
4. 담당자가 없으면 역할과 맡길 문서, 필요한 근거를 함께 제안한다. 사용자는 역할 생성, 나중에 배정, 해당 영역이 필요 없음 중 선택할 수 있다. 뒤의 두 선택은 각각 미배정과 해당 없음으로 남긴다. 이 선택을 이유로 기존 문서나 이미 만든 초안을 삭제하지 않는다. 권고를 거절하면 doc-steward에게 제품 내용의 첫 작성을 넘기지 않는다.
5. agent-author는 에이전트를 생성할 때마다 미배정 문서·절을 새 역할의 전문성과 대조한다. 단일 역할 추가와 팀 전체 생성에 동일하게 적용한다. 맞는 항목만 문서 경로·담당 절·추천 이유와 함께 제시하고, 사용자가 선택한 담당 범위를 역할 정의에 기록해 구조도에 표시한다. 미선택은 미배정으로 두며, 이미 지정한 작성자와 해당 없음 항목은 추천 대상에서 제외한다.
6. 개발 중 미배정 문서에 실제 변경이 필요해지면 발견자가 근거를 남기고 코디네이터가 담당 지정 요청을 올린다. doc-steward는 종료 시 정합성과 누락을 확인해 지정 작성자에게 수정을 요청한다. 문서 담당은 역할 지침·구조도·리뷰에서 확인하며, 편집 차단 훅은 추가하지 않는다.

### 작업 이력과 라이브 문서의 연결

Task 리포트·리뷰 기록·phase 이력은 기존 `_workspace/`나 팀별 문서 경로에 둔다. 현재 제품 상태에 영향을 주는 결과만 관련 라이브 문서로 연결한다. 그때는 프로젝트가 정한 경로와 양식, 해당 문서·절의 지정 작성자를 따른다. 기존 색인에 승인된 다른 정본 경로가 있으면 그 경로를 쓴다.

라이브 문서가 달라지는 Task는 spec에 실제 문서와 절·ID를 적는다. 작업자와 문서 작성 담당이 다르면 작업자는 리포트에 변경 근거와 인계 대상을 남기고 지정 작성자가 반영한다. 예를 들어 QA가 발견한 API 응답 변경은 QA 리포트에 재현 근거를 남기고 API 계약 작성자가 해당 연산 절을 갱신한다. 이력만 남기는 작업은 팀 리포트로 마칠 수 있다.

작성 담당자가 직접 내용을 반영한다. 검토 담당자는 확인한 문서의 위치와 결과를 남기며, 수정이 필요하면 원작성자에게 넘긴다. 문서가 이미 현행이면 무엇을 대조했는지 기록한다. 인계만 끝난 항목은 실제 반영과 구분하고, phase 마감 때 코디네이터가 원작성자의 반영 또는 현행 확인 결과까지 추적한다. doc-steward는 제품 문서 사이의 정합성과 연결을 확인한다. 하네스 개선은 제품 문서 대신 해당 하네스 문서로 연결한다.

필수 라이브 문서 수정은 이번 phase에서 반영하고 확인하는 것이 기본이다. 마감까지 반영하기 어려우면 코디네이터가 창구를 통해 사용자에게 이월 여부를 묻는다. 답변을 기다리는 동안 phase는 열어 둔다. 사용자가 명시적으로 이월하면 PM은 해당 백로그 항목에 남은 문서·절, 지정 작성자(없으면 미배정), 이월 사유를 기록하고 그 항목을 미완료로 남긴다. 코디네이터는 나머지 완료 항목의 정산과 하네스 회고를 거쳐 phase를 마감한다.

UI 담당자를 추가하면 같은 협업 관계를 양쪽 역할 카드에서 따라갈 수 있어야 한다. 읽는 참고 문서와 자신이 작성할 문서를 구분한다. 새 에이전트의 전문성은 [agent-author 조사 기준](../../../skills/agent-author/references/agent-corpus-research.md)의 지정 저장소와 기존 프로젝트 근거로 작성한다. 전문성을 요하는 역할은 관련 원문을 비교하고, 채택한 판단 기준·검증 방법·출처를 남긴다.

setup과 agent-author는 같은 역할 양식을 써서 독립 역할, 기존 팀원, 팀장과 팀원으로 구성된 팀 전체를 만들 수 있어야 한다. 승인된 역할·팀만 등록하고 기존 명단·모델 행과 중복을 피한다. Codex를 함께 쓰는 프로젝트는 기존 동기화 방식으로 역할 TOML과 스킬 포인터를 맞춘다.

## 설치 후 agent-author의 작성 품질 (검토 제안)

현재 제작 경로에는 두 출력 양식이 있다. [agent-author](../../../skills/agent-author/SKILL.md)는 단일 역할 작성 시 영문 범용 양식을 제시하고, 팀 등록 시 호출하는 [setup의 팀 구성 절차](../../../skills/setup/references/team-composition.md)는 프로젝트의 [하네스 양식](../../../template/docs/harness/templates/agent.md)을 사용한다. 범용 양식에는 전문 판단과 실패 대응을 쓰는 절이 있지만 하네스 양식에는 같은 내용을 어떻게 담을지 명시하지 않는다. 반대로 범용 양식의 예시 YAML에는 하네스의 Codex 동기화가 받지 않는 `model: inherit`가 있다.

임시 설치 템플릿에서 기존 planner의 본문을 `Do good work.` 한 줄로 바꾸자 모델 표 검사와 Codex 동기화가 모두 성공했다. 같은 파일에 범용 양식의 모델 필드를 넣자 동기화는 실패했다. 이 실험은 현재 자동 검사가 무엇을 구분하는지 보여 준다. 특정 사용자가 생성한 파일의 실패 경위는 실제 결과물과 대조해야 한다.

개선 제안은 다음과 같다.

1. setup을 마친 프로젝트에서는 단일 독립 에이전트, 기존 팀원 추가, 팀 전체 생성 모두 프로젝트의 `docs/harness/templates/agent.md`에서 시작한다. 범용 템플릿의 전문 판단 작성법은 하네스 양식에 반영한다. 프로젝트가 선택한 모델은 작업 단위별 모델 표에서 읽는다.
2. 새 전문 역할을 요청하면 지정 저장소에서 관련 역할 원문을 찾아 프로젝트에서 실제로 마주칠 결정에 대조한다. 산출물에는 핵심 분기, 선택 근거, 실패 신호, 검증 방법, 실제로 읽은 근거의 위치가 남아야 한다. 상세 근거는 역할용 reference나 기존 제작 보고에서 찾을 수 있게 한다. 접근하지 못한 자료는 미확인으로 적는다.
3. 완료 시 양식·연결과 내용 품질을 각각 검토한다. 정해진 절과 미작성 자리표시자, 역할·스킬·문서 경로, 명단과 모델 표 연결은 기계적으로 확인할 수 있다. 전문성은 기존 품질 검사표를 활용해 프로젝트의 대표 요청과 실패 사례를 대입하고, 작성된 지침으로 담당자의 행동·검증 증거·인계 상대를 결정할 수 있는지 확인한다. 자기 평가 점수만으로 이 검사를 대신하지 않는다.

### 두 양식을 함께 쓰는 방법 (확정)

하네스 설치 프로젝트에서 채우는 출력 양식은 `docs/harness/templates/agent.md` 하나다. setup에서 팀 전체를 만들거나 나중에 agent-author로 한 명을 추가할 때 모두 대상 프로젝트의 이 파일을 읽는다. `agent-author/references/agent-definition-template.md`는 같은 작업에서 함께 읽되, 전문 판단을 끌어내는 작성 질문과 좋은 예를 제공한다. 이 파일의 독립 설치용 출력 예시는 하네스가 없는 프로젝트용으로 구분한다. 생성한 역할 파일 본문에는 작성 질문과 안내 문장을 남기지 않는다.

| 통합 양식의 절 | 원래 두 양식에서 여기에 모을 내용 |
| --- | --- |
| 머리말과 핵심 역할 | 하네스 형식의 name·description, 역할이 언제 호출되고 어떤 결과를 내는지, 담당과 비담당 경계 |
| 작업 원칙 | 로드할 스킬, 확인된 도구, 편집 범위, 승인 경계. 명단에서 소속을, 모델 표에서 모델·effort를 읽는다. |
| 전문 판단 | 이 역할이 자주 마주치는 선택마다 조건·판단 근거·행동·확인할 증거·실패 시 대응을 연결한다. 근거는 실제 프로젝트 파일이나 확인한 참고자료를 가리킨다. |
| 입력과 출력 | 입력 정본과 누락 시 처리, 수행 순서, 결과물 경로와 보고 대상. 첫 작성·수정·정합성 확인을 구분해 담당 문서와 절을 명시한다. |
| 완료 기준 | 실제 산출물에서 통과를 판정할 증거, 재작업 조건, 검증하지 못했을 때 남길 기록 |
| 다시 호출될 때 / 오류 처리 / 협업 | 기존 하네스 절을 유지한다. 전 회차의 결과와 미결 사항, 재개·중단 조건, 직접 협의 상대와 목적, 배정·범위 변경을 올릴 경로를 담는다. |

예를 들어 API 계약 담당자에게 “호환성을 확인한다”만 적으면 어떤 상황에서 무엇을 할지 결정할 수 없다. 통합 양식에서는 “응답 필드 삭제 요청이 들어오면 계약 정본과 실제 소비 코드를 대조한다. 사용 중이면 그 소비자의 담당자와 전환 순서를 협의하고, 승인된 범위가 바뀌면 팀장에게 올린다. 완료 보고에는 영향을 받는 소비자와 계약 테스트 결과를 남긴다”처럼 쓴다. 실제 생성본에는 해당 프로젝트에서 확인한 경로와 역할명을 사용한다.

형식 검사는 하네스에서 허용한 머리말, 필수 절, 표의 역할·경로 참조를 본다. 내용 검토는 대표 요청을 하나 골라 이 정의만으로 판단·검증·인계가 가능한지 본다. 두 검사의 결과를 나누어 보고한다.

## 구조도 동작

Unity 예시의 팀 색상, 역할 카드, 팀 구조도·직접 협업·문서 소유권 세 보기를 재사용한다. 실선은 배정·보고, 점선은 직접 협의다. 팀장 없는 운영팀에 가상의 팀장을 그리지 않는다. 창구의 기획 단계와 실행 승인 뒤의 코디네이터 배정을 구분하고, doc-steward와 harness-engineer는 각각 독립 역할로 표시한다.

**팀장 OFF는 시안 A로 확정했다.** 팀장 카드에 OFF, 원래 팀에 ‘팀 배정 대기’를 표시하고 팀장을 지나는 배정·보고선을 비활성화한다. 켜진 팀원은 같은 팀에 남는다. 양 끝이 켜진 직접 협업선과 문서 담당은 유지한다. ON으로 되돌리면 배정선이 복구된다. 별도 영역에 활성 팀원을 옮기는 시안 B도 비교했다. 사용자는 소속과 대기 사유를 같은 팀에서 보는 A를 선택했다.

현재 agent-toggle의 실시간 갱신 주기, Claude/Codex별 정의 토글, 키트 설치와 수정 파일 보호를 유지한다. 구조도의 기본 관점은 현행 활성 Claude 역할 기준이고 Codex 정의는 해당 엔진 원문에서 확인한다. 개인별 스킬을 전역에서 쓰는 사용자에게는 설치 원본과 수정 대상 위치를 구분해 안내한다.

플러그인이 소유하는 변경은 템플릿과 역할 생성 절차다. 구조도 파서·화면은 사용자가 지정한 별도 스킬 `~/.claude/skills/agent-toggle/`의 변경 대상이다. 프로젝트 setup만으로 전역 스킬을 덮어쓰지 않는다. 실제 배포에서도 두 구성 요소가 같은 명단·역할 양식을 읽는지 각각 확인한다.

### 구조도에서 문서·모델·협업 상대 열기

- **`docs/ · 공통 기준 문서` 버튼**을 누르면 코드 지도와 12개 번호 폴더에 해당하는 13종을 모두 보여 준다. 각 항목에 문서 종류, 프로젝트에서 쓰는 경로, 지정 작성자를 함께 표시한다. 문서 경로를 누르면 그 파일의 본문이 열린다. 경로는 문서 색인에 지정한 정본을 우선하고 초안 단계에서는 설치 경로표의 경로를 쓴다. 작성자 이름은 소속 팀 색상의 태그로 표시하고, 태그를 누르면 해당 에이전트의 상세 팝업이 열린다. 한 문서를 나눠 쓰면 각 절 옆에 해당 작성자 태그를 표시한다. 미배정과 해당 없음도 구분한다.
- **문서 소유권 탭 (시안 확인·확정)**은 문서·범위마다 한 행을 두고 `문서 · 범위`, `정본 작성자`, `주요 검토자` 세 열로 표시한다. 첫 칸에는 문서 경로와 해당 범위를 함께 적는다. 정본 작성자와 주요 검토자는 그 범위에 지정된 역할을 각각 소속 팀 색상의 담당자 태그로 표시한다. 검토자가 여럿이면 각자 태그를 가지며, 어느 열에서든 태그를 누르면 해당 에이전트의 상세 팝업이 열린다. 주요 검토자는 역할 정의에 명시된 검토 범위에서 읽는다. 시안에 사용한 PRD·SRS 외의 배정은 화면 확인용 예시다.
- **직접 협업 탭**은 Unity 시안처럼 협의 주제마다 참여 역할과 협의 목적을 한 행에 묶는다. 역할 이름은 문서 소유권 탭과 같은 팀 색상의 태그로 표시하고, 협의하는 상대는 `↔`로 연결한다. 어느 쪽 태그를 눌러도 그 역할의 상세 팝업이 열린다. 협의 상대와 목적은 역할 정의에 명시된 내용을 사용한다.
- **`모델 선택 표` 버튼**을 누르면 setup에서 사용자에게 제공하는 [모델 선택 HTML 화면](../../../skills/setup/assets/model-survey.html)이 그대로 열린다. 사용자는 프로젝트의 현재 값을 조회하고 같은 화면에서 작업 단위별 런타임·모델·effort를 선택할 수 있다. 구조도에서 연 화면의 `저장`을 누르면 선택값을 현재 프로젝트의 `docs/harness/model-selection.md`에 즉시 반영한다. 저장을 마치는 데 별도 채팅 확인은 필요 없다.
- **에이전트 카드**를 누르면 Unity 시안처럼 역할 상세 팝업이 열린다. ‘직접 협업 상대’는 시안과 같은 태그 디자인을 쓰고 각 태그에 상대 팀의 색을 적용한다. 태그를 누르면 그 상대의 역할 상세로 이어진다. ‘읽는 입력’과 ‘작성하는 문서·산출물’을 구분하고, 작성 항목 안에서도 담당 라이브 문서·절과 작업 리포트 등 산출물을 구분해 보여 준다. 핵심 책임·입력·작성물·검토자·협업 상대·완료 기준은 내용별로 묶고 라벨 색상으로 구분한다.

## 기본 설치에서 줄일 파일 (설계 제안)

현재 설치본의 호출처와 새 역할의 책임을 대조했다. 아래 제거 시점은 **새 버전의 설치 템플릿**을 기준으로 한다.

| 기존 파일 또는 스킬 | 새 구성에서의 처리 | 제거 전에 확인할 일 |
| --- | --- | --- |
| `agents/prd-writer.md`, `agents/pm-reviewer.md` | 앞서 정한 대로 새 기본 역할에서 제외한다. | PM의 PRD·SRS 작성과 PM·Planner의 상호 리뷰를 연결한다. 옛 역할명으로 워커를 띄우는 경로와 모델 행도 전환한다. |
| `team-harness/SKILL.md` | 독립 회고 담당에게 쓰이지 않는 1인 팀장 승격·팀원 배정 절차를 제거한다. | 측정과 근거 있는 변경·변경 이력은 harness-retro, 실패 시 재시도와 최종 보고는 coordinator에서 확인한다. 하네스 팀을 찾는 명단·예시도 갱신한다. |
| `product-planning/SKILL.md`와 같은 이름의 Codex 포인터 | 기존 역할별로 읽을 파일을 고르던 진입점을, 새 역할 스킬이 연결된 뒤 제거한다. | `requirements.md`의 요청 대조·요구사항 작성 규칙은 prd-write와 srs-write에 나누고, `review.md`는 공용 리뷰에, `decomposition.md`와 `prioritization.md`는 backlog-management에 옮긴다. 새 요구사항과 자동 묶음 선정 양쪽에서 근거를 찾아갈 수 있어야 한다. |
| `team-product/SKILL.md` | **통합 확정.** 운영팀과 PM·Planner의 소속은 명단에 유지하고, 새 설치에서는 별도 운영팀 스킬을 없앤다. | 단독 PRD·계획 검토 요청의 배정, 리포트 인계, 재작업 한도와 재개는 plan-orchestrate에 둔다. 백로그 완료·보관은 backlog-management, 실행 뒤 PM 호출과 정산은 coordinator에 둔다. |

QA의 team-qa·team-lead·change-review·qa-verification은 서로 다른 호출자와 책임이 있다. 다이어그램 번들은 전역 스킬이 없는 프로젝트에서 필요하고, DAG 렌더러는 예제 HTML에서 CSS를 읽는다. `*.check.mjs`는 setup verify가 설치 후 탐색해 실행한다. 이 파일들은 사용처가 확인됐다. 저장소의 `examples/dev-team/`은 수동 설치 예제로 기본 설치에 복사되지 않는다.

현재 setup은 템플릿에서 빠진 옛 역할을 기존 프로젝트에서 자동 제거하지 않는다. 새 설치와 달리 기존 설치에서는 진행 중인 phase, 사용자 수정, 토글 OFF 파일, 생성한 Codex 정의를 확인하고 전환 범위를 제시한다. 기존 리포트는 원래 이름으로 읽을 수 있어야 한다. 정리 완료 기준은 옛 이름 중 **새 워커를 띄우거나 스킬을 로드하는 참조**가 없어지고 과거 기록으로부터의 재개가 되는 것이다.

설치 번들의 waterfall-timeline은 사용자 전역판에서 가져온다. 전역 스킬이 없는 프로젝트에서도 시작 전에는 T+ 예상 일정을, 실행 중에는 실제 시각 축에 완료·진행·대기 작업과 예상 종료를 표시한다. 여러 Run의 진행 자료도 같은 시간축에 합칠 수 있다. 사용자판의 Orca 변환기는 막대 시작에 Task 생성 시각을 사용하므로, 하네스가 Task를 미리 등록한 경우에는 워커 기동 전 대기도 포함된다.

## 기존 설치와 검증 기준

기존 팀·역할 지침에 새 표가 없으면 읽을 수 있는 기존 정보만 표시한다. 빠진 협업선이나 문서 소유권을 역할 이름으로 추정하지 않는다. 이전 버전의 prd-writer·pm-reviewer·1인 harness 팀, 모델 행, 스킬 포인터, 리포트 이름을 소비하는 재개 절차를 함께 점검한다. 새 설치의 기본 구성과 기존 설치의 전환을 구분한다. 진행 중인 phase의 팀 명단·기존 리포트를 소급 변경하지 않는다. 사용자 수정과 엔진별 OFF를 보존하고, 전환이 필요한 항목은 기존 설치 승인·충돌 처리 절차에 올린다.

- 새 설치에서 초안 13개의 양식 링크와 docs-management가 `docs/harness/templates/product-docs/`의 양식 12개를 가리키는지 확인한다. 기존 프로젝트에서는 setup 재실행 뒤에도 기존 양식 링크가 열리고 사용자 편집과 지정 작성자가 보존되는지 확인한다.
- 새 요구사항, 지정 백로그 ID, 자동 묶음 선정 각각에서 첫 호출자·검토자·사용자 승인 횟수·최종 실행 조건을 확인한다. 모든 실행 Task에서 해당 백로그 항목까지 추적할 수 있어야 한다.
- 동일한 PM 또는 Planner의 작업별 모델 표가 계획에 반영되고, 승인된 DAG와 실제 기동 배정이 일치하는지 확인한다. 승인 후 모델 표를 바꿔도 미등록·미기동 Task는 승인 당시 값으로 실행되고 다음 계획은 새 값을 읽어야 한다. 현재 Run도 바꾸도록 요청한 경우에는 해당 배정과 DAG 재승인 뒤 새 값으로 기동하는지 확인한다.
- 새 설치에서 PM의 네 작업이 위 표의 Opus와 작업별 effort를 사용하는지 확인한다. Planner effort를 max로 선택하면 기술 설계와 실행 계획은 각각 Fable/max, 요구사항 검토는 Opus/high여야 한다.
- 승인된 Task의 팀 내부 분해에서 팀장이 Planner를 직접 호출하고 분해안을 받아 팀원에게 배정하는지 확인한다. 분해안에 승인 범위 변경이나 다른 팀 배정이 필요하면 팀장이 배정 전에 코디네이터에게 올리는지 확인한다.
- 실행 팀의 팀장이 ON이면 단순한 Task 1개는 직접 배정할 수 있고, 단순한 Task 2개 또는 전문 분해가 필요한 Task 1개는 팀장을 거치는지 확인한다. 팀장이 OFF인 팀은 단순한 Task 1개여도 배정 대기여야 한다.
- agent-author로 역할 하나 및 팀 전체를 추가하고 창구 배정, 직접 협업, 문서 책임과 모델 배정이 작성 지침과 구조도에 같이 반영되는지 확인한다.
- 구조도에서 공통 기준 문서를 눌러 13종의 경로와 작성자를 대조한다. 색인에 정본이 지정된 문서와 설치 초안만 있는 문서에서 각각 경로를 눌러 해당 파일의 본문이 열리는지 확인한다. 절별로 작성자가 다른 문서에서는 각 태그의 색상이 해당 팀과 일치하고 누르면 그 절을 맡은 에이전트의 상세 팝업이 열리는지 확인한다. 미배정과 해당 없음도 확인한다.
- 문서 소유권 탭에서 같은 문서·범위의 정본 작성자와 주요 검토자가 각자 지정된 열에 나타나는지 대조한다. 주요 검토자가 여럿인 행에서 작성자와 각 검토자의 팀 색상 및 태그를 눌러 열리는 역할을 확인한다.
- 직접 협업 탭에서 서로 다른 팀이 협의하는 행을 골라 목적을 확인한다. 양쪽 태그의 팀 색상과 클릭 시 열리는 역할 상세가 문서 소유권 탭에서 같은 역할을 눌렀을 때와 일치해야 한다.
- 모델 선택 표를 열어 현재 값을 조회하고 작업 단위 하나의 설정을 바꾼다. `저장` 직후 프로젝트 모델 표의 해당 행과 화면을 다시 열었을 때의 선택값이 모두 저장한 값과 일치해야 한다. 역할 팝업에서는 작성 문서와 작업 산출물을 구별할 수 있고, 다른 팀의 협업 태그를 누르면 그 팀 색상의 태그가 가리킨 역할 상세가 열려야 한다.
- 같은 전문 역할을 setup의 팀 생성 경로와 설치 후 agent-author의 단일 역할 추가 경로에서 각각 작성한다. 두 결과 모두 프로젝트의 통합 양식을 따르는지 확인하고, 동일한 대표 업무를 주었을 때 각 정의에서 판단 근거·검증 증거·인계 상대를 찾을 수 있는지 따로 검토한다.
- 팀장 OFF/ON, 팀원 OFF/ON, 팀장 없는 운영팀, 코디네이터 직속 역할을 각각 확인한다. 활성 상태 변화로 원소속이나 문서 책임이 바뀌면 실패다.
- 새 설치에 team-product 스킬 파일이 없어도 명단을 읽은 구조도에 PM과 Planner가 팀장 없는 운영팀의 동료로 나타나야 한다. 창구의 단독 PRD 요청과 실행 뒤 PM의 백로그 완료 처리가 각각 담당 스킬로 이어지는지 확인한다.
- 미배정 API 계약이 있는 프로젝트에 관련 없는 역할과 API 전문가를 각각 추가한다. 후자에게만 작성 담당을 추천하고 수락하면 이후 재추천에서 빠지는지, 거절하면 미배정으로 남는지 확인한다.
- 라이브 문서가 바뀌는 사례에서 발견자의 리포트, 지정 작성자, 해당 문서의 절·ID와 근거까지 따라가 본다. 인계만 끝난 항목은 반영 대기로 두고, 이력 전용 Task는 팀 리포트로 정상 종료되는지 확인한다.
- 필수 문서 수정이 남으면 사용자 답변 전에는 phase가 열린 상태인지 확인한다. 사용자가 명시적으로 이월한 경우에는 해당 백로그 항목에 남은 문서·담당·사유가 기록되고 미완료로 남는지, 나머지 완료 항목을 정산하고 회고 뒤 phase를 마감하는지 확인한다.
- 전체 phase가 QA, 제품 문서 확인, 필수 하네스 회고를 거치는지와 검토된 버전에서만 실행 승인이 가능한지 확인한다.

위에서 이름을 정한 열은 그 표기를 사용한다. 그 밖의 표 열 표기, 브라우저 파서 내부 구조, 기존 양식 링크의 호환 방법, 테스트 구현은 빌더에게 맡긴다. 제품 코드·사용자 전역 스킬 변경과 배포는 설계 승인 뒤의 구현 작업으로 남긴다.
