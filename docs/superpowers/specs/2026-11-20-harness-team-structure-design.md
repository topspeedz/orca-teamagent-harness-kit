# Orca 하네스의 역할 구성과 실시간 팀 구조도

2026-11-20 · 설계 검토본 · 대상은 플러그인의 설치 템플릿, setup, agent-author와 사용자가 지정한 agent-toggle 스킬이다.

## 목적과 선택한 접근

한 프로젝트에서 창구가 일을 맡기는 경로, 워커가 읽는 작업 지침, 사용자가 보는 팀 구조도가 같은 관계를 나타내게 한다. 새 프로젝트에서 역할이 부족하면 setup이 필요한 역할을 추천하고, 나중에 agent-author로 추가한 역할도 같은 방식으로 일한다. 제품 문서의 첫 내용은 해당 분야를 담당한 사람이 작성한다.

| 검토한 접근 | 장점과 비용 | 결정 |
| --- | --- | --- |
| A. 팀 명단, 역할 정의, 모델 표를 연결 | 기존 파일을 읽는 워커와 구조도가 같은 근거를 사용한다. Markdown 작성 양식과 읽는 쪽이 함께 바뀌어야 한다. | 사용자 선택 |
| B. 단일 조직 명세에서 나머지 파일을 생성 | 한 파일에서 전체 관계를 편집하고 검사하기 쉽다. 기존 프로젝트의 이관과 생성된 파일의 수정 정책이 필요하다. | 대안으로 검토 |

## 역할과 실제 기동 경로

| 역할 | 배정·보고 | 책임 |
| --- | --- | --- |
| 사용자 창구 | 사용자와 대화하고 승인 전 운영 역할을 Orca로 기동 | plan-orchestrate로 접수·분기하고 그림과 승인 질문을 전달한다. |
| product-manager | 팀장 없는 운영팀. 승인 전에는 창구에 보고 | prd-write, srs-write, backlog-management로 제품 요구, 수락 기준, 백로그와 묶음을 작성한다. Planner의 계획을 제품 범위와 대조한다. |
| planner | PM과 동료. 창구가 직접 기동 | superpowers의 설계·계획 절차와 phase-planning으로 기술 선택, Task 분해, 파일 쓰기 범위, 의존성, 병렬 배정, 검증 순서와 예상 그림 입력을 작성한다. 새 제품 결정은 PM과 창구에 돌려보낸다. |
| coordinator | 실행 승인 뒤 창구가 기동 | 승인된 계획으로 팀장에게 배정하고 보고·질문·수정 루프를 관리한다. 완료 처리에 필요한 운영 역할과 독립 역할을 직접 호출한다. |
| 실행 팀 | 코디네이터 ↔ 팀장 ↔ 팀원 | 팀장은 팀 내부 Task를 배정하고 통합 보고한다. QA 팀은 qa-inspector와 code-reviewer의 기존 책임을 유지한다. |
| doc-steward | 코디네이터 직속, 무소속, 필수 | 개발·QA가 끝나면 docs-management로 코드·테스트·문서 정합성을 확인한다. 색인과 연결을 정리하고, 내용 결함은 원작성자에게 돌려보낸다. |
| harness-engineer | 코디네이터 직속, 무소속, 필수 | 문서 확인 뒤 매 phase harness-retro를 수행한다. 장부에서 지연·재작업·인계 누락을 확인하고 근거가 있을 때 하네스를 개선한다. 변경할 근거가 없어도 회고 결과를 남긴다. |

운영팀에는 팀장 워커를 만들지 않는다. PM에서 Planner로 넘긴다는 것은 브리프와 산출물을 통한 업무 인계다. 창구가 단계별 담당자를 기동하므로 PM이나 Planner를 서로의 상급자로 표시하지 않는다. 실행 이후에도 지정된 협업 상대끼리 팀을 넘어 사실 확인과 기술 협의를 할 수 있다. 새 Task 배정이나 범위 변경은 팀장·코디네이터에게 올리고 제품 범위 결정은 창구로 전달한다.

실행 spec에는 해당 Task의 협의 상대와 수신 경로를 싣는다. 상대가 기동되어 있으면 현행 Orca 메시지 경로로 질의·회신하고, 꺼져 있거나 호출할 수 없으면 배정자에게 돌려보낸다. 협의 결과로 정본이나 계획이 바뀌면 원작성자가 근거를 남긴다. 기존 사용자 승인·대기 규약은 유지한다.

실행 승인 뒤에 팀장이 이미 배정받은 Task의 복잡한 내부 분해를 Planner에게 맡기는 현행 경로는 유지하는 안이다. 이 호출은 팀장의 임시 작업 배정으로 상세 관계에 표시하며 Planner의 운영팀 소속을 바꾸지 않는다. 분해 결과가 승인 범위나 다른 팀 배정을 바꾸면 코디네이터에게 올린다.

## 세 가지 접수 경로

| 요청 | 먼저 하는 일 | 계획·승인 |
| --- | --- | --- |
| 새 요구사항 여러 개 | PM이 원문과 PRD·SRS·백로그 ID를 대조해 항목화한다. Planner가 누락과 계획 가능성을 검토한다. | 사용자가 전체 요청의 반영 여부와 이번 묶음을 확인한 뒤 Planner가 설계·계획한다. |
| 사용자가 백로그 ID 지정 | 창구가 지정한 묶음을 Planner에게 바로 전달한다. | PM의 항목화·묶음 선정 절차를 반복하지 않는다. 없는 ID, 완료된 항목, 범위를 넓혀야 하는 선행 조건은 구체적으로 올린다. |
| 기존 백로그에서 한 phase를 위임 | PM이 진행 가능한 항목의 우선순위·선행 조건·연관성을 바탕으로 한 가지 목표와 묶음을 고르고, 선택 이유를 적는다. | 묶음 승인을 따로 묻지 않고 Planner에게 넘긴다. 실행 승인 화면에서 사용자가 목표·선정 이유·항목을 함께 확인하고 바꿀 수 있다. |

제품 백로그의 단위는 사용자가 확인할 수 있는 결과와 수락 기준이다. 실행 Task에는 해당 백로그 ID와 실제 선후행 관계, 런타임·모델·effort, 쓰기 범위와 검증 방법을 기록한다. 하나의 항목을 여러 워커가 맡거나 여러 항목이 하나의 선행 계약을 공유할 수 있다.

plan-orchestrate에서 사용자가 ID를 명시한 경우에는 기존 ‘해법이 정해진 작업’ 단축 규칙보다 지정 ID 경로를 먼저 적용한다. 작은 항목도 Planner가 첫 담당자다. 이 분기 변경을 plan-orchestrate 밖의 일반적인 단일 파일 수정에 확대하지 않는다.

창구는 dag-swimlane과 waterfall-timeline으로 설계의 팀 단위 흐름과 계획의 Task 단위 흐름을 보여 준다. 시작 전 DAG는 대기 상태, 워터폴은 T+ 예상 모드다. 새 요구·명시 ID 경로는 현행 설계·계획 승인 절차를 따른다. 묶음 선정을 위임한 경로는 중간 승인을 따로 요구하지 않고 최종 예상 그림으로 실행을 승인받는다. 사용자가 범위를 바꾸면 영향을 받는 계획과 그림, 리뷰를 갱신한다. 승인 뒤에는 코디네이터가 같은 Run의 장부로 진행 상태를 갱신한다.

## 기본 스킬과 모델 배정

별도 prd-writer와 pm-reviewer 에이전트는 새 설치 기본 명단에서 뺀다. PM과 Planner는 공용 리뷰 스킬을 사용한다. 작성자 자가 점검은 상대 역할의 검토와 구분한다. PM이 요구사항을 새로 썼다면 Planner가 원문 누락과 실행 가능성을 본다. Planner가 계획을 쓰면 PM이 승인 범위와 수락 기준을 대조한다. 검토 기록은 검토한 문서 버전·백로그 ID·결과·열린 쟁점을 남긴다. 동일 버전의 검토를 반복하지 않는다.

setup의 초기 질문과 기존 QA, coordinator, dag-swimlane, waterfall-timeline, plan-orchestrate, phase-planning, harness-retro는 유지한다. 문서 관리 역할과 스킬의 설치 이름은 기존 doc-steward와 docs-management를 기준으로 한다. setup이 제공하는 모델 표에 PM의 요구사항 작성·항목화·계획 대조·완료 처리, Planner의 요구사항 검토·설계·계획을 구분해 둔다. Planner의 설계·계획에 Opus 또는 Fable과 high 또는 max를 작업별로 선택할 수 있게 한다. 최초 기본값은 현행 Planner의 Opus와 setup에서 선택한 effort를 사용하고, 사용자 변경은 기존 모델 표 설문에서 받는 안이다. PM의 신규 작업 행은 기존 동일 업무 행의 설정을 이전하는 안이다. 에이전트 이름을 바꿔 모델을 고르거나, 기존 프로젝트에서 사용자가 정한 값을 자동 교체하지 않는다.

## setup의 문서·담당자 설계

1. 설치 시 코드 지도와 12개 번호 폴더의 초안 13개를 준비한다. 경로 기준은 [현재 설치 경로표](../../../skills/setup/references/document-drafts.json)다. API·DB 계약, ADR, 런북은 이름이 정해지기 전까지 각 폴더의 draft.md를 쓴다. 실제 기록이 있는 기존 파일과 색인에 지정된 다른 경로의 정본은 보존한다.
2. 각 초안에서 해당 문서의 작성 양식을 docs/ 안에서 열 수 있게 한다. **설계 제안**은 배포용 양식의 정본을 docs/harness/templates/ 아래 제품 문서 양식 폴더에 두고 setup과 docs-management가 함께 참조하는 것이다. 기존 references/forms 경로를 사용하는 프로젝트는 연결을 유지한다. 설치 초안, 작성법, 실제 제품 사실은 구분한다.
3. setup은 문서별로 현재 역할의 지침과 편집 범위를 읽어 첫 작성자 후보와 근거를 보여 준다. PRD·SRS는 PM, 나머지는 프로젝트의 분야별 담당자를 찾는다. 한 경로를 여러 역할이 쓰면 담당 절과 책임을 구체적으로 나눈다. 색인은 doc-steward가 관리한다.
4. 담당자가 없으면 역할과 맡길 문서, 필요한 근거를 함께 제안한다. 사용자는 역할 생성, 나중에 배정, 해당 영역이 필요 없음 중 선택할 수 있다. 뒤의 두 선택은 각각 미배정과 해당 없음으로 남긴다. 이 선택을 이유로 기존 문서나 이미 만든 초안을 삭제하지 않는다. 권고를 거절하면 doc-steward에게 제품 내용의 첫 작성을 넘기지 않는다.
5. 개발 중 미배정 문서에 실제 작성이 필요해지면 코디네이터가 기존 역할 후보 또는 새 역할을 제안한다. 원작성자는 구현 근거를 남기고 doc-steward는 종료 시 근거와 연결을 확인한다. 리뷰는 실제 변경을 담당 범위와 대조한다. 파일 저장을 가로막는 편집 훅은 이 설계 범위 밖이다.

## agent-author와 agent-toggle이 함께 읽는 기준

| 정본 | 기록할 사실 | 사용하는 곳 |
| --- | --- | --- |
| docs/harness/team-org.md | 운영팀·실행 팀·독립 역할의 구분, 팀장과 명시적 팀원, 팀 스킬 | 창구, 배정, 구조도. 팀장 칸이 원래 빈 운영팀과 팀장을 꺼둔 실행 팀을 구분한다. |
| .claude/agents/역할.md | 핵심 역할과 장착 스킬, 직접 협의할 상대·목적, 배정·변경 요청 경로, 문서 경로·담당 절·첫 작성/수정/확인 책임 | 워커 작업 지침, 교차 리뷰, 구조도의 역할 상세·협업선·문서 탭 |
| docs/harness/model-selection.md | 역할·작업 단위별 런타임·모델·effort | 실제 Orca 기동과 구조도 모델 표시 |
| 기존 토글 상태와 설치 기록 | 엔진별 활성 여부, 키트에서 복사한 파일 | 실시간 표시와 복원. 역할 파일을 꺼도 팀 소속과 작성 담당이 유지된다. |

예를 들어 API 담당자에게는 UI 담당자와의 요청·응답 형식 협의, API 계약의 첫 작성, 작업 범위를 넓힐 때의 팀장 보고를 명시한다. UI 담당자를 추가하면 같은 협업 관계를 양쪽 역할 카드에서 따라갈 수 있어야 한다. 읽는 참고 문서와 자신이 작성할 문서를 구분한다. 새 에이전트의 전문성은 [agent-author 조사 기준](../../../skills/agent-author/references/agent-corpus-research.md)의 지정 저장소와 기존 프로젝트 근거로 작성한다. 전문성을 요하는 역할은 관련 원문을 비교하고, 채택한 판단 기준·검증 방법·출처를 남긴다.

setup과 agent-author는 같은 역할 양식을 써서 독립 역할, 기존 팀원, 팀장과 팀원으로 구성된 팀 전체를 만들 수 있어야 한다. 승인된 역할·팀만 등록하고 기존 명단·모델 행과 중복을 피한다. Codex를 함께 쓰는 프로젝트는 기존 동기화 방식으로 역할 TOML과 스킬 포인터를 맞춘다.

## 구조도 동작

Unity 예시의 팀 색상, 역할 카드, 팀 구조도·직접 협업·문서 소유권 세 보기를 재사용한다. 실선은 배정·보고, 점선은 직접 협의다. 팀장 없는 운영팀에 가상의 팀장을 그리지 않는다. 창구의 기획 단계와 실행 승인 뒤의 코디네이터 배정을 구분하고, doc-steward와 harness-engineer는 각각 독립 역할로 표시한다.

**팀장 OFF는 시안 A로 확정했다.** 팀장 카드에 OFF, 원래 팀에 ‘팀 배정 대기’를 표시하고 팀장을 지나는 배정·보고선을 비활성화한다. 켜진 팀원은 같은 팀에 남는다. 양 끝이 켜진 직접 협업선과 문서 담당은 유지한다. ON으로 되돌리면 배정선이 복구된다. 별도 영역에 활성 팀원을 옮기는 시안 B도 비교했다. 사용자는 소속과 대기 사유를 같은 팀에서 보는 A를 선택했다.

현재 agent-toggle의 실시간 갱신 주기, Claude/Codex별 정의 토글, 키트 설치와 수정 파일 보호를 유지한다. 구조도의 기본 관점은 현행 활성 Claude 역할 기준이고 Codex 정의는 해당 엔진 원문에서 확인한다. 개인별 스킬을 전역에서 쓰는 사용자에게는 설치 원본과 수정 대상 위치를 구분해 안내한다.

플러그인이 소유하는 변경은 템플릿과 역할 생성 절차다. 구조도 파서·화면은 사용자가 지정한 별도 스킬 `~/.claude/skills/agent-toggle/`의 변경 대상이다. 프로젝트 setup만으로 전역 스킬을 덮어쓰지 않는다. 실제 배포에서도 두 구성 요소가 같은 명단·역할 양식을 읽는지 각각 확인한다.

## 기존 설치와 검증 기준

기존 팀·역할 지침에 새 표가 없으면 읽을 수 있는 기존 정보만 표시한다. 빠진 협업선이나 문서 소유권을 역할 이름으로 추정하지 않는다. 이전 버전의 prd-writer·pm-reviewer·1인 harness 팀, 모델 행, 스킬 포인터, 리포트 이름을 소비하는 재개 절차를 함께 점검한다. 새 설치의 기본 구성과 기존 설치의 전환을 구분한다. 진행 중인 phase의 팀 명단·기존 리포트를 소급 변경하지 않는다. 사용자 수정과 엔진별 OFF를 보존하고, 전환이 필요한 항목은 기존 설치 승인·충돌 처리 절차에 올린다.

- 빈 프로젝트 setup과 재실행에서 13개 초안, 작성 양식 링크, 사용자 편집 보존, 선택한 문서 담당의 일치를 확인한다.
- 새 요구사항, 지정 백로그 ID, 자동 묶음 선정 각각에서 첫 호출자·검토자·사용자 승인 횟수·최종 실행 조건을 확인한다. 모든 실행 Task에서 해당 백로그 항목까지 추적할 수 있어야 한다.
- 동일한 PM 또는 Planner가 서로 다른 작업 단위로 기동될 때 모델 표의 해당 행을 사용하고, 예상 DAG와 실제 기동이 같은 배정을 가리키는지 확인한다.
- agent-author로 역할 하나 및 팀 전체를 추가하고 창구 배정, 직접 협업, 문서 책임과 모델 배정이 작성 지침과 구조도에 같이 반영되는지 확인한다.
- 팀장 OFF/ON, 팀원 OFF/ON, 팀장 없는 운영팀, 코디네이터 직속 역할을 각각 확인한다. 활성 상태 변화로 원소속이나 문서 책임이 바뀌면 실패다.
- 전체 phase가 QA, 제품 문서 확인, 필수 하네스 회고를 거치는지와 검토된 버전에서만 실행 승인이 가능한지 확인한다.

표 열의 정확한 표기, 브라우저 파서 내부 구조, 기존 양식 링크의 호환 방법, 테스트 구현은 빌더에게 맡긴다. 제품 코드·사용자 전역 스킬 변경과 배포는 설계 승인 뒤의 구현 작업으로 남긴다.
