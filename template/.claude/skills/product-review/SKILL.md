# product-review

`요구사항 검토`와 `계획 대조`는 PM이 기획 세션 안에서 자기 단계로 한다(`plan-orchestrate`의 기획 세션). 다른 역할이 검토하는 단계는 없고, 사용자 승인이 그 자리의 확인이다. 그래서 앞 단계에서 쓴 리포트의 `## 검증` 줄을 근거로 삼지 않고, 요청 원문과 정본 문서를 다시 열어 점검표대로 대조한다. 기존 46-product-manager의 요구사항 추적·정합성 대조 방법(revfactory/harness-100, Apache-2.0)을 역할에 맞춰 적용한다.

대상 문서·버전(파일명에 버전이 없으면 내용 해시 또는 커밋), BL ID, 결과·열린 쟁점을 함께 기록한다. 단독 PRD에서 BL·SRS가 범위 밖이면 해당 없음과 사유를 적고 원문↔US를 본다. 같은 버전·범위의 검토 결과가 있으면 재사용한다. 변경 시 영향받은 ID만 새 버전에서 재검하고, 열린 High는 PM이 고친 뒤 그 결함 ID를 다시 본다.

## 요구사항 검토

입력: 브리프, PM의 요청 대조·항목화 리포트, PRD, SRS, 백로그, 관련 결정 기록(`docs/07-decisions/`, 위치는 색인에 있다). 4번은 [분해 기준](../backlog-management/references/decomposition.md)의 "나누는 기준 다섯"과 "복잡도" 절을 기준으로 본다.

| 번호 | 볼 것 |
| --- | --- |
| 1 | 요청 원문과 브리프의 요구가 요청 대조 표에 모두 있고, 각 줄이 가리키는 `US`와 `FR`/`NFR`이 실제로 문서에 있다 |
| 2 | `(계획됨` 표시가 붙은 요구사항마다 다루는 백로그 항목이 있고, 항목마다 요구사항 ID가 있다 |
| 3 | 수락 기준이 대상, 조건, 기대 결과가 든 검사할 수 있는 문장이고, 오류 흐름 기준이 있다 |
| 4 | 항목이 분해 기준과 복잡도 규칙을 지킨다(13이 남아 있지 않거나 사유가 있다, 불확실성 8 이상에 조사 항목이 있다) |
| 5 | 수치와 우선순위에 출처(브리프의 사용자 결정)가 있다. 출처 없는 수치가 없고, RICE 추천값이 백로그에 적혀 있지 않다 |
| 6 | 이미 있는 요구사항, 결정 기록과 부딪치지 않는다 |
| 7 | 묶음 제안이 우선순위와 의존에 맞고, 목표 한 문장이 있다 |

1번은 요청 원문을 직접 읽고 요구를 다시 끊어 대조한다. 요청 대조 표와 앞 리포트의 `## 검증` 줄만 믿지 않는다.

앞 단계 리포트가 이미 `## 사용자 결정 필요`에 올린 것은 다시 적지 않고 그 리포트와 번호로 가리킨다. 그 결정이 빠져 결함이 되는 경우만 결함 표에 적는다.

## 계획 대조

입력: 브리프(새 요구에서 확인한 묶음, 사용자가 지정한 BL 또는 위임으로 선정한 묶음), 계획서, 백로그.

| 번호 | 볼 것 |
| --- | --- |
| 1 | 묶음의 모든 항목이 계획서의 `### 항목과 Task` 표에 Task와 함께 있다 |
| 2 | 항목마다 그 Task들이 수락 기준의 정상 흐름과 오류 흐름을 모두 만든다 |
| 3 | 계획된 모든 실행 Task의 `백로그:` 줄에 묶음 안의 실제 BL ID가 하나 이상 있다. 공통 선행 작업·리뷰·QA도 관련 BL에 연결한다. 누락, `없음`, 묶음 밖 ID는 결함이다 |
| 4 | 항목 사이의 선후가 DAG의 의존과 어긋나지 않는다 |
| 5 | 불확실성이 큰 항목에 조사 Task나 `## 리스크`의 줄이 있다 |
| 6 | 끝 검증 Task가 묶음의 항목을 모두 덮는다 |
| 7 | 실행 Task의 점수·근거가 자신의 책임과 완료 검사에 맞고 DAG의 런타임·추천·직접 지정이 계획과 일치한다. 표의 고정 역할과 사용자가 직접 지정한 조합의 고정 여부를 확인한다 |

병렬 효율(의존의 사유, 편집 범위 겹침, 사슬 길이)은 여기서 보지 않는다. 그것은 `phase-planning`의 승인 전 점검이다.

## 심각도

| 값 | 뜻 |
| --- | --- |
| `High` | 승인 전에 고쳐야 한다: 빠진 요구, 항목 없는 요구사항, 검사할 수 없는 수락 기준, 출처 없는 수치, 기존 결정과의 모순, Task 없는 항목, BL 누락·묶음 밖 ID가 있는 실행 Task |
| `Medium` | 고치면 좋지만 승인을 막지 않는다 |
| `Low` | 참고 |

결함 ID는 요구사항 검토가 `PR-<번호>`, 계획 대조가 `PC-<번호>`다.

## 다시 볼 때

spec에 결함 ID가 적혀 있으면 그 결함이 고쳐졌는지만 본다. 새로 넓게 찾지 않는다. 고치면서 새로 생긴 `High`가 보이면 적는다.

## 리포트 절

spec이 지정한 경로에 요구사항 검토 또는 계획 대조 리포트를 쓴다.

```markdown
## 한 일

## 검토 기록

| 대상 문서·버전 | BL ID | 결과 | 열린 쟁점 |
| --- | --- | --- | --- |

## 대조

| 요구 / 항목 | 요구사항 / Task | 결과 |
| --- | --- | --- |

## 결함

| ID | 심각도 | 위치 | 내용 | 고칠 쪽 (`product-manager` 또는 `사용자 결정 뒤 product-manager`) |
| --- | --- | --- | --- | --- |

## 사용자 결정 필요

## 검증
```

- 찾은 결함은 `## 결함`에만 적는다. `## 검증`에는 점검표의 줄마다 돌렸는지를 ✅나 ❌로 적는다. 돌리지 못한 줄만 ❌다.
