# change-review

리뷰는 변경을 읽고 "완료 기준을 채우는가, 더 작을 수 없는가, 규칙을 어기지 않는가"에 답하는 일이다. 읽어서 찾는다. 실행해서 찾는 것은 `qa-verification`의 몫이다.

**코드, 테스트, spec, 문서를 고치지 않는다. 리포트 파일 하나만 쓴다.** 결함을 찾는 것은 검증자의 실패가 아니다. 구현한 쪽이 자기 결과를 승인하지 않는다.

## 언제 돌리는가

- 중간에는 코드 리뷰만 돌린다. 뒤 Task가 그 위에 쌓이는 묶음이 끝났을 때 돌려, 다음 Task가 결함 위에 쌓이지 않게 한다.
- 같은 파일을 고치는 Task가 진행 중이면 그 파일의 리뷰는 편집이 끝난 뒤 한 번만 한다.
- 보안이나 돈이 걸린 변경은 모델 표(`docs/harness/model-selection.md`)의 별도 작업 단위 `보안·돈이 걸린 변경 리뷰`로 배정받는다.

## 절차

1. **범위.** spec, 구현 리포트, 변경 파일 목록을 읽는다. 목록이 없으면 `git status --short`와 `git diff`로 잡는다. 결함 수정을 리뷰하면 원래 결함 ID와 재현 절차를 먼저 읽는다.
2. **완료 기준 대조.** 수락 기준의 정본(백로그 항목)과 spec의 `완료 기준`을 연다. 기준 하나하나에 변경의 어느 부분(파일:줄)이 답하는지 표로 만든다. 답이 없는 기준이 첫 결함이다.
3. **네 렌즈로 읽기.** 아래 표. 파일마다 변경 → 호출부 → 형제 함수 → 기존 테스트 순으로 본다.
4. **주장 확인.** 구현 리포트가 ✅라 한 검사만 다시 돌린다. 결과가 다르면 High다. `## 검증` 절이 없거나 검증 줄이 없거나 "미실행"이면 그 자체가 High다. 확인할 주장이 없다고 승인하지 않는다. 끝 리뷰(구현 Task가 모두 끝난 뒤의 리뷰)면 그 전에, 합쳐진 코드에서 브라우저와 혼자 써야 하는 자원 없이 도는 검사(문법, 타입, 린트, 단위 테스트)를 프로젝트 명령으로 한 번 돌린다. Task마다 자기 범위만 검사했으므로 Task끼리 부딪힌 것은 여기서 처음 드러난다. 실패는 High다.
5. **리포트.** 아래 형식으로 쓴다. 판정은 High 개수로만 정한다.

## 네 렌즈

| 렌즈 | 본다 |
| --- | --- |
| 정확성 | 완료 기준 충족, 원인 수정, 경계 케이스. 공용 함수가 아니라 호출부 하나에 가드를 넣은 수정이면 형제 호출부를 찾아본다 |
| 단순성 | 요청 밖 코드, 한 번만 쓰는 추상화, 중복, 죽은 코드, 이미 있는 헬퍼의 재구현, 요청하지 않은 옵션과 설정 |
| 규칙 | `AGENTS.md`와 프로젝트 규칙 문서의 기술 결정. 새 의존성, 정해진 경로를 우회한 호출 |
| 보안(정적) | 신뢰 경계의 입력 검증, 비밀 값이 클라이언트·로그·오류 메시지로 흐르는지, 출력 정화, 인증과 권한 경로 |

## 테스트 먼저 확인

구현 Task는 완료 기준을 재현하는 테스트를 먼저 쓰고 실패를 확인한 뒤 구현한다. 결함 수정은 ID마다 재현 테스트, 원인 수정, 통과 순서다. 리뷰는 이것을 본다.

- 검증 줄이 없거나 테스트가 의미 없으면 High다. 의미 없는 테스트: 구현을 그대로 베낀 테스트, 입력을 바꿔도 실패하지 않는 테스트, 아무것도 단언하지 않는 테스트.
- 결함 수정에 그 ID의 재현 테스트가 없으면 High다.

## 심각도와 판정

| 심각도 | 기준 |
| --- | --- |
| High | 완료 기준 미달, 규칙 위반, 증상만 덮은 수정, 보안 경로, 테스트 실패나 의미 없는 테스트, 검증 줄이 없음 |
| Medium | 동작은 맞지만 다음 변경을 비싸게 만든다 |
| Low | 취향과 정리. "선택"이라 표시한다 |

- **승인** = High 0. **수정 요청** = High 1 이상. 반려 등급은 두지 않는다.
- Medium 이하는 판정에 영향이 없다. 리포트에 적고, 코디네이터가 백로그 인박스로 보낸다.
- 취향으로 수정 요청 판정을 만들지 않는다.

## 리포트 형식

경로는 spec의 `보고:` 줄을 따른다. 형식은 양식 `docs/harness/templates/report.md`를 따르고, `## 한 일`과 `## 검증` 사이에 아래 절을 넣는다.

```markdown
# <Task ID> <이름> 리포트

판정: 승인 | 수정 요청 — High n · Medium n · Low n
범위: 변경 파일 n · 기준 <base>

## 한 일

## 완료 기준 대조
| 기준 | 변경의 근거(파일:줄) | 판정 |

## 결함
### R-1 [High] <한 줄>
- 파일:줄
- 왜: (렌즈, 규칙이나 spec 근거)
- 대안: (가장 작은 수정. 코드 3줄 이내)

## 원인 수정 확인 (결함 수정 리뷰일 때)
| 원래 ID | 고친 위치 | 형제 호출부 | 재현 테스트 | 판정 |

## 직접 소통

## 검증
- ✅ 변경 파일 전부 읽음
- ✅ `<구현 리포트가 ✅라 한 검사 명령>` → <결과>
- (참고) <범위 밖이거나 spec이 막아서 하지 않은 것>

## QA에 넘길 관찰
실행해야 확인되는 것. ID 없음.

## 판단 필요
규칙과 spec의 충돌, 범위 해석. 코디네이터를 거쳐 사용자에게.

## 남은 것
```

- 결함 표의 High는 발견이고 `## 검증`의 ❌는 검증 실패다. 찾은 결함을 `## 검증`에 ❌로 쓰지 않는다.
- `## 검증` 줄은 내가 할 일을 했는지만 적는다. 돌리지 못한 것도 ❌다. 완료 기준 밖의 줄은 `(참고)`로 시작한다. 그렇지 않으면 `report-check`가 실패한다.
- 결함 번호는 같은 범위의 이전 리뷰에서 이어 쓴다. 리뷰어가 여럿이면 팀장이 번호를 나눠 준다.

## 하지 않는 것

- 코드, 테스트, spec, 문서 편집. 발견은 적고 수정은 그 영역의 팀이 한다.
- 서버나 브라우저 실행, 흐름 검증, 성능 측정(`qa-verification`).
- 점수표, 복잡도 지표 표. 결함이 아니라 지면만 늘린다.
