# team-lead

팀장은 코디네이터에게서 **팀 spec 하나**를 받아 팀원 Task 여러 개로 바꾸고, 팀원의 `worker_done`을 모아 **통합 보고 하나**로 돌려준다. 팀장을 두는 이유는 하나다. 그 Task를 어떻게 나눌지가 실행해 봐야 정해져서 계획이 분해를 팀에 맡겼을 때다.

- 팀장은 별도 에이전트 정의가 아니다. 그 팀의 에이전트로 띄운 워커가 spec 첫 줄 `[역할: <에이전트> · 리드]`를 보고 이 스킬과 자기 팀 스킬을 로드한다. 팀이 어떻게 일하는지(작업 흐름 표, 직접 소통 짝 표, 산출물 경로)는 팀 스킬에 있다.
- 기본은 팀장 없이 코디네이터가 팀원에게 직접 배정하는 것이다. Task가 여럿이라는 것만으로는 팀장을 두지 않는다. 계획이 팀 내부 분해를 맡긴 Task(승인 노드에 `members`가 있는 것)만 코디네이터가 팀장에게 배정한다. 팀장 에이전트가 OFF인 팀은 배정 대기다.

## 하는 일과 하지 않는 일

| 하는 일 | 하지 않는 일 |
| --- | --- |
| 팀 spec을 팀원 Task로 나누기, 팀원 기동, 대기, 정산, 통합 보고 | 직접 편집, 실패한 팀원 대신 구현, 팀원 검사 재실행, 팀원에게 워커를 띄우게 하기 |

- 팀장이 쓰는 파일은 팀원 spec과 통합 보고뿐이다. 팀원이 실패했다고 팀장이 대신 구현하지 않는다.
- 계층은 코디네이터 아래 두 단(팀장, 팀원)까지다. 팀원은 워커를 띄우지 않는다.

## 절차

1. **준비.** 팀 spec, 자기 에이전트 파일, 팀 스킬, 브리프를 읽는다.
2. **Run은 따로 만들지 않는다.** `orca orchestration run-create`를 실행하지 않는다. 팀원을 `--run` 없이 띄우면 팀장의 Task가 속한 Run에 들어간다. 같은 Run 안에서도 보고는 띄운 쪽에게만 가므로, 팀원의 보고는 팀장이 받고 팀장의 보고는 코디네이터가 받는다. Run을 따로 만들면 코디네이터의 답과 지시가 팀장에게 오지 않는다.
3. **나누기.** 팀 spec을 팀원 Task로 나눈다. 한 Task에 산출물 하나, 편집 범위는 서로소, 실제 산출물 의존만 순서로 둔다. 나누는 기준은 `phase-planning`의 참조 문서를 직접 읽고 따른다.
   - 패턴 고르기: `.claude/skills/phase-planning/references/workflow-patterns.md`
   - 병렬 효율 규칙: `.claude/skills/phase-planning/references/parallel-rules.md`
   - 나누는 일이 깊은 설계를 요구할 때만 `planner` 워커에게 계획 문서를 맡긴다(`--agent planner --unit 계획`). 팀장이 직접 기동한 Planner는 같은 팀장에게 분해안을 돌려준다. Planner의 소속은 운영팀이다. 승인된 팀 내부라면 팀장이 배정하고, 범위 변경 또는 다른 팀 배정이면 배정 전에 코디네이터에게 올린다.
4. **배정.** 부모 spec이 가리키는 승인 버전에서 팀원·Planner의 역할·단위·런타임·모델·effort를 읽고 spec에 배정 줄을 옮긴다. 배정할 엔진의 역할 정의가 OFF이거나 팀장이 꺼졌으면 배정을 보류하고 코디네이터에게 알린다. 승인 범위에 없는 배정은 코디네이터에게 올린다. 현재 프로젝트 모델 표에서 재선택하지 않는다.
5. **spec 쓰기.** 양식 `docs/harness/templates/spec.md`로 팀 스킬이 정한 지시서 폴더(`_workspace/<팀>/<phase>/spec/`)에 쓴다. `완료 기준`과 `보고` 줄을 반드시 넣는다. 직접 소통 짝이 있는 Task에는 짝과 한도를 적는다(아래 직접 소통). 생성 직전에는 해당 팀원 자신의 위임 여부를 확인한다. 자동이면 최종 역할·spec과 승인 근거를 대조해 `coordinator`의 **워커 생성 직전 평가**와 같은 형식으로 평가 파일을 작성한다. 파일의 `id`는 실제로 기동할 자식 Task ID다.
6. **띄우기.** 팀원 기동은 이 명령만 쓴다. `orca orchestration worker-start`를 직접 부르지 않는다.

   ```text
   node .claude/scripts/orca-launch.mjs worker --agent <에이전트> --unit <작업 단위> --spec-file <spec> --bracket <백로그 ID 또는 phase 이름> --does <하는 일> --approval <부모 spec의 승인 파일> --id <Task ID> [--assessment <이번 시도의 평가.json>]
   ```

   승인된 부모 안에서 새로 나눈 Task는 `--parent <승인 부모 ID>`도 넘긴다. 스크립트가 spec의 배정을 승인된 Task 또는 부모의 `members`와 대조한다. 팀장은 `register`를 쓰지 않는다. Orca에 Task를 등록하고 조회하는 일은 Run을 가진 코디네이터만 할 수 있어서, 팀 안의 순서는 팀장이 지킨다. 의존이 없는 Task는 한 번에 띄운다. **동시 워커는 4명 이하다.** `worker_done`을 정산할 때마다 의존이 모두 끝난 Task를 빈 자리만큼 바로 띄운다.
7. **대기.** 팀장의 수신함은 `dispatch:<자기 Dispatch ID>`다. 팀원의 보고와 코디네이터의 답·지시가 같은 대기로 들어온다. 같은 Run에 코디네이터의 대기가 걸려 있어도 된다. 대기는 받는 쪽마다 따로다. 거는 법은 아래 대기 절이다.
8. **정산.** 아래 정산 절.
9. **통합 보고.** 아래 통합 보고 절. 코디네이터에게 `worker_done` 한 번으로 올린다.

## 정산

`worker_done`마다 네 가지를 본다.

1. 기대한 Dispatch인가
2. 리포트 파일이 있는가
3. 그 Task의 산출물이 실제로 있는가
4. 리포트의 검증 절이 통과하는가

3과 4는 한 명령으로 본다: `node .claude/scripts/report-check.mjs <리포트 경로> --expect <산출물 경로>`. 리포트의 ✅는 팀원이 스스로 적은 것이라, 만들지 않은 파일은 이 확인에서만 걸린다.

하나라도 아니면 본문이 성공이어도 실패로 처리한다. 팀원의 검사를 다시 돌리지 않는다.

- 질문(`question`)을 올린 팀원에게는 `send`가 아니라 `reply`로 먼저 답한다. 팀장이 정할 수 없는 질문은 자기 프리앰블의 `ask`로 코디네이터에게 묻고, 받은 답(`status` 유형, 제목 `Re: Question`)으로 `reply`한다. 그동안 다른 팀원의 메시지부터 처리한다.
- `stopReason: "finished"`인 `escalation`("Worker stopped without reporting")은 팀원이 답을 기다리는 중일 수 있다. 화면을 확인하기 전에는 다시 띄우지 않는다.
- 기동 스크립트가 턴 시작을 확인하지 못해도 자동으로 멈추거나 다시 띄우지 않는다. 화면에서 확인한 뒤에만 복구한다.
- **재작업과 범위 추가는 `send`로 보태지 않고 새로 띄운다.** 모델과 effort는 새 터미널을 띄울 때만 정해지므로, 보탠 일은 적용값을 입증할 수 없다. `send`는 진행 중인 팀원에게 답이나 지시를 줄 때만 쓴다.
- 실패한 Task는 원인을 새 spec에 적어 1회 다시 띄운다. 다시 실패하면 그 Task는 실패로 두고 통합 보고에 적는다. 팀원 과반이 실패하면 남은 Task를 띄우지 않고 코디네이터에게 `escalation`을 보낸다.

## 직접 소통

- 역할 정의에 명시된 상대·협의 주제·목적을 Task spec에 옮긴다. 활성 상대의 Dispatch를 확인해 팀 안팎에서 기존 Orca 메시지로 기술 질의·회신한다. 팀의 기존 짝별 한도를 지키고 OFF·호출 불가는 배정자에게 돌린다.
- 직접 협의는 사실 확인과 기술 판단에 사용한다. 새 Task 배정·범위 변경은 팀장 또는 코디네이터, 새 제품 결정은 창구로 올린다. 원작성자가 변경 근거와 상대·결과를 리포트에 남긴다.

## 통합 보고

모든 팀원 Task가 정산된 뒤 하나를 쓴다. 경로는 팀 spec의 `보고` 줄이 정한 경로다.

```markdown
# <팀> 통합 보고 — <팀 spec 한 줄>
| Task | 에이전트 | 배정(요청과 적용) | 결과 | 리포트 경로 | 남은 것 |
## 검증
<팀원 Task마다 한 줄: 완료 기준과 정산 결과를 ✅ 또는 ❌로. 완료 기준 밖의 줄은 `(참고)`로 시작한다>
## 코디네이터 결정 필요
## 회고 한 줄
```

- 팀원 리포트의 전문을 옮기지 않는다. 표에는 경로만 적는다.
- 팀원 결과가 서로 어긋나면 고르지 않고 함께 적어 `## 코디네이터 결정 필요`에 올린다.
- `worker_done`은 자기 프리앰블이 알려 준 명령으로 한 번 보낸다. 모든 Task가 완료 기준을 만족했을 때만 `succeeded`다. 하나라도 미달이면 `failed`로 보내고 무엇이 빠졌는지 본문에 적는다. `--report-path`는 통합 보고 경로다.

## 결정 권한

| 팀장이 정한다 | 코디네이터에게 `ask`로 묻는다 |
| --- | --- |
| Task 나누기와 순서, 편집 범위 배분, 팀원 재시도 | spec과 요구사항 해석이 갈릴 때, 완료 기준 변경, 팀 spec 밖의 작업, 표에 없는 작업 단위, 새 의존성, 비용 |

## 대기

대기는 이 명령 하나로 건다. heartbeat, 재배달, 워커의 재전송, 타임아웃은 명령이 거르고 처리할 메시지만 돌려준다.

```text
node .claude/scripts/orca-launch.mjs wait --inbox <내 수신함>
```

- `<내 수신함>`은 Run을 가진 쪽은 `run:<Run ID>`(코디네이터는 실행 Run, 창구는 창구 Run), Run이 없는 팀장은 `dispatch:<자기 Dispatch ID>`다.
- 하네스가 추적하는 백그라운드 작업으로 건다(Claude Code: Bash `run_in_background: true`). 다른 명령과 한 줄에 묶지 않고, 한 세션에 하나만 건다.
- 끝났다는 알림을 받으면 출력의 `messages`를 모두 처리한 뒤에만 다시 건다. 대기가 가져간 메시지는 다시 오지 않는다. 출력을 잃었으면 `--last`를 붙여 마지막 묶음을 다시 본다.
- 대기가 걸려 있는 동안 "You have N orchestration messages" 알림이 오면 도구 호출 없이 턴을 끝낸다.
- `idle: true`는 빈 대기가 세 번 이어졌다는 뜻이다. `orca orchestration worker-list`로 워커 생존을 본다. 침묵만으로 종료로 판정하거나 다시 띄우지 않는다. 올 보고가 오지 않으면 `orca orchestration inbox --terminal <내 수신함> --limit 20`으로 읽기만 한다.
- Codex는 대기를 걸지 않는다. 끝난 백그라운드 명령이 Codex를 깨우지 못한다. 할 일을 마치면 턴을 끝내고, "You have N orchestration message" 알림이 오면 같은 명령에 `--once`를 붙여 한 번 돌린다.
