# qa-verification

고치지 않는다. 실행해서 찾고, 쓴 사람이 바로 재현할 수 있게 적는다. 재현 절차가 없는 결함은 결함이 아니다. 결함을 찾는 것은 검증자의 실패가 아니다. 리포트를 썼으면 성공이고, 검사 자체를 못 했을 때만 실패다.

## 범위 받기

- spec에서 받는 것: 검사 범위, 백로그 항목 ID(수락 기준의 정본), 실행 방법(서버, 명령, 테스트 데이터), 리포트 경로. 대조할 경계면 목록이 있으면 그것도 받는다.
- 영역이 나뉘면 spec에서 **맡을 영역, 보지 않을 영역, 결함 ID 접두어**를 함께 받는다. 셋 중 하나라도 없으면 `ask`로 받는다. 맡지 않은 영역의 결함이 보이면 결함으로 적지 않고 `## 관찰`에 한 줄만 적는다.
- 범위가 좁으면(결함 하나, 변경 하나) 그 변경이 닿는 흐름과 수락 기준으로 한정한다.

## 절차

1. **흐름 실행.** 수락 기준의 흐름을 실제로 돌려 단계마다 기대값과 비교한다. 읽기만 해서 통과로 적지 않는다.
2. **경계면 대조.** 데이터를 주고받는 양쪽(호출과 응답, 입력과 저장, 생산자와 소비자)을 함께 연다. 생산자 쪽 필드 목록을 적고, 소비자 쪽이 접근하는 필드와 대조한 뒤, 어긋난 곳을 실행해 확인한다. 한쪽만 읽으면 못 잡는다. 대조할 짝과 점검 항목은 아래 경계면 대조 절에 있다.
3. **수락 기준 대조.** 백로그 항목의 수락 기준을 항목마다 ✅나 ❌로 대조한다. 기준을 리포트에 다시 쓰지 않고 항목 ID를 가리킨다.
4. **관련 테스트.** spec이 정한 범위의 테스트만 돌린다. 저장소 전체 테스트는 코디네이터가 Run 끝에 한 번 돌린다.
5. **기록.** 결함마다 아래 형식으로 적는다.

실행 환경이 뜨지 않으면 정적으로 할 수 있는 검사(경계면 대조, 테스트)만 하고, 못 돌린 흐름은 `## 검증`에 ❌로 적는다. 통과로 적지 않는다.

외부 데이터와 운영 상태를 바꾸지 않는다. 시험으로 만든 상태는 검사 뒤 되돌린다. 토큰이나 비밀 값은 리포트와 출력에 쓰지 않는다.

## 경계면 대조

절차 2에서는 아래 짝을 함께 연다. 대조할 짝은 spec이 넘긴 것을 먼저 보고, 없으면 계획서(`docs/superpowers/plans/<phase>.md`)의 `## DAG` 의존 줄에서 고른다. 의존 줄에는 뒤 Task가 앞 Task의 무엇을 읽는지 적혀 있다.

| 대조 대상 | 생산자 | 소비자 |
| --- | --- | --- |
| 응답 구조 | 응답을 만드는 곳 | 그 응답을 읽는 쪽이 기대하는 형태 |
| 경로 | 실제 파일과 라우트 구조 | 링크와 이동 코드의 경로 |
| 상태 전이 | 전이를 정의한 곳 | 상태를 바꾸는 코드 |
| 저장에서 화면까지 | 저장소의 필드 이름 | 응답 필드와 화면이 읽는 이름 |

- 점검 항목은 [references/boundary-checklist.md](references/boundary-checklist.md)에 있다. 항목마다 결과를 리포트의 `## 경계면 대조`에 ✅, ❌, `(해당 없음)`으로 적는다.
- ❌는 결함 표에도 ID를 붙여 적는다.
- 점검표에 없는 어긋남을 찾으면 리포트의 `## 점검표 후보`에 "양쪽이 맞는가" 꼴의 한 줄로 적는다. 점검표 파일은 직접 고치지 않는다. QA 워커 여럿이 같은 때에 돌기 때문이다. 후보는 회고 때 점검표로 옮겨진다.

## 브라우저

브라우저를 여는 Task면 [references/browser.md](references/browser.md)를 먼저 읽는다. 요점은 넷이다.

- **병렬은 워커 단위다.** 프로젝트 설정의 두 줄(`PLAYWRIGHT_MCP_ISOLATED`, `PLAYWRIGHT_MCP_HEADLESS`)이 있어서 같은 폴더의 QA 워커 여럿이 Playwright MCP를 동시에 쓴다. 한 세션 안의 서브에이전트끼리는 브라우저를 나눠 쓰지 못한다.
- **비밀값은 Playwright MCP에 넣지 않는다.** 쿠키, 토큰, 비밀번호를 넣거나 읽으면 `secret-gate` 훅이 막는다. 로그인이 필요한 검증은 `.claude/scripts/browser/launch.cjs`로 한다.
- **화면을 여러 장 찍는 캡처와 3D·WebGL 실측은 Playwright MCP로 하지 않는다.** `launch.cjs` 스크립트로 돌려 파일로 남기고, 그 파일을 읽어 판정한다.
- **성능 수치는 다른 검증이 끝난 뒤 혼자 여러 번 잰다.** 병렬로 도는 동안 잰 값으로 판정하지 않는다. 수치 옆에 `@playwright/mcp` 버전과 Claude Code 버전을 적는다.

## 심각도

| 심각도 | QA 기준 |
| --- | --- |
| High | 흐름이 막히거나 수락 기준을 어긴다 |
| Medium | 동작은 하지만 명세와 다르다 |
| Low | 미세한 것 |

- 고치는 것은 High 이상과 완료 기준 미달뿐이다. Medium 이하는 인박스로 보낸다. 리포트의 `## 인박스 후보` 절에 한 줄씩 적고, `product-manager`가 인박스에 옮긴다.
- 데이터 이상(비어 있는 값, 중복, 플레이스홀더)은 코드 결함이 아니다. 코드가 요구와 다르게 가공하거나 숨기면 코드 결함이다.

## 결함 ID

- 형식은 `H-n`, `M-n`, `L-n`이다. 같은 범위의 이전 리포트가 있으면 번호를 이어 쓴다.
- 영역이 나뉘면 spec이 배정한 접두어를 모든 ID 앞에 붙인다(`A-H-1`, `B-M-2`). 영역 리포트끼리 번호가 겹치면 통합 보고에서 구분이 안 된다.
- 같은 결함은 재검에서도 같은 ID를 쓴다. 새 번호를 붙이지 않는다.

## 재검

재검은 그 결함 ID의 재현 확인만 한다. 새 탐색, 새 시나리오, 전체 테스트를 하지 않는다.

1. spec이 넘긴 결함 ID마다 원래 리포트의 재현 절차를 그대로 다시 돌린다. 빌드한 결과물로 확인하는 결함은 다시 빌드한 뒤에 돌린다. 빌드 전에 돌리면 고친 결함이 그대로 재현된다.
2. 결과는 같은 리포트의 다음 버전 파일(`_v<N+1>`)에 쓴다. 넘긴 파일을 고쳐 쓰지 않는다. 첫 줄 아래에 `재검 회차: N`을 적는다.
3. 결함 표의 상태 열에 `해결됨`, `남음`, `미재검`(spec이 넘기지 않은 ID), `새로 찾음`(아래 4) 중 하나를 적는다.
4. 새 결함을 찾으려고 탐색하지는 않는다. 그래도 재검 중에 새로 찾은 결함이 High면 결함 표에 새 ID로 넣고 상태를 `새로 찾음`으로 적는다. 남은 High로 세어지고, 이번에 고칠지는 코디네이터가 루프 횟수를 보고 정한다(2회를 다 썼으면 사용자에게 묻는다). 원래 결함의 회귀면 원래 ID에 `남음`으로 적고 근거를 붙인다. Medium 이하는 `## 인박스 후보`에 적는다.

수정 루프는 최대 2회다. 회차를 세고 루프를 멈추는 것은 코디네이터와 팀장의 몫이고, 이 스킬은 회차를 리포트에 적기만 한다.

## 편집 범위

- 테스트 파일만 고칠 수 있다. 결함을 재현하는 회귀 테스트를 추가할 수 있다(테스트 이름에 결함 ID, 예: `H-1: …`).
- 제품 코드를 고치지 않는다. 실패한 테스트도 고치지 않고 결함으로 적는다.

## 리포트 형식

경로와 이름은 spec을 따른다(`team-qa`의 산출물 규칙). 뼈대는 양식 `docs/harness/templates/report.md`이고, 결함 표와 QA 절을 더한다.

```markdown
# <Task ID> <이름> 리포트

재검 회차: N            ← 재검일 때만

## 한 일
- 검사 범위, 실행 환경(서버, 빌드 종류), 수행한 절차 번호

## 결함
| ID | 심각도 | 상태 | 위치 | 근거 |
| --- | --- | --- | --- | --- |
| H-1 | High | ❌ 발견 | `파일:줄` | 기대(정본 항목 ID) / 실제 / 재현 절차 |

## 경계면 대조
| 대조 대상 | 생산자 | 소비자 | 결과 |
| --- | --- | --- | --- |
| 응답 구조 | `파일:줄` 만드는 형태 | `파일:줄` 기대하는 형태 | ✅ 또는 ❌ H-1 |

- ✅ / ❌ <결함 ID> / (해당 없음) <점검표 항목>

## 수락 기준 대조
- ✅ / ❌ <백로그 항목 ID의 기준 줄>

## 판단 필요
- 규칙과 요구가 부딪치는 것. 결함이 아니다.

## 인박스 후보
- Medium 이하 결함(재검 중에 새로 찾은 것 포함), 후속 작업. 한 줄씩

## 점검표 후보
- 점검표에 없는데 이번에 찾은 어긋남. "양쪽이 맞는가" 꼴로 한 줄씩 (출처: <결함 ID>)

## 관찰
- 범위 밖에서 본 것. 한 줄씩

## 직접 소통

## 검증
- ✅ `<내가 돌린 검사>` → <결과>
- ❌ `<못 돌린 흐름>` → <이유>
- (참고) <완료 기준 밖의 줄>

## 남은 것
```

- **결함 표의 ❌는 발견이고, `## 검증`의 ❌는 검증 실패다.** 찾은 결함, 경계면 대조의 ❌, 수락 기준 ❌는 `## 결함`, `## 경계면 대조`, `## 수락 기준 대조`에만 적고, `## 검증`에는 내가 할 검사를 했는지만 적는다. 못 돌린 것도 ❌다.
- 범위 밖이거나 spec이 금지해서 안 한 줄은 `(참고)`로 시작한다.
- 보고는 spec의 `보고` 줄을 따른다. 제목에 High 개수를 넣는다.
