# requirements-write

작업 단위는 `요구사항 정리`다. 요구사항 작성의 바탕은 revfactory/harness-100의 46-product-manager(Apache-2.0)다.

## 읽는 것

- 브리프 원문·사용자 결정, 기존 결정 기록, 색인 `docs/DOCUMENTATION_INDEX.md`가 가리키는 정본. 기본 PRD는 `docs/01-product/prd.md`, 기본 SRS는 `docs/02-requirements/srs.md`다.
- 쓸 문서의 양식만 읽는다. PRD는 `docs/harness/templates/product-docs/prd.md`, SRS는 `docs/harness/templates/product-docs/srs.md`다. 각 양식의 `채우는 법` 절이 작성법이고 `문서 구조` 절이 문서의 꼴이다. 이 스킬은 양식의 규칙을 다시 적지 않는다.
- ID 번호와 상태 표시는 `.claude/skills/docs-management/SKILL.md`의 `ID와 상태 값` 절, 어느 사실을 어느 문서에 쓰는지는 같은 파일의 `정본 표` 절만 읽는다.

첫 제품 사실이나 첫 실제 요구사항을 채울 때 설치 초안 표시를 걷는다.

## 절차

1. **요청 끊기.** 요청을 한 가지 요구씩 R1, R2로 끊고 원래 번호를 유지한다. 범위를 나누기 전에 이번 묶음 밖 요구도 전부 대조한다. 우선순위·팀 규모 같은 결정은 해당 줄의 근거로 쓴다.
2. **PRD.** 요구마다 US를 연결한다. 배경·목표·성공 지표·가정은 브리프가 뒷받침하는 값만 쓰고, 빠진 값은 열린 질문에 올린다. 이유를 모르면 `이유 정해지지 않음`으로 둔다. 사용자 흐름·화면에는 확인된 정보만 넣고 제외한 요구와 사유를 남긴다. PRD에는 SRS의 `(계획됨)` 표시를 붙이지 않는다.
3. **SRS.** US를 FR/NFR로 잇는다. 아직 미구현인 줄은 제자리에서 고친다. 바뀔 기존 동작의 줄이 없으면 새 줄을 만들고 현재 동작을 리포트에 적는다. 인터페이스·계약 ID와 다른 절은 실제 정본과 확인된 근거가 생기면 연결한다.
4. **대조 표.** `요구 | 요청 원문 요약 | US | FR / NFR | 넣지 않은 사유` 표를 리포트에 남긴다. PRD만 쓰면 FR/NFR 칸에는 요청 범위를 적는다. 요구마다 실제 ID 또는 제외 사유가 있는지, 각 ID가 문서에 있고 유일한지, 수치·우선순위의 출처가 있는지 확인한다. 구현 가능성이 미확인이면 리포트에 남긴다.
5. **결정 올리기.** 여러 해석이 가능하면 추천안과 근거를 `사용자 결정 필요`에 남긴다. 이미 있는 결정과 부딪치면 창구에 올린다. 같은 문서를 나눠 쓸 때는 순차로 진행하고 남은 범위를 보고한다.
6. **넘기기.** PM 자가 점검 후 Planner가 해당 버전을 `product-review`로 검토한다. PM은 실제 정본 경로와 ID를 함께 넘긴다.

## 구현 뒤 현행 반영

QA 근거로 구현이 확인되면 PM이 SRS의 `(계획됨)` 표시와 수용 기준을 현행화하고, 바뀐 절을 `doc-steward`에게 전달한다. 제품 결정을 문서 확인자에게 넘기지 않는다.
