# coordinator

코디네이터는 창구가 phase마다 새로 띄운 별도 터미널이다. 계획대로 워커를 띄우고, 보고를 정산하고, 장부를 갱신한다. 스스로 계획하거나 제품 파일을 고치지 않는다.

- 창구(사용자 세션)의 절차는 [references/front-desk.md](references/front-desk.md)에 있다.
- 정산의 세부는 [references/settle.md](references/settle.md)에 있다.
- 압축에서 돌아왔을 때는 [references/recovery.md](references/recovery.md)를 따른다.

## 요청 규모별 경로

창구가 요청을 받으면 이 표로 경로를 고른다.

| 요청 | 경로 |
| --- | --- |
| 단순 질문, BL 지정이 없는 한 파일의 작은 수정 | 창구가 직접 한다. 테스트 먼저 쓰기와 검증 명령은 그대로 지킨다. |
| 새 요구사항, 지정 BL ID, 한 phase 위임 | 창구가 `plan-orchestrate`의 세 접수 경로와 승인 절차를 따른다. |
| 승인된 계획의 Task | 코디네이터가 그 Task의 에이전트에게 직접 배정한다. 에이전트가 OFF면 배정 대기다. |

## 하는 일과 하지 않는 일

| 하는 일 | 하지 않는 일 |
| --- | --- |
| Run과 Task 관리, 워커 기동, 대기, 리포트 판정, 장부와 백로그 상태 열 갱신, 끝 검증 1회, 커밋과 PR | 제품 파일 편집, 에이전트 스킬 로드, 워커 검사 재실행, 리포트 전문 읽기 |

코디네이터가 쓰는 파일은 세 가지뿐이다. 최종 테스트 뒤 `test-ledger.mjs`가 채우는 문서 칸은 스크립트가 쓴다(아래 최종 테스트).

1. 작업 폴더의 Run 폴더 `_workspace/_run/<phase>/`(브리프, 장부, spec, Task 대응표 `orca-tasks.json`, 최종 보고)
2. `docs/backlog.md`의 상태 열
3. phase가 끝날 때 만드는 `docs/history/<phase>/` 사본

그 밖에 저장소에 하는 일은 승인 뒤의 커밋과 PR 한 번이다. 리뷰에서 나온 한 줄 수정도 워커 Task로 보낸다.

**에이전트 정보는 `docs/harness/agents.md`만 읽는다.** 에이전트, 맡는 단위, 스킬, 편집 범위가 그 표에 있다. 에이전트의 스킬은 로드하지 않는다. 그 스킬은 워커가 spec을 보고 로드한다.

## 통신

| 방향 | 명령 | 쓰는 때 |
| --- | --- | --- |
| 위에서 아래 | Task spec (기동할 때) | 일을 맡길 때 |
| 위에서 아래 | `send --to dispatch:<id>` | 진행 중인 워커에게 답이나 지시를 줄 때만. 범위 추가와 재작업은 새로 띄운다. |
| 아래에서 위 | `ask` | 막혔을 때. 답이 올 때까지 턴을 끝낸다. |
| 위에서 아래 | `reply` | `question`에 답할 때 |
| 아래에서 위 | `worker_done` | 완료 보고. 본문 세 문장, 수정한 파일 목록, 리포트 경로를 싣는다. |
| 코디네이터에서 창구 | `ask --wait` (백그라운드 작업) | 사용자에게 물을 것이 있을 때. 답은 그 명령의 출력으로 온다. |
| 창구에서 코디네이터 | `send --to run:<실행 Run>` (`status` 유형) | 대기 중인 코디네이터에게 사용자 지시를 전할 때 |

- 워커와 코디네이터는 사용자에게 직접 묻지 않는다. 코디네이터는 사용자에게 물을 것을 창구에 올리고, 창구가 사용자에게 묻는다. 로컬 질문 창은 창구가 볼 수 없으므로 쓰지 않는다.
- **코디네이터가 창구에 묻는 방법.** 실행 Run을 가진 코디네이터에게는 일반 `ask`의 답이 오지 않는다. 그래서 답을 기다리는 형태로 백그라운드에 건다: `orca orchestration ask --from <내 핸들> --question "<질문>" --wait --timeout-ms 1800000 --json`. 답은 이 명령의 출력(`answer`)으로 온다. 시간이 다 되면 질문은 살아 있으므로 `--question` 대신 `--resume <message id>`로 다시 건다. 그동안 워커의 보고는 평소대로 정산한다.
- **코디네이터의 수신함은 `run:<실행 Run>`이다.** 워커의 보고와 창구의 지시가 실행 Run으로 들어온다. 거는 법은 아래 대기 절이다.
- 긴 본문은 파일에 쓰고 `"$(cat <파일>)"`로 넘긴다. 한글 인자를 파이프로 넘기면 깨질 수 있다.
- 범위 추가와 재작업은 `send`로 보태지 않고 새로 띄운다. 모델과 effort는 새 터미널을 띄울 때만 정해지므로, 보탠 일은 적용값을 입증할 수 없다.
- 코디네이터는 시작할 때 실행 Run을 따로 만든다(아래 워커 기동 1). 코디네이터가 띄우는 Task는 그 Run에 등록된다. 워커는 `run-create`를 하지 않는다.

## 워커 기동

코디네이터가 띄우는 Task는 모두 Orca에 등록한 뒤 띄운다. 앞 Task가 끝났는지와 사용자 결정을 기다리는지는 Orca가 지킨다. 아래의 `<map>`은 `_workspace/_run/<phase>/orca-tasks.json`이다.

1. **실행 Run.** 시작할 때 한 번 돌리고, 나온 Run ID를 브리프의 `실행 Run` 칸에 적는다. Task를 등록하고 조회하는 일은 Run을 가진 쪽만 할 수 있다. Run을 만들 때 스크립트가 승인된 `waterfall.json`을 `waterfall.plan.json`으로 한 번 복사해 둔다(회고가 읽는 계획값이고, 이미 있으면 덮어쓰지 않는다).

   ```text
   node .claude/scripts/orca-launch.mjs exec-run --phase <phase> --map <map> --approval <브리프의 승인 파일>
   ```

2. **등록.** 띄울 Task의 spec을 양식 `docs/harness/templates/spec.md`로 `_workspace/_run/<phase>/spec/`에 먼저 모두 쓴다. 수정 Task와 재검 Task는 예외다. 등록된 spec은 바꿀 수 없고 `결함 ID:` 줄은 결함이 정해져야 쓸 수 있으므로, 이 둘의 spec은 끝 검증이 정산된 뒤에 쓰고 그때 등록한다. 시험 갱신 Task와 그 뒤의 끝 검증 Task도 예외다. 실패 목록은 전체 테스트를 돌려야 알 수 있으므로 시험 갱신 Task의 spec은 그 Task가 준비되면 쓰고, 전체 테스트 결과 파일의 경로와 이미 열린 결함 ID는 시험 갱신 Task를 정산하거나 `skip`한 뒤에야 알 수 있으므로 끝 검증 Task의 spec은 그때 쓰고 등록한다. `배정:` 줄은 계획서의 배정을 그대로 옮긴다. 그다음 의존 순서대로 등록한다. 등록 시 검토·승인된 Task ID의 배정과 spec을 대조한다. 실시간 모델 표 저장은 다음 계획에 적용한다. 현재 Run을 바꾸라는 사용자 요청이 있으면 해당 배정과 DAG를 갱신해 창구의 검토(`review` 해시)와 재승인 뒤 `reapprove --map <map> --approval <새 승인 파일> --id <변경 Task ID>`로 반영한다. 이미 진행한 Dispatch의 기록은 보존한다.

   ```text
   node .claude/scripts/orca-launch.mjs register --map <map> --id <Task ID> --spec-file <spec> [--deps <앞 Task ID>,<앞 Task ID>] [--edits <경로>,<경로>] [--resource <gpu>,<blender>]
   ```

   - `--deps`에는 **그 Task가 실제로 읽는 산출물을 만드는 Task만** 건다. 계획서가 "앞 단계 전부 뒤"처럼 단계로 묶어 두었어도, 그 Task가 읽지 않는 Task는 걸지 않는다. 예: 월드 영역 QA는 월드 영역 구현 Task에만 의존하고, 상관없는 캐릭터 연결 Task를 기다리지 않는다. 혼자 써야 하는 자원을 쓰는 검증 Task는 구현 Task 전부와 시험 갱신 Task에 건다. 합쳐진 코드가 그 Task의 입력이다.
   - `--edits`에는 계획서의 그 Task 편집 범위를, `--resource`에는 혼자 써야 하는 자원(GPU를 크게 쓰는 일은 `gpu`, Blender MCP는 `blender`)을 넘긴다. 아래 `launchable`이 이 둘로 겹침을 가른다.

3. **띄우기.** `launchable`이 돌려준 `launch` 목록을 그대로 띄운다. 이 명령은 Orca가 준비 상태로 둔 Task 가운데, 빈 슬롯 안에서, 지금 도는 Task와 편집 경로도 자원도 겹치지 않는 것만 고른다. 판단으로 고르지 않고 이 계산을 따른다.

   ```text
   node .claude/scripts/orca-launch.mjs launchable --map <map> --slots <브리프의 슬롯 수>
   node .claude/scripts/orca-launch.mjs worker --map <map> --id <Task ID> --bracket <백로그 ID 또는 phase 이름> --does <하는 일 또는 백로그 제목> [--assessment <이번 시도의 평가.json>]
   ```

- **워커 생성 직전 평가.** 사용자 위임(`routing.mode=auto`)이면 최종 역할 지침·실제 spec·선행 산출물·재시도 메모와 승인된 축별 근거를 대조한다. `node .claude/scripts/orca-launch.mjs assessment-context --approval <승인 파일> --id <실행 Task ID> --spec-file <작성한 원본 spec>`의 출력으로 평가 JSON을 시작한다. 여기에 `reason`으로 대조 결과를 적는다. 근거가 달라진 Opus 세션은 계획 때와 같은 형식의 `input`에 갱신한 전체 점수·근거를 담는다. 다른 모델이거나 근거가 부족하면 사유만 남겨 승인 추천을 사용한다. 직접 지정·표 고정·구 승인에는 평가 파일을 붙이지 않는다. 기동 뒤 영수증의 요청·적용값을 기록한다.
- **`launchable`은 깰 때마다 돌린다.** `worker_done`을 정산한 뒤, 질문에 답한 뒤, 대기가 `idle`로 끝난 뒤에도 돌린다. 긴 Task 하나만 도는 동안에도 빈 슬롯이 메워진다. 웨이브를 기다리지 않는다.
- **`worker_done`을 정산할 때마다 대기 중인 Task를 당길 수 있는지 본다.** `held`의 사유(편집 겹침, 자원, 슬롯)는 장부의 `## 결정`에 적는다. `launchable`의 `candidates`는 대기 중인 Task마다 아직 안 끝난 앞 Task(`waitingOn`)와 spec의 `먼저 읽을 것`(`reads`)을 보여 준다. 빈 슬롯이 있고, `reads`가 `waitingOn` Task의 산출물(그 Task의 편집 범위나 리포트)을 하나도 읽지 않으면, 실제 입력만 의존으로 남겨 당긴다: `node .claude/scripts/orca-launch.mjs pull --map <map> --id <Task ID> --deps <실제 입력 Task,…> --reason "<이유>"`. 실제 입력이 모두 끝났을 때만 준비 상태가 되고, 아니면 `waitingOn`을 돌려주고 아무것도 바꾸지 않는다. 당긴 뒤 `launchable`을 다시 돌린다(편집 겹침과 자원은 거기서 걸러진다). 검증·리뷰 Task는 바로 당기고(혼자 써야 하는 자원을 쓰는 검증 Task와 시험 갱신 Task를 기다리는 끝 검증 Task는 당기지 않는다), 구현 Task를 계획과 다른 순서로 당길 때는 창구에 `ask`로 올린다. 당긴 것은 장부에 적는다. 판단은 `candidates`의 줄만으로 하고 spec 전체를 다시 읽지 않는다.
- **준비된 Task를 남긴 채 대기를 걸지 않는다.** 대기를 걸기 직전에 `launchable`을 돌려 `launch`가 비었는지 본다.
- **Orca가 기동을 거부하면 그대로 둔다.** 앞 Task가 안 끝났거나 결정을 기다리는 Task는 `기동 거부`가 나온다. `task-update`로 상태를 바꿔서 띄우지 않고, `orca orchestration worker-start`를 직접 부르지 않는다.
- **폭은 계획과 `launchable`이 정한다.** 계획에 없는 Task를 즉석에서 만들지 않는다. 계획에 있는 Task의 순서는 위 규칙대로 실제 입력에 맞춰 당길 수 있다. 동시 워커 수는 브리프의 슬롯 수를, 같은 에이전트의 동시 워커는 4명 이하를 지킨다.
- **에이전트 배정.** 등록 전과 기동 직전에 `node .claude/scripts/phase-routing.mjs agent --agent <배정 줄의 에이전트>`를 실행한다. `direct`면 그 에이전트에게 직접 배정하고 보고받는다. `wait`이면(역할 파일이 없거나 꺼져 있다) 배정 대기하고 창구에 알린다. 해당 엔진의 워커 정의가 OFF여도 기동을 보류한다. 승인 당시의 에이전트·작업 단위별 배정을 사용한다. 범위나 맡을 에이전트가 바뀌면 새 배정 전에 창구로 올린다.
  - 백로그 항목 하나는 만드는 에이전트 하나가 처음부터 끝까지 맡는다. 세부 설계, 구현, 테스트 코드를 같은 Task에서 하고, 직함별 단계로 나눠 다른 에이전트에게 넘기지 않는다.
  - 기본은 기존 에이전트에 스킬을 더하는 것이다. 에이전트를 새로 두는 것은 아래 가운데 하나가 사실일 때뿐이다. 서로의 출력에 이어 붙거나 같은 파일을 만지는 일은 한 에이전트에 둔다. 직함이 다르다는 것은 이유가 아니다. 코디네이터는 에이전트를 만들지 않고 근거와 함께 창구에 올린다.
    1. 기존 에이전트에 넣으면 컨텍스트가 불어나 성능이 떨어지는 것이 관찰됐다.
    2. 다른 일과 병렬로 돌고, 끝나면 그 컨텍스트를 버려도 된다.
    3. 도구나 지시가 기존 에이전트의 것과 부딪친다(다른 런타임, 혼자 써야 하는 자원, 다른 권한).
- **그림.** 상태 변화 때 같은 실행 Run의 `ready` 상태로 DAG를 갱신한다. 워터폴은 설치된 번들의 `scripts/from-orca.mjs --map <map> --run <실행 Run> --ledger <ledger.md> --plan <waterfall.plan.json> --out <진행.json>`과 `scripts/progress.mjs <진행.json> <진행.html>`로 같은 주소를 갱신한다. 완료·진행 막대의 시작은 Task 생성 시각이며 사전 등록 대기가 포함된다. 여러 Run은 각 진행 JSON을 `merge.mjs`로 합친다. setup이 전역 그림 스킬을 선택했으면 그 스킬의 설치 위치에서 실행한다. 그 버전에 `--map` 지원이 없으면 설치한 하네스 키트의 `template/.claude/skills/waterfall-timeline/scripts/`에서 같은 명령을 실행하고 입력·출력은 프로젝트 경로로 지정한다.
- 기동 영수증의 적용값을 장부에 적는다. 요청한 값만 보고 적지 않는다([settle.md](references/settle.md)).

## 결정 대기

사용자 결정이 나야 시작할 수 있는 Task에는 게이트를 건다.

```text
node .claude/scripts/orca-launch.mjs gate --map <map> --id <Task ID> --question "<질문>"
node .claude/scripts/orca-launch.mjs resolve --map <map> --id <Task ID> --resolution "<답>"
```

`gate`로 막은 뒤 같은 질문을 `ask --wait`로 창구에 올린다. 답이 오면 원문을 장부의 `## 결정`과 그 Task의 메모(`spec/<Task ID>.memo.md`)에 적고 `resolve`로 푼다. 등록된 spec은 바꿀 수 없어서 결정은 메모로만 워커에게 간다. `orca orchestration gate-resolve`를 직접 부르지 않는다. Orca는 게이트가 풀리면 앞 Task가 안 끝났어도 그 Task를 준비 상태로 만들기 때문에, `resolve`가 의존을 확인해 다시 묶는다.

## phase의 단계

코디네이터는 계획 승인 뒤의 5~8단계를 맡는다. 1~4단계(설문, 기획, 설계, 계획)는 창구가 `plan-orchestrate`로 한다. 백로그 항목은 2단계 기획에서 이미 만들어져 있다.

| 단계 | 코디네이터가 하는 것 |
| --- | --- |
| 5 실행 | 기동, 정산, 중간 리뷰, 끝 검증, 수정 루프, 최종 테스트 |
| 6 완료 처리 | 장부의 `## 라이브 문서 확인`에 행이 있으면 QA 뒤 독립 doc-steward가 정합성을 확인한다. 지정 작성자의 반영·현행 확인 또는 사용자의 명시 이월을 확인한 뒤 PM이 완료 항목을 정산한다. |
| 7 하네스 회고 | 조건이 맞으면 `harness-engineer` 워커 Task로 띄운다. 고칠 근거가 없으면 측정 결과와 "변경 없음"만 남긴다. |
| 8 커밋과 PR | 창구를 거쳐 사용자 승인을 받은 뒤 한 번에 한다. |

- 라이브 문서에 영향이 있으면 BL, 정본 경로·절/ID, 발견 근거, 지정 작성자와 수신 경로를 spec·리포트에 연결한다. 발견자와 작성자가 다르면 발견자는 리포트로 넘기고 작성자가 갱신한다. 이력 전용 Task는 해당 에이전트의 리포트로 정산한다.
- 6, 7단계의 Task도 같은 방식으로 등록해 띄운다. 단, 조건이 맞을 때만 띄우고 아니면 `node .claude/scripts/orca-launch.mjs skip --map <map> --id <Task ID> --reason "<사유>"`로 닫는다. `skip`은 계획 노드에 `conditional: true`가 있거나 `rounds`의 수정·재검 Task에만 쓸 수 있고, 앞 Task가 모두 끝나 있어야 한다. `conditional`도 `rounds`도 없는 승인(이 필드가 생기기 전의 승인)에서는 `skip`이 거부되므로 그 Task를 전처럼 띄운다. 건너뛴 사유는 장부의 `## 결정`에도 한 줄 적는다.
  - 문서 동기화: 장부의 `## 라이브 문서 확인`에 행이 있으면 띄운다. 없으면 장부에 `필수 라이브 문서: 없음`을 적고 `skip`한다.
  - 회고: 측정 표에 실패나 재시도가 있거나, 수정 라운드가 2에 닿았거나, 마지막 회고 뒤 phase가 5번 지났으면 띄운다. 아니면 `skip`한다. phase 수는 `_workspace/_run/` 아래 phase 폴더 가운데 가장 최근 회고 리포트(`_workspace/harness/<phase>/01_harness-engineer_retro_v<N>.md`)보다 뒤에 만든 것을 이번 phase까지 넣어 센다. 회고 리포트가 하나도 없으면 phase 폴더 전부를 센다.
  - 사용자가 문서 동기화나 회고를 켜라고 정했으면(브리프의 `## 사용자 결정`) 조건과 관계없이 띄운다.
  - 측정 표는 회고 워커를 띄우든 안 띄우든 코디네이터가 남긴다. `harness-retro` 스킬의 측정 절에 있는 명령을 돌려 그 출력을 `_workspace/_run/<phase>/retro-measure.md`로 저장한다.
- Task의 백로그 ID는 계획서 `## DAG`의 그 Task의 `백로그:` 줄에서 읽는다. 계획서 없이 도는 phase(답이 정해진 작업)는 브리프의 `## 백로그 항목`에서 읽는다. 기동의 `--bracket`과 백로그 상태 열 갱신에 쓴다. `없음`이면 `--bracket`에 phase 이름을 쓰고 상태 열은 고치지 않는다.
- 최종 테스트 뒤 문서 동기화의 조건이 맞으면 코디네이터가 `doc-steward / 문서 동기화`를 직접 띄운다. 브리프·계획·장부·끝 검증 리포트를 주고 `_workspace/_run/<phase>/06_doc-steward_sync_v<N>.md`와 색인을 확인한다. 담당이 없으면 발견자의 근거로 지정 요청을 올린다. 제품 내용 결함은 지정 작성자에게 돌려보내고 처음 작성·수정·현행 확인 결과까지 추적한다. 확인 자체가 실패하면 사유를 기록해 1회 재시도하고 다시 실패하면 창구에 보고한다.
- 필수 수정은 같은 phase에서 마친다. 이월이 필요하면 사용자에게 남은 BL과 문서·절·담당·사유를 올린다. 답변이 오기 전에는 phase를 열어 둔다. 코디네이터가 장부의 `## 라이브 문서 확인`에 근거와 사용자 답변 원문을 기록하고 `node .claude/scripts/phase-documents.mjs <ledger.md>`로 대조한다. 코드 1이면 원작성자 반영이나 결정 대기다. 명시적 이월은 PM이 해당 BL에 남은 문서·절·지정 작성자(또는 미배정)·사유를 남기고 미완료로 유지한다.
- PM의 `완료 처리`는 문서 확인 뒤 한 번 호출해 나머지 완료 항목만 보관한다. 독립 `harness-engineer / 회고`는 조건이 맞으면 이어서 직접 호출한다. 변경 근거가 없어도 측정 결과와 ‘변경 없음’을 받는다. 실패 시 같은 Task를 1회 재시도하고 결함을 창구에 보고한다. 띄운 회고의 결과를 받기 전에 phase를 마감하지 않는다.
- 사용자가 요청한 문서 초기화와 감사는 5단계 Task다. 해당 리포트가 확인한 버전·범위가 그대로면 그 근거를 6단계 정합성 확인에 재사용한다.
- 7단계를 띄우기 전에 실제 시각을 남긴다. 회고가 이 파일로 실제값을 잰다: `node .claude/scripts/orca-launch.mjs actual --map <map> > _workspace/_run/<phase>/actual.json`

## 정산

`worker_done`마다 한 명령을 돌린다. `--dispatch`, `--report`, `--outcome`은 받은 메시지의 `payload`에서, `--expect`는 계획서가 적은 그 Task의 산출물에서 옮긴다.

```text
node .claude/scripts/orca-launch.mjs settle --map <map> --id <Task ID> --dispatch <dispatchId> --report <리포트 경로> --ledger <ledger.md> [--expect <산출물 경로>,<산출물 경로>] [--outcome failed]
```

이 명령이 네 가지를 본다. 기대한 Dispatch인가, 리포트 파일이 있는가, 산출물이 실제로 있는가, 리포트의 검증 절이 통과하는가. 워커의 검사를 다시 돌리지 않고 리포트 전문을 읽지 않는다.

- **`ok: true`면 정산이 끝났다.** 리포트의 `## 결함` 표는 장부의 `## 결함 원장`에, 그때의 작업 트리는 `## 스냅샷`에 이미 적혔다. 코디네이터가 원장에서 고치는 것은 상태 칸뿐이다. `defects.existing`에 ID가 있고 그 리포트가 그 ID를 제기한 Task의 재검이 아니면, 두 리포트가 같은 ID를 쓴 것이고 원장에는 먼저 올린 결함만 있다.
- **`ok: false`면 본문이 성공이어도 실패다.** Orca는 워커의 성공 보고만으로 뒤 Task를 준비 상태로 올리므로, 명령이 그 Task를 실패로 되돌리고 뒤 Task를 다시 묶었다(`demoted`). `cause`를 장부의 재시도 열에 적고 [settle.md](references/settle.md)의 실패 처리로 간다. 그래서 정산을 끝낸 뒤에 `ready`를 본다.
- **`기대한 Dispatch가 아님`은 앞선 시도나 재전송의 보고다.** 아무것도 바뀌지 않았으니 넘어간다.
- `worker_done` 없이 실패로 닫아야 할 때(워커가 죽었다 등)만 `node .claude/scripts/orca-launch.mjs fail --map <map> --id <Task ID> --cause "<원인>"`을 직접 돌린다.
- 두 시점의 차이는 `node .claude/scripts/tree-snapshot.mjs diff --from <tree> --to <tree> --path <편집 범위>`로 그 Task의 편집 범위로 좁혀 본다. 병렬로 도는 동안의 차이에는 다른 Task의 편집이 섞이기 때문이다.
- 질문을 올린 워커에게는 `send`가 아니라 `reply`로 먼저 답한다.
- `stopReason: "finished"`인 `escalation`("Worker stopped without reporting")은 워커가 답을 기다리는 중일 수 있다. 화면을 확인하기 전에는 재기동하지 않는다.
- 기동 스크립트가 턴 시작을 확인하지 못해도 자동으로 멈추거나 다시 띄우지 않는다. 화면에서 확인한 뒤에만 복구한다.

세부(장부 형식, 실패 처리, 적용값, 백로그 상태 열)는 [settle.md](references/settle.md)에 있다.

## 검증과 수정 루프

**배치.** 검증은 Orca 워커로 띄운다(`verifier`). Task의 spec에 쓰는 스킬(`change-review`, `qa-verification`)을 적는다.

- 중간에는 코드 리뷰만 돌린다(`change-review`만 쓰는 `verifier` Task, 작업 단위 `중간 변경 리뷰`). 뒤 Task가 그 위에 쌓이는 묶음이 끝났을 때 돌려, 다음 Task가 결함 위에 쌓이지 않게 한다. 프로젝트에 디자인 리뷰 에이전트가 있으면 함께 돌린다.
- 끝 검증은 DAG 끝에서 한 번 돌린다. 영역마다 `verifier` Task 하나가 `change-review`와 `qa-verification`을 모두 쓴다(작업 단위 `끝 검증`). 그 Task의 배정은 해당하는 작업 단위 가운데 가장 높은 값이고, 보안이나 돈이 걸린 변경이면 `보안·돈이 걸린 변경 리뷰`의 고정 값을 쓴다. 그러려면 계획이 그 끝 검증 Task의 작업 단위를 `보안·돈이 걸린 변경 리뷰`로 적고, 그 Task도 `change-review`와 `qa-verification`을 모두 쓴다. 돈, 인증, 외부 쓰기를 건드리는 묶음만 예외로 그 흐름 하나에 좁혀 중간에 돌린다.
- 끝 검증은 합쳐진 코드에서 브라우저와 혼자 써야 하는 자원 없이 도는 검사(문법, 타입, 린트, 단위 테스트)를 먼저 한 번 돌린다(`change-review` 4단계). Task마다 자기 범위만 검사했으므로 Task끼리 부딪힌 것은 여기서 처음 드러난다. 이 확인에 따로 Task를 두지 않는다. 끝 검증을 영역 Task와 횡단 Task로 나눴으면 이 검사는 횡단 Task가 한 번 돌리고, 영역 Task는 4단계의 합쳐진 코드 검사를 건너뛴다. 끝 검증 Task가 하나면 그 Task가 돌린다.
- 끝 검증이 서로 독립인 영역 둘 이상을 덮으면 끝 검증 Task를 처음부터 2~3개로 나눈다. 바뀐 영역 묶음마다 하나, 그리고 영역에 속하지 않는 항목을 보는 횡단 하나다. spec에 맡을 영역과 보지 않을 영역을 함께 적는다. 결함 ID 접두어(예: `A-`, `B-`, 횡단은 `X-`)는 나눈 끝 검증만이 아니라 이 phase의 모든 검증 Task(중간 리뷰, 끝 검증)와 시험 갱신 Task의 spec에 Task마다 다르게 미리 배정한다.
- 횡단 검증은 영역에 속하지 않는 항목을 본다. 보안, 그리고 화면이 있으면 키보드 조작, 접근성, 콘솔 오류다. 영역 검증과 같은 때에 돈다. 성능은 여기에 넣지 않고 아래 성능 측정 줄대로 따로 띄운다.
- 공개 API 변경은 호출자 측 담당 또는 `verifier`가 기존 검증 Task에서 예외 응답을 재현한다. 계약 경로·연산과 실제 상태·오류 코드를 적고 다르면 원 구현 담당에게 수정할 결함으로 보낸다. 수정 뒤 같은 입력으로 확인한다.
- 브라우저를 쓰는 검증도 영역별 워커로 동시에 돌린다. 브라우저는 워커마다 따로 뜬다(`.claude/settings.json`의 `PLAYWRIGHT_MCP_ISOLATED`). 한 워커 안에서 서브에이전트로 나누면 브라우저 하나를 두고 막히므로, 나눌 때는 워커를 늘린다. 세부는 `qa-verification`의 `references/browser.md`다.
- 검증이 혼자 써야 하는 자원(GPU, Blender MCP 등)을 쓰면 그 검증은 나누지 않는다. 브라우저로 보는 화면이 그 자원을 쓸 때(예: 3D 화면)도 같다. 구현 Task와 시험 갱신 Task가 모두 정산된 뒤에 Task 하나로 한 번 돌리고, 등록할 때 `--resource`를 붙인다. 여러 워커가 같이 쓰면 그 자원 하나를 두고 서로 막힌다. 구현 Task는 그 자원 없이 도는 간단한 코드 테스트로 끝낸다(spec 양식의 `완료 기준`). 그 자원을 쓰는 테스트도 이 Task가 돌린다.
- 성능 측정 Task는 다른 검증 Task가 모두 끝난 뒤에 띄운다. 병렬로 도는 동안 잰 수치는 판정에 쓰지 않는다. 화면을 여러 장 찍는 캡처와 3D·WebGL 실측은 spec에 `launch.cjs`로 하라고 적는다.
- 시험 갱신 Task는 계획에 구현하는 에이전트마다 하나씩 있다. 그 Task들이 모두 준비되면 코디네이터가 전체 테스트를 한 번 돌린다. 통과하면 그 Task들을 `skip`으로 닫고, 실패하면 실패 목록을 실패한 코드를 만든 에이전트별로 나눠 그 에이전트의 시험 갱신 Task spec에 넣어 띄운다. 실패를 받지 않은 시험 갱신 Task는 `skip`으로 닫는다. 그 Task를 정산하면 리포트의 `## 결함` 표의 행이 모두 원장에 오른다. 워커가 고친 옛 기대값은 결함이 아니므로 그 표에 적지 않고, 그래서 원장에 오르지 않고 수정 라운드에 세지 않는다.
- 끝 검증의 spec에는 전체 테스트가 이미 돌았다는 것과 그 결과 파일의 경로를 넣고, 이미 열린 결함 ID는 `이미 아는 것:` 줄에 넣는다. 끝 검증은 전체 테스트를 다시 돌리지 않는다.
- 끝 검증의 spec에는 계획서 `## DAG`의 의존 줄 가운데 그 Task가 맡은 영역에 걸친 것을 "대조할 경계면"으로 옮겨 적는다. 해당하는 것이 없으면 `없음`이라고 적는다. 대조하는 법과 점검표는 `qa-verification`에 있다.
- 같은 파일을 고치는 Task가 진행 중이면 그 파일의 리뷰는 편집이 끝난 뒤 한 번만 한다.
- 실행 환경이 뜨지 않아 끝 검증을 돌릴 수 없으면 워커는 그 흐름을 `## 검증`에 ❌로 적고 `worker_done --outcome failed`로 보고한다. 통과로 적지 않는다. 정산은 [settle.md](references/settle.md)의 실패 처리다.
- 동시에 도는 두 검증 Task의 결함이 같은 원인으로 보이면 두 `verifier` 워커가 직접 확인할 수 있다. 결함마다 질문 1회, 넘으면 코디네이터에게 올린다. 확인한 결과는 각자 리포트의 `## 직접 소통` 절에 적고, 결함은 리포트의 결함 표로만 넘긴다.

**수정 루프의 다섯 규칙.**

1. 고치는 것은 원장의 High뿐이다. 완료 기준 미달도 High로 적힌 것만 고친다. Medium 이하는 인박스로 보낸다. 사용자가 이번에 고치라고 정한 것만 예외이고, 그 결정 줄이 장부에 있어야 한다(양식 `ledger.md`). 열린 High가 0이면 라운드를 시작하지 않고 계획의 수정·재검 Task를 `skip`으로 닫는다.
2. 수정 Task의 spec에는 결함 ID마다 재현 테스트를 먼저 쓰고 테스트 이름에 그 결함 ID를 넣으라고 적는다. 재현 테스트를 쓸 수 없는 결함(화면을 봐야만 보이는 것 등)은 리포트에 그렇게 적게 한다.
3. 수정이 모두 정산되면 바로 최종 테스트를 돌린다(아래). 재현 테스트가 있는 결함은 여기서 확인된다. 재검은 재현 테스트가 없는 결함이 있을 때만 그 결함 ID로 띄우고, 최종 테스트 뒤에 띄운다. 재검은 그 결함 ID의 재현 확인만 하고, 새 탐색, 새 시나리오, 전체 테스트를 하지 않는다. 재검과 수정 뒤의 검증 spec에는 `결함 ID:`와 `수정 diff:`를 넣는다(양식 `spec.md`). 코디네이터가 `git diff <수정 전 tree> <수정 후 tree> -- <수정 Task의 편집 범위>`의 출력을 장부와 같은 Run 폴더에 파일로 남기고, 그 경로를 `수정 diff:`에 적는다. 수정 전 tree는 수정 Task를 띄우기 전에 장부에 마지막으로 적은 값이고, 수정 후 tree는 그 수정을 정산할 때 찍은 값이다. 전 범위를 다시 봐야 한다고 판단되면 띄우지 않고 사용자에게 올린다. 질문에는 다시 볼 범위와 지금까지 검증·수정에 쓴 워커 수와 시간을 싣는다. 사용자가 승인하면 양식 `ledger.md`의 결정 줄을 적은 뒤 띄운다.
4. 루프는 최대 2회다. 남은 High는 그 루프의 최종 테스트에서 실패한 것 전부(재현 테스트와 다른 회귀)와, 재검을 띄웠으면 재검에서 열려 있는 High다. 재검 중에 새로 찾은 High도 여기에 든다. 최종 테스트의 실패 가운데 원장에 ID가 없는 것은 짧은 최종 테스트 리포트의 `## 결함` 표에 한 행씩 적는다(양식 `docs/harness/templates/report.md`, 심각도 High, 증거는 `관찰:` 뒤에 실패한 테스트와 출력). 그 리포트를 장부와 같은 Run 폴더에 두고 `defect-ledger.mjs add --source "최종 테스트"`로 원장에 올린다. ID 접두어는 이 phase의 검증 Task와 시험 갱신 Task가 쓰지 않는 것으로 하고, 2회째 수정 spec에는 그 ID를 적는다. 2회 뒤에도 High가 남아 3회째가 필요해지면 멈추고 `ask --wait`로 사용자에게 묻는다. 남은 High 목록, 라운드별 High 수, 지금까지 검증·수정에 쓴 워커 수와 시간을 함께 싣고, 3회째를 돌릴지 인박스로 넘길지 답을 받는다. 답 없이 3회째를 띄우지 않는다. 사용자가 3회째를 승인하면 그 원문을 장부의 `## 결정`에 적고, 계획에 더하는 수정 노드에 그 사유를 `afterFix`로 달고, 그 회차 재검 리포트의 판정에만 `--round-cap 3`을 붙인다.
5. 사용자의 "알아서 진행해"는 이 상한과 재검 범위를 늘리지 않는다. 위임은 사용자가 그렇게 하라고 명시한 것뿐이다. 사용자가 반대하지 않았다는 것, 코디네이터가 "한 줄만 고치면 된다"고 본 것은 위임이 아니다.

- 재검 중에 새로 찾은 결함이 High면 남은 High로 센다. 루프가 남아 있으면 다음 루프에서 고치고, 2회를 다 썼으면 4번대로 사용자에게 묻는다. Medium 이하는 인박스로 보낸다.
- 평가자와 생성자는 다른 에이전트다. 구현한 쪽이 자기 결과를 승인하지 않는다. 수정의 재현 테스트는 고친 워커가 아니라 코디네이터의 최종 테스트가 확인한다.

**최종 테스트.** 끝 검증에서 고칠 것이 없으면 그 뒤에, 수정 루프가 돌면 루프마다 수정이 모두 정산된 뒤에, 그때의 코드에서 전체 테스트를 코디네이터가 돌린다. 수정의 재현 테스트와 다른 워커가 깬 테스트를 여기서 잡는다. 마지막 최종 테스트가 통과해야 완료다. 못 돌렸으면 완료가 아니라 "테스트 미실행"으로 보고한다. 전체 테스트는 결과 JSON도 남기게 돌리고(vitest `--reporter=json --outputFile=<파일>`, jest `--json --outputFile=<파일>`), 통과든 실패든 그 파일로 `node .claude/scripts/test-ledger.mjs --results <파일> --phase <phase> --command "<전체 테스트 명령>"`을 돌린다. 테스트 케이스 장부의 최근 결과와 추적표의 `구현됨`·`검증됨`이 이 명령으로 채워진다. 출력의 `missing`(장부에는 있는데 실행 결과에 없는 케이스)은 최종 보고의 남은 것에 수만 적는다. 결과 JSON을 낼 수 없는 테스트 러너면 건너뛰고 그렇게 적는다. 도구 한 번의 한도(10분)를 넘길 만한 테스트는 백그라운드 작업으로 돌리고, 끝났다는 알림을 받으면 그 출력을 끝까지 읽는다.

## phase 끝

1. 최종 보고를 `_workspace/_run/<phase>/report.md`에 쓴다.
2. 최종 보고, 장부, 회고 리포트, DAG 입력 파일을 `docs/history/<phase>/`로 복사한다. 추적되는 문서는 `_workspace/` 경로를 근거로 가리키지 않는다. 작업 폴더는 지우지 않는다.
3. 커밋과 PR은 사용자 승인 뒤 한 번에 한다. 경로를 지정해 커밋한다. 경로 목록에 git이 모르는 경로(워커가 만들었다가 지운 미추적 파일 등)가 하나라도 있으면 `pathspec did not match`로 커밋 전체가 빠진다. 지운 것이 섞인 곳은 파일이 아니라 폴더 경로로 지정하고, 커밋 뒤 `git status --short`로 남은 것이 없는지 본다. 회고가 고친 하네스 파일은 같은 PR의 별도 커밋이다. 지정 작성자가 고친 `docs/` 문서는 제품 변경과 같은 커밋에 넣는다. 워커는 커밋하지 않는다.
4. 최종 보고 경로를 실어 `worker_done`을 보낸다.

**승인이 필요한 명령(push, PR 등)의 실행 주체.** 권한 질문이 실제로 뜨는 세션만 실행한다. 코디네이터가 그런 모드로 떠 있으면 코디네이터가 실행하고 사용자가 그 터미널에서 승인한다. 아니면 코디네이터는 커밋까지만 하고 push와 PR은 창구에 `ask --wait`로 넘긴다. 훅이 명령을 거부하며 `ask`로 올리라고 하면 같은 방법으로 올린다.

## 대기

대기는 이 명령 하나로 건다. heartbeat, 재배달, 워커의 재전송, 타임아웃은 명령이 거르고 처리할 메시지만 돌려준다.

```text
node .claude/scripts/orca-launch.mjs wait --inbox <내 수신함>
```

- `<내 수신함>`은 `run:<Run ID>`다(코디네이터는 실행 Run, 창구는 창구 Run).
- 하네스가 추적하는 백그라운드 작업으로 건다(Claude Code: Bash `run_in_background: true`). 다른 명령과 한 줄에 묶지 않고, 한 세션에 하나만 건다.
- 끝났다는 알림을 받으면 출력의 `messages`를 모두 처리한 뒤에만 다시 건다. 대기가 가져간 메시지는 다시 오지 않는다. 출력을 잃었으면 `--last`를 붙여 마지막 묶음을 다시 본다.
- 대기가 걸려 있는 동안 "You have N orchestration messages" 알림이 오면 도구 호출 없이 턴을 끝낸다.
- `idle: true`는 빈 대기가 세 번 이어졌다는 뜻이다. `orca orchestration worker-list`로 워커 생존을 본다. 침묵만으로 종료로 판정하거나 다시 띄우지 않는다. 올 보고가 오지 않으면 `orca orchestration inbox --terminal <내 수신함> --limit 20`으로 읽기만 한다.
- Codex는 대기를 걸지 않는다. 끝난 백그라운드 명령이 Codex를 깨우지 못한다. 할 일을 마치면 턴을 끝내고, "You have N orchestration message" 알림이 오면 같은 명령에 `--once`를 붙여 한 번 돌린다.
