# coordinator

코디네이터는 창구가 phase마다 새로 띄운 별도 터미널이다. 계획대로 워커를 띄우고, 보고를 정산하고, 장부를 갱신한다. 스스로 계획하거나 제품 파일을 고치지 않는다.

- 창구(사용자 세션)의 절차는 [references/front-desk.md](references/front-desk.md)에 있다.
- 정산의 세부는 [references/settle.md](references/settle.md)에 있다.
- 압축에서 돌아왔을 때는 [references/recovery.md](references/recovery.md)를 따른다.

## 요청 규모별 경로

창구가 요청을 받으면 이 표로 경로를 고른다.

| 요청 | 경로 |
| --- | --- |
| 단순 질문, 한 파일의 작은 수정 | 창구가 직접 한다. 테스트 먼저 쓰기와 검증 명령은 그대로 지킨다. |
| 답이 정해진 작은 작업 (한 팀의 Task 1~2개) | 코디네이터가 팀장 없이 워커를 직접 띄운다. |
| 한 팀의 Task가 3개 이상이거나 나누는 데 도메인 판단이 필요 | 코디네이터가 팀장을 띄우고, 팀장이 팀원을 띄운다. |
| 요구사항이 흐릿한 큰 작업 | 설문부터 시작하는 전체 흐름을 탄다(`plan-orchestrate`). 코디네이터는 계획 승인 뒤에 뜬다. |

기준값 3은 실측값이다. 팀장 세션에는 고정 비용이 있어서 Task가 적으면 이득보다 비용이 크다.

## 하는 일과 하지 않는 일

| 하는 일 | 하지 않는 일 |
| --- | --- |
| Run과 Task 관리, 워커 기동, 대기, 리포트 판정, 장부와 백로그 상태 열 갱신, 끝 검증 1회, 커밋과 PR | 제품 파일 편집, 팀 스킬 로드, 워커 검사 재실행, 리포트 전문 읽기 |

코디네이터가 쓰는 파일은 세 가지뿐이다.

1. 작업 폴더의 Run 폴더 `_workspace/_run/<phase>/`(브리프, 장부, spec, Task 대응표 `orca-tasks.json`, 최종 보고)
2. `docs/backlog.md`의 상태 열
3. phase가 끝날 때 만드는 `docs/history/<phase>/` 사본

그 밖에 저장소에 하는 일은 승인 뒤의 커밋과 PR 한 번이다. 리뷰에서 나온 한 줄 수정도 워커 Task로 보낸다.

**팀 정보는 `docs/harness/team-org.md`만 읽는다.** 팀, 팀장이 되는 에이전트, 팀원, 팀 스킬 이름, 편집 범위가 그 표에 있다. 팀 스킬과 도메인 스킬은 로드하지 않는다. 그 스킬은 워커가 spec을 보고 로드한다.

## 통신

| 방향 | 명령 | 쓰는 때 |
| --- | --- | --- |
| 위에서 아래 | Task spec (기동할 때) | 일을 맡길 때 |
| 위에서 아래 | `send --to dispatch:<id>` | 진행 중인 워커에게 답이나 지시를 줄 때만. 범위 추가와 재작업은 새로 띄운다. |
| 아래에서 위 | `ask` | 막혔을 때. 답이 올 때까지 턴을 끝낸다. |
| 위에서 아래 | `reply` | `question`에 답할 때 |
| 아래에서 위 | `worker_done` | 완료 보고. 본문 세 문장, 수정한 파일 목록, 리포트 경로를 싣는다. |
| 코디네이터에서 창구 | `ask --wait` (백그라운드 작업) | 사용자에게 물을 것이 있을 때. 답은 그 명령의 출력으로 온다. |
| 창구에서 코디네이터 | `send --to run:<실행 Run>` (`status` 유형) | 대기 중인 코디네이터에게 사용자 지시를 전할 때 |

- 워커와 코디네이터는 사용자에게 직접 묻지 않는다. 코디네이터는 사용자에게 물을 것을 창구에 올리고, 창구가 사용자에게 묻는다. 로컬 질문 창은 창구가 볼 수 없으므로 쓰지 않는다.
- **코디네이터가 창구에 묻는 방법.** 실행 Run을 가진 코디네이터에게는 일반 `ask`의 답이 오지 않는다. 그래서 답을 기다리는 형태로 백그라운드에 건다: `orca orchestration ask --from <내 핸들> --question "<질문>" --wait --timeout-ms 1800000 --json`. 답은 이 명령의 출력(`answer`)으로 온다. 시간이 다 되면 질문은 살아 있으므로 `--question` 대신 `--resume <message id>`로 다시 건다. 그동안 워커의 보고는 평소대로 정산한다.
- **대기에는 `--run <실행 Run>`을 붙인다.** 워커의 보고와 창구의 지시가 실행 Run으로 들어온다.
- **대기 명령은 단독으로 건다.** 다른 명령과 한 줄에 묶지 않는다. 대기 작업이 끝났다는 알림을 받으면 그 출력을 끝까지 읽고, 들어 있는 메시지를 정산한 뒤에만 다시 건다. 대기가 가져간 메시지는 다시 오지 않는다. 올 보고가 안 오면 `orca orchestration inbox --terminal run:<실행 Run> --limit 20`으로 이미 가져간 메시지가 있는지 본다.
- 긴 본문은 파일에 쓰고 `"$(cat <파일>)"`로 넘긴다. 한글 인자를 파이프로 넘기면 깨질 수 있다.
- 범위 추가와 재작업은 `send`로 보태지 않고 새로 띄운다. 모델과 effort는 새 터미널을 띄울 때만 정해지므로, 보탠 일은 적용값을 입증할 수 없다.
- 코디네이터는 시작할 때 실행 Run을 따로 만든다(아래 워커 기동 1). 코디네이터가 띄우는 Task는 그 Run에 등록되고, 팀장과 팀원도 그 Run에 들어간다. 같은 Run 안에서도 보고는 띄운 쪽에게만 간다. 팀장은 `run-create`를 하지 않는다.

## 워커 기동

코디네이터가 띄우는 Task는 모두 Orca에 등록한 뒤 띄운다. 앞 Task가 끝났는지와 사용자 결정을 기다리는지는 Orca가 지킨다. 아래의 `<map>`은 `_workspace/_run/<phase>/orca-tasks.json`이다.

1. **실행 Run.** 시작할 때 한 번 돌리고, 나온 Run ID를 브리프의 `실행 Run` 칸에 적는다. Task를 등록하고 조회하는 일은 Run을 가진 쪽만 할 수 있다. Run을 만들 때 스크립트가 승인된 `waterfall.json`을 `waterfall.plan.json`으로 한 번 복사해 둔다(회고가 읽는 계획값이고, 이미 있으면 덮어쓰지 않는다).

   ```text
   node .claude/scripts/orca-launch.mjs exec-run --phase <phase> --map <map>
   ```

2. **등록.** 띄울 Task의 spec을 양식 `docs/harness/templates/spec.md`로 `_workspace/_run/<phase>/spec/`에 먼저 모두 쓴다. `배정:` 줄은 계획서의 배정을 그대로 옮긴다. 그다음 의존 순서대로 등록한다. 스크립트가 `배정:` 줄을 모델 표와 대조하고, 다르면 등록하지 않는다. 사용자가 다른 값을 지시했으면 spec에 `사용자 예외: <원문>` 줄을 넣고 `--override-reason "<원문>"`을 넘긴다.

   ```text
   node .claude/scripts/orca-launch.mjs register --map <map> --id <Task ID> --spec-file <spec> [--deps <앞 Task ID>,<앞 Task ID>] [--edits <경로>,<경로>] [--resource <gpu>,<blender>]
   ```

   - `--deps`에는 **그 Task가 실제로 읽는 산출물을 만드는 Task만** 건다. 계획서가 "앞 단계 전부 뒤"처럼 단계로 묶어 두었어도, 그 Task가 읽지 않는 Task는 걸지 않는다. 예: 월드 영역 QA는 월드 영역 구현 Task에만 의존하고, 상관없는 캐릭터 연결 Task를 기다리지 않는다. 혼자 써야 하는 자원을 쓰는 검증 Task는 구현 Task 전부에 건다. 합쳐진 코드가 그 Task의 입력이다.
   - `--edits`에는 계획서의 그 Task 편집 범위를, `--resource`에는 혼자 써야 하는 자원(GPU를 크게 쓰는 일은 `gpu`, Blender MCP는 `blender`)을 넘긴다. 아래 `launchable`이 이 둘로 겹침을 가른다.

3. **띄우기.** `launchable`이 돌려준 `launch` 목록을 그대로 띄운다. 이 명령은 Orca가 준비 상태로 둔 Task 가운데, 빈 슬롯 안에서, 지금 도는 Task와 편집 경로도 자원도 겹치지 않는 것만 고른다. 판단으로 고르지 않고 이 계산을 따른다.

   ```text
   node .claude/scripts/orca-launch.mjs launchable --map <map> --slots <브리프의 슬롯 수>
   node .claude/scripts/orca-launch.mjs worker --map <map> --id <Task ID> --bracket <백로그 ID 또는 phase 이름> --does <하는 일>
   ```

- **`launchable`은 깰 때마다 돌린다.** `worker_done`을 정산한 뒤, 질문에 답한 뒤, 대기가 시간 초과로 끝난 뒤에도 돌린다. 긴 Task 하나만 도는 동안에도 빈 슬롯이 메워진다. 웨이브를 기다리지 않는다.
- **`worker_done`을 정산할 때마다 대기 중인 Task를 당길 수 있는지 본다.** `held`의 사유(편집 겹침, 자원, 슬롯)는 장부의 `## 결정`에 적는다. `launchable`의 `candidates`는 대기 중인 Task마다 아직 안 끝난 앞 Task(`waitingOn`)와 spec의 `먼저 읽을 것`(`reads`)을 보여 준다. 빈 슬롯이 있고, `reads`가 `waitingOn` Task의 산출물(그 Task의 편집 범위나 리포트)을 하나도 읽지 않으면, 실제 입력만 의존으로 남겨 당긴다: `node .claude/scripts/orca-launch.mjs pull --map <map> --id <Task ID> --deps <실제 입력 Task,…> --reason "<이유>"`. 실제 입력이 모두 끝났을 때만 준비 상태가 되고, 아니면 `waitingOn`을 돌려주고 아무것도 바꾸지 않는다. 당긴 뒤 `launchable`을 다시 돌린다(편집 겹침과 자원은 거기서 걸러진다). 검증·리뷰 Task는 바로 당기고(혼자 써야 하는 자원을 쓰는 검증 Task는 당기지 않는다), 구현 Task를 계획과 다른 순서로 당길 때는 창구에 `ask`로 올린다. 당긴 것은 장부에 적는다. 판단은 `candidates`의 줄만으로 하고 spec 전체를 다시 읽지 않는다.
- **준비된 Task를 남긴 채 대기를 걸지 않는다.** 대기를 걸기 직전에 `launchable`을 돌려 `launch`가 비었는지 본다.
- **Orca가 기동을 거부하면 그대로 둔다.** 앞 Task가 안 끝났거나 결정을 기다리는 Task는 `기동 거부`가 나온다. `task-update`로 상태를 바꿔서 띄우지 않고, `orca orchestration worker-start`를 직접 부르지 않는다.
- **폭은 계획과 `launchable`이 정한다.** 계획에 없는 Task를 즉석에서 만들지 않는다. 계획에 있는 Task의 순서는 위 규칙대로 실제 입력에 맞춰 당길 수 있다. 동시 워커 수는 브리프의 슬롯 수를, 한 팀의 동시 워커는 4명 이하를 지킨다.
- **팀장.** 한 팀의 Task가 3개 이상이거나 나누는 데 도메인 판단이 필요하면 팀장을 띄운다. 그 팀의 Task들은 팀 spec 하나로 묶어 Task 하나로 등록하고(`register`에 `--lead`), 팀 사이의 의존은 이 팀 Task끼리 건다. 팀 안의 순서는 팀장이 지킨다. 명단의 "팀장이 되는 에이전트"로, spec 첫 줄을 `[역할: <에이전트> · 리드]`로 쓴다. 팀장 spec의 배정 줄은 계획서의 팀원 배정이 아니라 `배정: <에이전트> / 리드 (<모델 표의 `리드` 줄 값>)`이다. 팀장에게는 팀 spec 하나를 주고 통합 보고 하나를 받는다.
- **그림.** `ready`가 돌려준 상태가 바뀔 때마다 `dag-swimlane`으로 스윔레인을 **같은 파일 경로로** 다시 게시한다. 사용자는 같은 주소에서 진행을 본다. 상태는 `ready`의 `status`에서 가져오고 기억으로 적지 않는다(`completed`는 완료, `dispatched`는 진행, 그 밖은 대기).
- 기동 영수증의 적용값을 장부에 적는다. 요청한 값만 보고 적지 않는다([settle.md](references/settle.md)).

## 결정 대기

사용자 결정이 나야 시작할 수 있는 Task에는 게이트를 건다.

```text
node .claude/scripts/orca-launch.mjs gate --map <map> --id <Task ID> --question "<질문>"
node .claude/scripts/orca-launch.mjs resolve --map <map> --id <Task ID> --resolution "<답>"
```

`gate`로 막은 뒤 같은 질문을 `ask --wait`로 창구에 올린다. 답이 오면 원문을 장부의 `## 결정`과 그 Task의 메모(`spec/<Task ID>.memo.md`)에 적고 `resolve`로 푼다. 등록된 spec은 바꿀 수 없어서 결정은 메모로만 워커에게 간다. `orca orchestration gate-resolve`를 직접 부르지 않는다. Orca는 게이트가 풀리면 앞 Task가 안 끝났어도 그 Task를 준비 상태로 만들기 때문에, `resolve`가 의존을 확인해 다시 묶는다.

## phase의 단계

코디네이터는 계획 승인 뒤의 4~8단계를 맡는다. 1~3단계(설문, 설계, 계획)는 창구가 `plan-orchestrate`로 한다.

| 단계 | 코디네이터가 하는 것 |
| --- | --- |
| 4 백로그 반영 | `product-manager` 워커 Task로 띄운다. 계획의 Task를 백로그 항목에 연결한다. |
| 5 실행 | 기동, 정산, 중간 리뷰, 끝 검증, 수정 루프, 최종 테스트 |
| 6 완료 처리 | `product-manager` 워커 Task로 띄운다. 백로그를 정리한다. |
| 7 하네스 회고 | `harness-engineer` 워커 Task로 띄운다. 생략하지 않는다. 고칠 근거가 없으면 측정 결과와 "변경 없음"만 남긴다. |
| 8 커밋과 PR | 창구를 거쳐 사용자 승인을 받은 뒤 한 번에 한다. |

- 4, 6, 7단계의 Task도 같은 방식으로 등록해 띄운다.
- 7단계를 띄우기 전에 실제 시각을 남긴다. 회고가 이 파일로 실제값을 잰다: `node .claude/scripts/orca-launch.mjs actual --map <map> > _workspace/_run/<phase>/actual.json`

건너뛰기: 백로그 항목과 수락 기준이 이미 있으면 4단계를 생략한다.

## 정산

`worker_done`마다 네 가지를 본다. 기대한 Dispatch인가, 리포트 파일이 있는가, 계획서가 적은 그 Task의 산출물이 실제로 있는가, 리포트의 검증 절이 통과하는가. 뒤의 둘은 한 명령으로 본다: `node .claude/scripts/report-check.mjs <리포트 경로> --expect <산출물 경로>`. 하나라도 아니면 본문이 성공이어도 실패로 처리한다. 워커의 검사를 다시 돌리지 않고 리포트 전문을 읽지 않는다.

- **실패로 처리할 때는 `fail` 명령을 돌린다.** `node .claude/scripts/orca-launch.mjs fail --map <map> --id <Task ID> --cause "<원인>"`. Orca는 워커의 성공 보고만으로 그 Task를 끝난 것으로 치고 뒤 Task를 준비 상태로 올린다. 이 명령이 그 Task를 실패로 되돌리고 뒤 Task를 다시 묶는다. 그래서 정산을 끝낸 뒤에 `ready`를 본다.
- 질문을 올린 워커에게는 `send`가 아니라 `reply`로 먼저 답한다.
- `stopReason: "finished"`인 `escalation`("Worker stopped without reporting")은 워커가 답을 기다리는 중일 수 있다. 화면을 확인하기 전에는 재기동하지 않는다.
- 기동 스크립트가 턴 시작을 확인하지 못해도 자동으로 멈추거나 다시 띄우지 않는다. 화면에서 확인한 뒤에만 복구한다.

세부(장부 형식, 실패 처리, 적용값, 백로그 상태 열)는 [settle.md](references/settle.md)에 있다.

## 검증과 수정 루프

**배치.** 검증은 Orca 워커로 띄운다(검증 팀 `team-qa`).

- 중간에는 코드 리뷰만 돌린다. 뒤 Task가 그 위에 쌓이는 묶음이 끝났을 때 돌려, 다음 Task가 결함 위에 쌓이지 않게 한다. 프로젝트에 디자인 리뷰 팀이 있으면 함께 돌린다.
- QA는 DAG 끝에서 한 번 돌린다. 돈, 인증, 외부 쓰기를 건드리는 묶음만 예외로 그 흐름 하나에 좁혀 중간에 돌린다.
- 끝 리뷰는 합쳐진 코드에서 브라우저와 혼자 써야 하는 자원 없이 도는 검사(문법, 타입, 린트, 단위 테스트)를 먼저 한 번 돌린다(`change-review` 4단계). 이 확인에 따로 Task를 두지 않는다.
- 끝 검증이 서로 독립인 영역 둘 이상을 덮으면 QA를 처음부터 2~3명으로 나눈다. 바뀐 영역 묶음마다 한 명, 그리고 영역에 속하지 않는 항목을 보는 횡단 한 명이다. Task마다 결함 ID 접두어를 미리 배정한다.
- QA가 혼자 써야 하는 자원(GPU, Blender MCP 등)을 쓰면 그 QA는 나누지 않는다. 구현 Task가 모두 정산된 뒤에 Task 하나로 한 번 돌리고, 등록할 때 `--resource`를 붙인다. 여러 워커가 같이 쓰면 그 자원 하나를 두고 서로 막힌다. 구현 Task는 그 자원 없이 도는 간단한 코드 테스트로 끝낸다(spec 양식의 `완료 기준`).
- 끝 QA의 spec에는 계획서 `## DAG`의 의존 줄을 "대조할 경계면"으로 옮겨 적는다. 팀장에게 맡길 때는 팀 spec에 적는다.
- 같은 파일을 고치는 Task가 진행 중이면 그 파일의 리뷰는 편집이 끝난 뒤 한 번만 한다.

**수정 루프의 다섯 규칙.**

1. 고치는 것은 High 이상과 완료 기준 미달뿐이다. Medium 이하는 인박스로 보낸다.
2. 수정 Task의 spec에는 결함 ID마다 재현 테스트를 먼저 쓰고 테스트 이름에 그 결함 ID를 넣으라고 적는다. 재현 테스트를 쓸 수 없는 결함(화면을 봐야만 보이는 것 등)은 리포트에 그렇게 적게 한다.
3. 수정이 모두 정산되면 바로 최종 테스트를 돌린다(아래). 재현 테스트가 있는 결함은 여기서 확인된다. 재검은 재현 테스트가 없는 결함이 있을 때만 그 결함 ID로 띄우고, 최종 테스트 뒤에 띄운다. 재검은 그 결함 ID의 재현 확인만 하고, 새 탐색, 새 시나리오, 전체 테스트를 하지 않는다.
4. 루프는 최대 2회다. 남은 High는 그 루프의 최종 테스트에서 실패한 것 전부(재현 테스트와 다른 회귀)와, 재검을 띄웠으면 재검에서 열려 있는 High다. 재검 중에 새로 찾은 High도 여기에 든다. 2회 뒤에도 High가 남아 3회째가 필요해지면 멈추고 `ask --wait`로 사용자에게 묻는다. 남은 High 목록을 함께 싣고, 3회째를 돌릴지 인박스로 넘길지 답을 받는다. 답 없이 3회째를 띄우지 않는다. 사용자가 3회째를 승인하면 그 원문을 장부의 `## 결정`에 적고, 그 회차 재검 리포트의 판정에만 `--round-cap 3`을 붙인다.
5. 사용자의 "알아서 진행해"는 이 상한과 재검 범위를 늘리지 않는다. 위임은 사용자가 그렇게 하라고 명시한 것뿐이다. 사용자가 반대하지 않았다는 것, 코디네이터가 "한 줄만 고치면 된다"고 본 것은 위임이 아니다.

- 재검 중에 새로 찾은 결함이 High면 남은 High로 센다. 루프가 남아 있으면 다음 루프에서 고치고, 2회를 다 썼으면 4번대로 사용자에게 묻는다. Medium 이하는 인박스로 보낸다.
- 평가자와 생성자는 다른 에이전트다. 구현한 쪽이 자기 결과를 승인하지 않는다. 수정의 재현 테스트는 고친 워커가 아니라 코디네이터의 최종 테스트가 확인한다.

**최종 테스트.** 끝 검증에서 고칠 것이 없으면 그 뒤에, 수정 루프가 돌면 루프마다 수정이 모두 정산된 뒤에, 그때의 코드에서 전체 테스트를 코디네이터가 돌린다. 수정의 재현 테스트와 다른 워커가 깬 테스트를 여기서 잡는다. 마지막 최종 테스트가 통과해야 완료다. 못 돌렸으면 완료가 아니라 "테스트 미실행"으로 보고한다. 도구 한 번의 한도(10분)를 넘길 만한 테스트는 백그라운드 작업으로 돌리고, 끝났다는 알림을 받으면 그 출력을 끝까지 읽는다. 팀장의 팀 전체 검증이 지금과 같은 최종 코드 상태에서 돈 것이면 그 결과로 갈음한다.

## phase 끝

1. 최종 보고를 `_workspace/_run/<phase>/report.md`에 쓴다.
2. 최종 보고, 장부, 회고 리포트, DAG 입력 파일을 `docs/history/<phase>/`로 복사한다. 추적되는 문서는 `_workspace/` 경로를 근거로 가리키지 않는다. 작업 폴더는 지우지 않는다.
3. 커밋과 PR은 사용자 승인 뒤 한 번에 한다. 경로를 지정해 커밋한다. 경로 목록에 git이 모르는 경로(워커가 만들었다가 지운 미추적 파일 등)가 하나라도 있으면 `pathspec did not match`로 커밋 전체가 빠진다. 지운 것이 섞인 곳은 파일이 아니라 폴더 경로로 지정하고, 커밋 뒤 `git status --short`로 남은 것이 없는지 본다. 회고가 고친 하네스 파일은 같은 PR의 별도 커밋이다. 워커는 커밋하지 않는다.
4. 최종 보고 경로를 실어 `worker_done`을 보낸다.

**승인이 필요한 명령(push, PR 등)의 실행 주체.** 권한 질문이 실제로 뜨는 세션만 실행한다. 코디네이터가 그런 모드로 떠 있으면 코디네이터가 실행하고 사용자가 그 터미널에서 승인한다. 아니면 코디네이터는 커밋까지만 하고 push와 PR은 창구에 `ask --wait`로 넘긴다. 훅이 명령을 거부하며 `ask`로 올리라고 하면 같은 방법으로 올린다.

## 대기 계약 (생략·요약 금지)
대기 명령의 세부 인자는 `orca skills get orchestration`을 따른다. 아래 1~5는 그와 별개로 항상 지킨다. Codex는 1~5 대신 6을 지킨다.
1. 대기는 하네스가 추적하는 백그라운드 작업으로 건다(Claude Code: Bash `run_in_background: true`). 포그라운드 대기는
   도구 한도(최대 10분)에 끊기고, `Start-Process`·`nohup` 분리 실행은 끝나도 아무도 못 깨운다. stderr keepalive를 Monitor로 보지 않는다.
   결과는 stdout의 JSON만 읽고 `| head -c`로 자르지 않는다(keepalive 줄이 자를 몫을 다 먹어 본문이 사라진다 — 거르려면 `| grep -v _keepalive`).
   **한 세션에 `check --wait`는 동시에 하나** — 앞 대기의 깨우기를 받은 뒤에만 다시 걸고, 추적을 잃은 앞 대기는 먼저 멈춘다.
2. 깨우는 조건에서 heartbeat를 뺀다: `orca orchestration check --wait --types "worker_done,escalation,question,status" --timeout-ms 1800000 --json`.
   heartbeat를 빼도 타임아웃마다 1회는 깨므로 짧게 잡으면 빈 깨움만 는다.
   `status`는 빼지 않는다 — 사용자 지시가 대기 중인 코디네이터에게 전달되는 통로다(빼면 사용자 지시를 놓친다).
3. 깨면 돌려받은 묶음 전체를 처리한다. `--types`는 깨우는 조건일 뿐 묶음에는 heartbeat도 섞여 온다. 소비하는 `check`가
   묶음을 처리됨으로 표시하므로 `--ack`는 붙이지 않는다(그 표시를 하지 않는 구버전 Orca 전용 옵션이다).
   이미 처리한 message id는 다시 정산하지 않는다 — `"replayed": true` 묶음(heartbeat뿐인 묶음의 재배달, 또는 겹쳐 건 대기가
   거부 없이 받은 같은 `worker_done`)이 그 경우다. 같은 Dispatch의 `worker_done`이 id만 다르게 수 초 간격으로 두 번 오면 워커
   재전송이다 — 첫 것으로만 정산한다. 소비하는 `check`는 대기를 건 쪽 본인만 실행한다(서브에이전트는 쓰지 않는다).
4. 묶음에 heartbeat만 있으면 사용자에게 보고하지 않고 말없이 대기를 다시 건다.
   "You have N orchestration messages" 알림도 같다 — 추적 중인 대기가 있으면 도구 호출 없이 턴을 끝낸다.
5. 타임아웃은 실패가 아니다. 다시 걸기 전에 `orca orchestration inbox --terminal <내 수신함> --limit 5`로 최근 5개만 한 번 보고,
   아직 정산하지 않은 message id가 있으면 정산한 뒤 다시 건다(가져갔는데 읽지 못한 메시지는 여기에만 남는다).
   `<내 수신함>`은 Run을 가진 쪽은 `run:<Run ID>`, Run이 없는 팀장은 `dispatch:<자기 Dispatch ID>`다.
   연속 3번 빈 대기면 `worker-list`로 워커 생존을 본다. 침묵·타임아웃·목록 부재만으로 종료로 판정하거나 재기동하지 않는다.
   heartbeat는 워커가 보내는 것이지 코디네이터가 보내거나 답할 것이 아니다.
6. Codex는 `check --wait`를 걸지 않는다. 끝난 백그라운드 명령은 Codex를 깨우지 못하고, 대기가 가져간 메시지에는 Orca 알림도 오지 않아
   메시지가 묻힌다. 할 일을 마치면 턴을 끝낸다. "You have N orchestration message" 알림이 오면 알림이 적어 준 `check` 명령을 그대로 한 번 돌려
   묶음 전체를 3대로 처리한다. 사용자 지시도 이 알림으로 온다. 그 `check`가 비어 있으면 5의 `inbox --limit 5`를 한 번 본다.
