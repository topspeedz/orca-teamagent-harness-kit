# 정산의 세부

> 읽는 시점: 대기에서 깨어 묶음을 처리할 때. 처음 한 번 읽고, 장부 형식이 헷갈릴 때 다시 연다.

## 1. 묶음 처리

깨면 받은 묶음 전체를 메시지 유형별로 처리한다. 이미 처리한 message id는 다시 정산하지 않는다.

| 유형 | 처리 |
| --- | --- |
| `question` | `send`가 아니라 `reply --id <message id>`로 먼저 답한다. 코디네이터가 모르는 것은 `ask --wait`로 창구에 올리고(`SKILL.md`의 통신), 그 답으로 `reply`한다. 장부의 질문 열을 1 올린다. 답한 뒤 다음 깸에서 `unhandled` 명령으로 그 답이 처리됐는지 본다(`SKILL.md`의 정산). |
| `worker_done` | 2절의 세 가지를 확인한다. |
| `escalation` | `stopReason: "finished"`("Worker stopped without reporting")이면 워커가 답을 기다리는 중일 수 있다. 화면을 확인하기 전에는 재기동하지 않는다. 그 밖은 코디네이터가 풀 수 있는 것(경로, 환경 안내)은 풀어 `send --to dispatch:<id>`로 알리고, 아니면 `ask --wait`로 올린다. |
| `status` | 창구가 전한 사용자 지시다. 실행 Run으로 온다. 장부의 `## 결정`에 원문을 적고 따른다. |
| heartbeat만 | 보고 없이 다시 대기를 건다. |

## 2. worker_done의 네 가지 확인

1. **기대한 Dispatch인가.** 장부에 적은 그 Task의 Dispatch ID와 같아야 한다. 같은 Dispatch의 `worker_done`이 id만 다르게 두 번 오면 첫 것으로만 정산한다.
2. **리포트 파일이 있는가.** `worker_done`에 실린 리포트 경로의 파일이 실제로 있어야 한다.
3. **계획서가 적은 산출물이 있는가.** 리포트의 ✅는 워커가 스스로 적은 것이고, 만들지 않은 파일은 git에도 흔적이 남지 않는다. 아래 명령에 `--expect <산출물 경로>`를 붙여 함께 본다. 산출물이 여럿이면 `--expect`를 그만큼 붙인다. 팀장에게 준 팀 Task는 통합 보고가 산출물이므로 붙이지 않는다.
4. **`node .claude/scripts/report-check.mjs <리포트 경로> --expect <산출물 경로>`가 코드 0인가.** 표준 출력의 JSON 한 줄만 읽는다. `failed` 줄은 장부의 재시도(원인) 열로, `notes`(`(참고)` 줄)는 최종 보고의 남은 것으로 옮긴다.

하나라도 아니면 본문이 성공이어도 실패로 처리한다. 코디네이터는 리포트 전문을 읽지 않고, 워커의 검사를 다시 돌리지 않는다.

## 3. 장부

phase마다 `_workspace/_run/<phase>/ledger.md` 하나를 양식 `docs/harness/templates/ledger.md`로 쓴다.

- 예산 줄: 구현 Task 수, 검증 Task 수, 수정 루프의 현재 횟수(최대 2).
- 표는 하나만 둔다. 열은 `Task | 에이전트 | 배정(요청과 적용) | 재시도(원인) | 질문 | 리포트 경로`다.
- 산문과 결정은 표 밖의 `## 결정` 절에 쓴다. 표 사이에 산문을 끼우지 않는다.
- **Task의 상태는 장부에 적지 않는다.** Orca가 기준이고 `ready` 명령의 `status`로 본다. 결정을 기다리는 Task는 게이트로 막는다(`SKILL.md`의 결정 대기).
- 리포트 경로 열은 항상 가장 최신 버전(`_v<N>.md`)을 가리킨다.
- 스윔레인과 워터폴의 상태도 `ready`의 `status`에서 가져온다.
- 수정 루프를 돌릴 때마다 예산 줄의 `수정 루프 <N>회`를 1 올린다.
- 실제 시각은 손으로 적지 않는다. 7단계를 띄우기 전에 `actual` 명령이 Orca의 기록으로 `actual.json`을 쓴다(`SKILL.md`의 phase의 단계). 회고(`harness-retro`)가 이 파일로 실제값을 잰다.

## 4. 적용값을 장부에 적기

- 기동 영수증의 `requested`와 `applied`를 배정 열에 함께 적는다. 예: `요청 claude opus/medium · 적용 opus/medium`. 요청한 값만 보고 적지 않는다.
- 영수증의 `matched`가 거짓이거나 적용값이 비어 있으면 그대로 적고 최종 보고에 남긴다.
- 코디네이터 자신의 적용값은 기동 줄에 넣은 model과 effort다. 미리 만든 터미널에 Task를 배정하면 영수증에 적용값이 없기 때문이다.
- `사용자 예외:`로 띄운 Task는 그 원문을 `## 결정`에 적는다.

## 5. 실패 처리

| 상황 | 처리 |
| --- | --- |
| 네 가지 확인 중 하나가 아니다, 또는 `--outcome failed` | `fail` 명령을 돌리고 원인을 장부의 재시도 열에 적는다. 같은 원인을 그 Task의 메모(spec 옆의 `<Task ID>.memo.md`)에 적은 뒤 **같은 Task를** 1회 다시 띄운다: `node .claude/scripts/orca-launch.mjs worker --map <map> --id <Task ID> --bracket <…> --does <…> --retry`. Orca에 등록된 spec은 바꿀 수 없으므로 원인은 메모로만 전한다. 그래도 실패하면 그 Task 없이 진행할 수 있는지 보고 `ask --wait`로 사용자에게 올린다. |
| 팀장의 통합 보고가 실패 | 위와 같은 방법으로 처리한다. 메모에는 통합 보고의 미달 Task만 적는다. 다시 뜬 팀장은 그것만 한다. |
| 기동 영수증의 `turnStarted: false` | 자동으로 멈추거나 다시 띄우지 않는다. 화면에서 턴이 시작되지 않은 것을 확인한 뒤에만 사람이 복구한다. 화면에서 본 상태별 복구(둘 다 같은 Dispatch이고 재기동이 아니다): 지시가 입력창에 붙은 채 제출되지 않았으면 Enter를 1회 보낸다. 입력창이 비어 대기 중이면 spec 경로, Task ID와 Dispatch ID, `worker_done` 명령을 다시 입력한다. 장부에 그 상태를 적는다. |
| 등록이 배정 불일치로 거부 | spec의 `배정:` 줄을 계획서와 모델 표에 맞게 고친다. 팀장(`--lead`)이면 배정 줄의 작업 단위가 `리드`이고 값이 표의 `리드` 줄과 같은지 본다. 표에 맞는 작업 단위가 없으면 정하지 않고 `ask --wait`로 올린다. |
| 같은 워커에게 일을 더해야 한다 | `send`로 보태지 않고 새 Task를 등록해 띄운다. |
| `기동 거부`가 나온다 | 앞 Task가 안 끝났거나 게이트가 걸려 있다. `unmet`에 적힌 Task를 기다린다. 상태를 손으로 바꾸지 않는다. |

## 6. 백로그 상태 열

- 코디네이터는 `docs/backlog.md`의 **상태 열만** 고친다. 해당 줄을 ID(`BL-####`)로 찾아 그 줄의 상태 칸만 바꾼다. 값은 `todo`, `doing`, `blocked`, `done`이다.
- 항목의 내용, 수락 기준, 인박스, 보관 파일, 파일 구조는 `product-manager`의 몫이다. 코디네이터가 고치지 않는다.
- 코드를 바꾼 항목은 최종 테스트 1회가 통과해야 `done`이다. 못 돌렸으면 `doing`으로 두고 최종 보고에 "테스트 미실행"을 적는다.
- 검증에서 나온 Medium 이하 결함은 코디네이터가 모으지 않는다. 검증 리포트의 경로만 6단계 기획 Task의 spec에 넘기고, 기획이 그 리포트의 `## 인박스 후보`를 읽어 인박스에 한 줄씩 넣는다.
