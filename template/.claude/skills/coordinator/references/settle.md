# 정산의 세부

> 읽는 시점: 대기에서 깨어 묶음을 처리할 때. 처음 한 번 읽고, 장부 형식이 헷갈릴 때 다시 연다.

## 1. 묶음 처리

대기가 돌려준 `messages`를 유형별로 모두 처리한다. heartbeat와 이미 넘겨준 메시지는 대기 명령이 걸러서 오지 않는다.

| 유형 | 처리 |
| --- | --- |
| `question` | `send`가 아니라 `reply --id <message id>`로 먼저 답한다. 코디네이터가 모르는 것은 `ask --wait`로 창구에 올리고(`SKILL.md`의 통신), 그 답으로 `reply`한다. 장부의 질문 열을 1 올린다. |
| `worker_done` | 2절의 `settle` 한 명령으로 정산한다. |
| `escalation` | `stopReason: "finished"`("Worker stopped without reporting")이면 워커가 답을 기다리는 중일 수 있다. 화면을 확인하기 전에는 재기동하지 않는다. 그 밖은 코디네이터가 풀 수 있는 것(경로, 환경 안내)은 풀어 `send --to dispatch:<id>`로 알리고, 아니면 `ask --wait`로 올린다. |
| `status` | 창구가 전한 사용자 지시다. 실행 Run으로 온다. 장부의 `## 결정`에 원문을 적고 따른다. |

## 2. worker_done의 네 가지 확인

`node .claude/scripts/orca-launch.mjs settle …`(`SKILL.md`의 정산)이 네 가지를 보고 표준 출력에 JSON 한 줄을 낸다. 그 줄만 읽는다.

1. **기대한 Dispatch인가.** Task 대응표에 적힌 그 Task의 Dispatch ID와 같아야 한다. 다르면 아무것도 바꾸지 않고 `기대한 Dispatch가 아님`으로 끝난다.
2. **리포트 파일이 있는가.** `worker_done`에 실린 리포트 경로의 파일이 실제로 있어야 한다.
3. **계획서가 적은 산출물이 있는가.** 리포트의 ✅는 워커가 스스로 적은 것이고, 만들지 않은 파일은 git에도 흔적이 남지 않는다. 산출물이 여럿이면 `--expect`에 쉼표로 잇는다.
4. **리포트의 검증 절이 통과하는가.** `failed` 줄은 장부의 재시도(원인) 열로, `notes`(`(참고)` 줄)는 최종 보고의 남은 것으로 옮긴다.

하나라도 아니면 본문이 성공이어도 실패다. 명령이 그 Task를 실패로 되돌리고 뒤 Task를 다시 묶는다. 영향 미확인 항목은 해당 리포트의 `## 남은 것`에서 다음 확인 방법과 원본 경로를 끝 QA 또는 최종 보고에 옮긴다. High의 증거·영향 근거가 비어 정산에 실패하면 원래 결과를 보존하고 보고서의 분류만 보완한다. 이때 제품 수정이나 테스트 재실행은 필요하지 않다.

## 3. 장부

phase마다 `_workspace/_run/<phase>/ledger.md` 하나를 양식 `docs/harness/templates/ledger.md`로 쓴다.

- 예산 줄: 구현 Task 수, 검증 Task 수. 수정 라운드는 손으로 세지 않는다. `defect-ledger.mjs`가 수정 Task를 띄운 라운드의 수를 센다.
- 기동 장부의 열은 `Task | 에이전트 | 배정(요청과 적용) | 재시도(원인) | 질문 | 리포트 경로`다.
- 산문과 결정은 표 밖의 `## 결정` 절에 쓴다. 표 사이에 산문을 끼우지 않는다.
- **Task의 상태는 장부에 적지 않는다.** Orca가 기준이고 `ready` 명령의 `status`로 본다. 결정을 기다리는 Task는 게이트로 막는다(`SKILL.md`의 결정 대기).
- 리포트 경로 열은 항상 가장 최신 버전(`_v<N>.md`)을 가리킨다.
- 스윔레인과 워터폴의 상태도 `ready`의 `status`에서 가져온다.
- `## 결함 원장`은 `defect-ledger.mjs add`가 쓴다. 코디네이터는 상태 칸만 고친다. 값은 양식 `ledger.md`를 따른다.
- 실제 시각은 손으로 적지 않는다. 7단계를 띄우기 전에 `actual` 명령이 Orca의 기록으로 `actual.json`을 쓴다(`SKILL.md`의 phase의 단계). 회고(`harness-retro`)가 이 파일로 실제값을 잰다.

## 4. 적용값을 장부에 적기

- 기동 영수증의 `requested`와 `applied`를 배정 열에 함께 적는다. 자동 재평가로 배정이 달라졌으면 계획값과 최종값, 바뀐 축과 사유도 남긴다.
- 영수증의 `matched`가 거짓이거나 적용값이 비어 있으면 그대로 적고 최종 보고에 남긴다.
- 코디네이터 자신의 적용값은 기동 줄에 넣은 model과 effort다. 미리 만든 터미널에 Task를 배정하면 영수증에 적용값이 없기 때문이다.
- `사용자 예외:`로 띄운 Task는 그 원문을 `## 결정`에 적는다.

## 5. 실패 처리

자동 위임한 Task의 재시도는 `--retry --assessment <새 시도의 평가.json>`으로 기동한다. 같은 범위의 실제 판단·수행 실패를 확인했으면 `failureDispatches`에 해당 Dispatch ID를 명시하고 `input.scores.F`에 누적 확정 건수(상한 2)를 적는다. 의도된 RED, 미기동, 장비·권한 부재는 제외한다. 같은 Dispatch는 한 번만 센다. 직접 지정과 구 승인에는 승인값을 사용한다.

| 상황 | 처리 |
| --- | --- |
| 네 가지 확인 중 하나가 아니다, 또는 `--outcome failed` | `settle`이 이미 그 Task를 실패로 되돌렸다. 출력의 `cause`를 장부의 재시도 열에 적는다. 같은 원인을 그 Task의 메모(spec 옆의 `<Task ID>.memo.md`)에 적은 뒤 **같은 Task를** 1회 다시 띄운다: `node .claude/scripts/orca-launch.mjs worker --map <map> --id <Task ID> --bracket <…> --does <…> --retry`. Orca에 등록된 spec은 바꿀 수 없으므로 원인은 메모로만 전한다. 그래도 실패하면 그 Task 없이 진행할 수 있는지 보고 `ask --wait`로 사용자에게 올린다. |
| 검증 Task가 실패로 정산됐지만 산출물이 있고 뒤 Task의 실제 입력이 갖춰졌다 | `pull`로 실제 입력만 의존으로 남기고(`SKILL.md`의 워커 기동) 사유를 장부 `## 결정`에 적고 진행한다. |
| 기동 영수증의 `turnStarted: false` | 자동으로 멈추거나 다시 띄우지 않는다. 화면에서 턴이 시작되지 않은 것을 확인한 뒤에만 사람이 복구한다. 장부에 그 상태를 적는다. |
| 등록이 배정 불일치로 거부 | 계획 Task ID와 승인 버전, 역할·단위·실제 spec을 대조한다. 승인값을 쓸 수 없으면 창구에 올린다. 현재 표를 소급 적용하지 않는다. |
| 같은 워커에게 일을 더해야 한다 | `send`로 보태지 않고 새 Task를 등록해 띄운다. |
| `기동 거부`가 나온다 | 앞 Task가 안 끝났거나 게이트가 걸려 있다. `unmet`에 적힌 Task를 기다린다. 상태를 손으로 바꾸지 않는다. |

## 6. 백로그 상태 열

- 코디네이터는 `docs/backlog.md`의 **상태 열만** 고친다. 해당 줄을 ID(`BL-####`)로 찾아 그 줄의 상태 칸만 바꾼다. 값은 `todo`, `doing`, `blocked`, `done`이다.
- 항목의 내용, 수락 기준, 인박스, 보관 파일, 파일 구조는 `product-manager`의 몫이다. 코디네이터가 고치지 않는다.
- 코드 변경은 마지막 최종 테스트와 필수 문서 확인을 모두 마쳐야 `done`이다. 미실행 테스트는 `doing`이다. 이력만 남긴 Task는 완료 기준을 충족한 리포트로 끝낼 수 있다. 필수 라이브 문서가 하나도 없는 phase는 장부에 `필수 라이브 문서: 없음`을 적는다.
- 계획·브리프와 QA 리포트에서 영향받은 모든 (BL, 정본, 절·ID)를 장부에 한 행씩 적는다. 백로그 없는 작업은 BL 칸에 `없음`을 적고 상태 열을 건드리지 않는다. 근거 칸에 발견 리포트와 반영을 확인한 리포트의 프로젝트 상대 경로를 각각 백틱으로 감싼다. 같은 리포트에서 양쪽을 추적할 수 있으면 한 번만 적는다. doc-steward의 확인에서 지정 작성자와 실제 정본의 해당 절, 대조한 근거를 찾을 수 있어야 한다. 인계만 끝났거나 담당자가 없으면 반영 대기다.
- 필수 절을 이월할 때는 창구가 해당 BL·문서·절·담당(없으면 미배정)·사유를 사용자에게 묻는다. 그 범위에 동의한 실제 답을 받은 뒤, 코디네이터는 표와 `## 결정`에 원문을 기록한다. 결정의 한 줄 형식은 `- BL-0001 | docs/05-api/orders.md | API-001 | 이월 승인 | 다음 phase에서 반영해 주세요.`다. 답변에 파이프가 있으면 표에서만 `\|`로 적는다. 각 줄은 해당 절에만 적용한다. 재시도 소진·답변 대기·거절을 승인으로 기록하지 않는다.
- 프로젝트 루트에서 `node .claude/scripts/phase-documents.mjs <장부 경로>`를 실행한다. 코드 1이면 phase를 열어 둔다. 코드 0이면 PM이 최종 QA와 대조해 완료 항목을 보관하고, `deferred` BL은 남은 문서·절·담당·사유와 함께 활성 백로그에 미완료로 남긴다. 한 BL에 이월한 절이 하나라도 있으면 다른 절을 확인했어도 보관하지 않는다. 정산 뒤 회고 조건이 맞으면 독립 harness-engineer의 회고를 받아 마감하고, 아니면 회고 Task를 `skip`하고 마감한다.
- 검증에서 나온 Medium 이하 결함은 코디네이터가 모으지 않는다. 검증 리포트와 문서 동기화 리포트의 경로만 6단계 기획 Task의 spec에 넘기고, 기획이 그 리포트들의 `## 인박스 후보`를 읽어 인박스에 한 줄씩 넣는다.
