# docs-management

제품의 지금 상태를 담는 live 문서의 정본 규칙이다. 워커가 남기는 리포트, 설계서, 계획서, phase 사본은 그때의 기록이고, 지금 상태는 `docs/`에 둔다. 역할 정의에 지정된 작성자가 해당 문서·절을 처음 쓰고 갱신한다. `doc-steward`는 색인을 관리하고, 구현·테스트 근거와 문서의 정합성을 확인해 발견한 결함을 지정 작성자에게 넘긴다.

모든 에이전트가 자기 문서를 쓸 때 이 파일을 읽는다. 만든 에이전트가 제품의 사실을 바꾸면 같은 Task에서 자기 문서를 고친다. 그 지식이 그 컨텍스트에 있으므로 다른 역할에 넘겨 나중에 쓰게 하지 않는다. 이때는 아래 규칙, 양식, 담당, ID와 상태 값을 따르고, 작업 단위별 절차 파일과 `## 리포트`·`## 오류 처리`·`## 하지 않는 것`은 `doc-steward`의 문서 Task에 적용된다.

성공 기준은 하나다. 다른 에이전트가 이 문서만 읽고 정확하게 구현하고 검증할 수 있다. 문서를 많이 쓰는 것은 기준이 아니다.

## 어느 일이면 어느 파일을 읽는다

어느 일인지는 spec의 `배정` 줄에 적힌 작업 단위로 안다. 이 파일을 읽은 뒤 아래 표의 파일만 읽는다. 나머지 절차 파일과 쓰지 않는 양식은 읽지 않는다.

| 작업 단위 | 하는 일 | 읽는 파일 |
| --- | --- | --- |
| `문서 초기화` | 기존 정본·초안과 담당자를 확인하고 근거를 작성자에게 넘긴다. 사용자가 요청할 때만 한다 | [references/init.md](references/init.md), [references/audit.md](references/audit.md), 쓸 문서의 양식 |
| `문서 동기화` | 변경 근거를 담당 절과 대조하고 지정 작성자의 반영 또는 현행 확인을 추적한다. 장부의 `## 라이브 문서 확인`에 행이 있을 때 한다. 없으면 코디네이터가 `skip`으로 닫는다 | [references/sync.md](references/sync.md), [references/audit.md](references/audit.md), 고칠 문서의 양식 |
| `문서 감사` | 문서 전체를 점검표로 본다. 사용자가 요청할 때만 한다 | [references/audit.md](references/audit.md), 점검할 문서의 양식 |

## 일곱 규칙

1. **정본 하나.** 같은 사실은 한 문서에만 쓰고 다른 문서는 ID나 경로로 가리킨다(아래 정본 표).
2. **양방향 추적.** 요구사항 ID, 화면 기능 ID, 계약 ID, 코드, 테스트 ID를 추적표로 잇는다. 요구사항에서 테스트로, 테스트에서 요구사항으로 둘 다 따라갈 수 있어야 한다.
3. **영향 분석 먼저.** 바뀐 파일에서 영향 받는 문서를 먼저 찾고, 그 문서만 연다.
4. **근거.** 코드에서 확인한 사실과, 정해지지 않았거나 확인하지 못한 것을 상태 값으로 구분한다. 확인하지 못한 것을 구현된 사실처럼 적지 않는다.
5. **바뀐 곳만.** 문서 전체를 다시 쓰지 않고 해당 절만 고친다.
6. **점검.** 일을 끝내기 전에 문서 사이의 모순, 누락, 끊긴 참조를 점검표로 본다.
7. **사람 승인.** 요구사항, 우선순위, 아키텍처 결정을 정하지 않는다. 승인된 것만 옮기고, 결정이 필요한 것은 올린다.

- setup은 위 양식에서 코드 지도와 12개 번호 폴더의 설치 초안을 만든다. 처음 작성할 때 기존 정본이 있으면 그 파일을 쓰고, 없으면 초안에 근거를 채우고 머리의 `설치 초안` 표시를 지운다. API·DB 계약, ADR, 런북은 각 폴더의 `draft.md`를 위 표의 실제 이름으로 저장한다. 설치 초안만 있는 줄의 정본과 상태는 `없음`이다. 사실을 채우는 일은 해당 문서·절의 지정 작성자가 맡는다.
- 이 프로젝트에 없는 영역(예: 화면이 없는 도구의 `docs/03-ui-ux/`)은 색인에 `해당 없음`으로 적고 만들지 않는다.
- 다른 경로에 이미 문서가 있으면 옮기거나 지우지 않는다. 색인의 정본 문서 칸에 그 경로를 적는다. 번호 폴더로 옮길지는 사용자 결정이므로 리포트의 `## 인박스 후보`에 한 줄로 올린다.
- 문서의 머리에는 `docs/harness/templates/live-doc.md`에 따라 읽는 시점, 역할과 소유 범위, 문서·절별 지정 작성자, 마지막으로 갱신한 phase를 적는다. 양식에서 별도 머리 표를 지정하면 그 형식을 따른다.
- 문서·절마다 담당 에이전트는 아래 담당 표와 역할 파일의 `## 문서 책임` 표를 따른다. 미배정 절은 근거를 리포트에 남기고 코디네이터를 통해 담당 지정을 요청한다. 색인의 배정 대기 표에서 미배정과 해당 없음을 구분한다.
- 30KB를 넘는 문서는 주제별로 나눈다. 원래 파일에는 나눈 파일을 가리키는 표를 남긴다. 예: 화면이 많으면 `docs/03-ui-ux/screens/<화면 ID>.md`.
- `docs/` 안에서 이 역할의 것이 아닌 곳은 고치지 않고 가리키기만 한다: `docs/backlog.md`와 `docs/backlog-archive.md`(기획), `docs/harness/`(하네스), `docs/superpowers/`(`product-manager`의 설계서와 계획서), `docs/history/`(코디네이터의 phase 사본).

## 문서 담당

문서마다 그 지식을 가진 에이전트가 담당이다. 기본 배정은 아래 표이고, 문서·절의 범위는 각 역할 파일의 `## 문서 책임` 표가 정본이다. 프로젝트가 에이전트나 스킬을 더하면 `agent-author`가 문서 담당도 함께 등록한다. 담당이 없는 문서는 색인의 `작성자 배정 대기`에 남는다.

| 문서 | 담당 |
| --- | --- |
| PRD, SRS, 백로그, WBS, 제품·범위 결정 기록 | `product-manager` |
| UI 명세와 화면 문서 | `frontend` |
| 아키텍처 | `backend`(서버와 데이터 구조), `frontend`(화면 쪽 구조와 계약) |
| API와 데이터 계약, 코드 지도, 운영 절차 | `backend` |
| 테스트 케이스, 요구사항 추적표 | `verifier` |
| 하네스 변경 이력 | `harness-engineer` |
| 문서 색인, 문서 사이의 연결 | `doc-steward` |

- `doc-steward`는 전체를 본다. 코드, 테스트와 문서가 맞는지, 색인과 연결이 맞는지 확인하고 색인과 연결은 직접 고친다. 내용이 틀렸으면 담당 에이전트에게 돌려보낸다.

## ID와 상태 값

- ID의 번호는 세 자리다(`FR-001`). ADR만 네 자리다(`ADR-0001`). 테스트 케이스의 영역은 대문자 영어 낱말이다(`TC-CART-014`).
- 새 번호는 문서와 변경 이력에 나온 그 접두어의 최댓값 + 1이다. 이미 쓴 번호를 다른 뜻으로 다시 쓰지 않는다. 없어진 항목은 줄을 지우고 변경 이력의 `Removed`에 ID를 남긴다.
- ID는 정의하는 문서 한 곳에서만 정의한다. 다른 문서는 ID로 가리킨다.

요구사항의 상태는 추적표에만 적고, 값은 아래 넷 중 하나다. 다른 문서(SRS, UI 명세, 계약 문서)에서는 예외만 그 줄 끝에 표시한다: 아직 코드에 없는 줄은 `(계획됨)`, 이미 구현된 줄의 문장이 바뀔 예정이면 `(계획됨: 바뀜 — <새 문장>)`, 없어질 예정이면 `(계획됨: 삭제)`, 어긋난 줄은 `(확인 필요: 사유)`. 계획된 변경은 지정 작성자가 표시하고 구현 근거를 확인한 뒤 갱신한다.

| 값 | 뜻 | 옆에 적는 근거 |
| --- | --- | --- |
| `계획됨` | 지정 작성자가 실행 전에 쓴 줄, 또는 승인된 설계서나 백로그 수락 기준에 있으나 코드에서 확인하지 못했다. 이번 phase의 묶음에 들지 못해 다음으로 미뤄진 줄도 여기다 | 설계서 경로와 절, 또는 백로그 ID(미뤄진 줄은 그 줄을 다루는 항목) |
| `구현됨` | 코드에서 확인했다 | 파일 경로와 심볼(`src/cart.mjs#addItem`) |
| `검증됨` | 확인하는 테스트가 있고 최근 결과가 통과다. `구현됨`과 이 값 사이는 `test-ledger.mjs`가 최종 테스트 결과로 바꾸므로 손으로 고치지 않는다 | 테스트 파일과 테스트 이름 |
| `확인 필요` | 문서와 코드가 다르거나 근거를 찾지 못했다 | 사유 한 줄 |

- 근거는 저장소에 있는 것만 가리킨다: 코드 경로, 테스트 이름, 설계서 경로, phase 이름. `_workspace/` 경로는 적지 않는다. 그 폴더는 git에 올라가지 않는다.
- 색인의 문서 상태는 `없음`, `해당 없음`, `최신`(마지막 점검에서 끊긴 참조와 열린 불일치가 없었다), `확인 필요`(열린 불일치가 있다) 중 하나다.

## 정본 표

| 사실 | 정본 | 다른 문서는 |
| --- | --- | --- |
| 목표, 성공 지표, 사용자 스토리, 하지 않는 것 | PRD | 가리킨다 |
| 요구사항 문장과 수용 기준 | SRS | `FR`/`NFR` ID로 가리킨다 |
| 화면의 구성요소, 상태, 동작 | UI 명세 | `SCR`/`UI-FUNC` ID로 가리킨다 |
| 요청과 응답 형식, 스키마, 오류 코드 | 계약 문서. 기계가 검증하는 파일(OpenAPI YAML, SQL 스키마)이 있으면 그 파일 | 가리킨다 |
| 결정의 이유와 대안 | ADR | 아키텍처 문서 9절은 번호만 나열한다 |
| 구조, 배치, 횡단 개념, 위험과 기술 부채 | 아키텍처 문서 | 가리킨다 |
| 테스트 절차와 기대 결과 | 자동화된 것은 테스트 코드, 손으로 하는 것은 테스트 케이스 장부 | 가리킨다 |
| 요구사항과 화면·계약·코드·테스트의 연결, 요구사항의 상태 | 추적표 | 연결 표를 따로 만들지 않는다 |
| 실행 순서와 명령 | 런북. 검증 명령은 `AGENTS.md`의 `명령` 절 | 가리킨다 |
| 값(디자인 토큰, 설정값, 환경 변수 목록) | 코드나 설정 파일 | 경로를 가리킨다. 값을 복사하지 않는다 |
| 진행 중인 작업의 수락 기준 | 백로그 항목(`product-manager`) | 그 작업이 끝나면 SRS가 현재 요구사항의 정본이 된다 |
| 그 phase의 설계와 계획 | `docs/superpowers/`의 설계서와 계획서 | 본문을 고치지 않고 가리킨다 |

## 추가만 하는 기록

`docs/07-decisions/`(ADR), `docs/08-implementation/wbs.md`(phase 색인), `docs/12-changelog/`(변경 이력)는 줄을 더하기만 하는 기록이다. 날짜와 phase 이름을 둔다. 나머지 문서는 현재 상태만 담는다. 날짜가 붙은 경과, 대체된 옛 내용, 백로그 번호 나열을 넣지 않는다.

## 결정과 불일치

- 문서에 쓰는 결정의 출처는 넷뿐이다: 승인된 설계서, 계획서, 백로그 항목, 브리프의 사용자 결정. 출처를 문서에 적을 때는 설계서 경로와 phase 이름으로 적는다.
- ADR은 이미 내려진 결정만 기록한다. 출처가 없는 결정처럼 보이는 변경(예: 설계서에 없이 바뀐 라이브러리)은 ADR로 쓰지 않고 불일치로 올린다.
- 승인된 기준이 분명하면 해당 절의 지정 작성자에게 근거와 수정을 요청하고 반영을 확인한다. 예: 이번 phase의 승인된 설계서와 검증된 코드가 같고 옛 문서만 다르다.
- 코드가 승인된 설계나 요구사항과 다르거나, 출처 없이 바뀐 것은 어느 쪽도 맞다고 정하지 않는다. 리포트의 `## 불일치` 표에 적고 지정 작성자에게 해당 줄의 확인을 요청한다. 코드와 설계서는 고치지 않는다.

## 리포트

경로는 spec의 `보고` 줄이 정한다(`_workspace/_run/<phase>/NN_doc-steward_<산출물>_v<N>.md`). 양식 `docs/harness/templates/report.md`의 절에 아래 절을 더한다.

```markdown
# <Task ID> <이름> 리포트

## 한 일

## 영향 분석

| 바뀐 경로 | 닿는 ID | 고칠 문서 | 사유 |
| --- | --- | --- | --- |

## 반영 확인

| 문서·절/ID | 지정 작성자 | 반영·현행 확인 근거 또는 대기 사유 |
| --- | --- | --- |

## 불일치

| ID | 문서 위치 | 문서 내용 | 코드의 실제 | 승인된 기준으로 보이는 쪽과 근거 |
| --- | --- | --- | --- | --- |
| DOC-1 | | | | |

## 인박스 후보

- <불일치 한 줄 요약> (DOC-1)

## 직접 소통

없음

## 검증

- ✅ `<점검 명령>` → <결과>
- ❌ 필수 반영 대기 · <BL> · <문서와 절/ID> · <지정 작성자 또는 미배정> · <근거>

## 남은 것
```

- 불일치의 ID는 리포트 안에서 `DOC-1`부터 센다. 표가 비면 "없음"이라고 쓴다.
- `## 인박스 후보`에는 불일치마다 한 줄을 적는다. `product-manager`가 완료 처리에서 인박스로 옮긴다.
- `## 검증`에는 점검표(`references/audit.md`)의 줄을 ✅나 ❌로 적는다. 여기의 ❌는 이 Task가 끝내지 못한 것이다.
- 이번 변경 범위 밖에서 발견한 기존 문서 부채만 `- ❌ (참고) 불일치 <N>건: <ID들>`로 적어 인박스 후보에 올린다. `## 불일치` 표에는 ID와 근거를 적는다.
- 이번 phase의 필수 문서·절이 미배정이거나 인계만 끝났으면 `## 검증`에 BL·문서·절/ID·작성자·근거와 함께 `❌ 필수 반영 대기`로 보고한다. 코디네이터는 지정 작성자의 반영·현행 확인 결과가 올 때까지 완료 정산과 phase 마감을 보류한다. 사용자가 명시적으로 이월하면 해당 BL에 남은 문서·절, 작성자와 사유를 기록해 미완료로 두고 나머지 항목의 정산과 회고 뒤 마감한다.
- 영향 받는 문서가 없으면 `## 한 일`에 "변경 없음"이라고 쓴다.

## 오류 처리

| 상황 | 대응 |
| --- | --- |
| 설계서나 검증 리포트가 없다 | 코드와 git 변경을 근거로 확인한다. 미확인 항목은 리포트에 남겨 지정 작성자에게 넘긴다 |
| 결정이 있어야 쓸 수 있는 절이다 | 비워 두고 `ask`로 올린다. 추측으로 채우지 않는다 |
| 색인이 커밋된 적이 없어 지난 동기화의 경계를 알 수 없다 | 마지막 커밋 뒤의 변경을 범위로 삼는다. 커밋이 하나도 없으면 작업 트리 전체다(`references/sync.md` 1단계) |
| 양식에 맞지 않는 기존 문서가 있다 | 그대로 두고 색인에 올린다. 양식으로 옮겨 쓸지는 `## 인박스 후보`에 올린다 |
| 고칠 문서가 30KB를 넘는다 | 지정 작성자에게 분할을 요청하고 결과를 `## 반영 확인`에 적는다 |

## 하지 않는 것

- 코드, 테스트, 백로그, 설계서와 계획서, `docs/history/`, `docs/harness/`, `AGENTS.md` 편집.
- 요구사항, 우선순위, 아키텍처 결정을 새로 정하기.
- 코드와 명세의 차이를 한쪽에 맞춰 조용히 없애기.
- 기존 문서 옮기기와 지우기.
- 릴리스 정하기. 변경 이력 반영은 지정 작성자에게 넘긴다.
- 리포트 전문 읽기. 구현 리포트는 `## 한 일`만, 검증 리포트는 결함 표와 `## 검증`만 읽는다.
