# 동기화 절차

> 읽는 시점: 작업 단위가 `문서 동기화`일 때. 장부의 `## 라이브 문서 확인`에 행이 있을 때 phase의 6단계에서 최종 테스트 뒤에 돈다.

doc-steward가 지난 동기화 뒤 코드·테스트·문서 변경을 대조한다. 제품 내용의 첫 작성과 수정은 해당 문서·절의 지정 작성자가 한다.

## 1. 변경 구하기

바뀐 파일은 넘겨받지 않고 git에서 구한다. 워커는 커밋하지 않고 phase 끝에 한 번에 커밋되므로, 색인을 마지막으로 고친 커밋이 지난 동기화의 경계다.

```sh
git log -1 --format=%H -- docs/DOCUMENTATION_INDEX.md   # 기준 커밋
git diff --stat <기준 커밋>                               # 그 뒤에 바뀐 추적 파일(커밋된 것과 안 된 것)
git status --short                                       # 새로 생긴 파일
```

- 아래 경로는 변경 목록에서 뺀다: `_workspace/`, `.claude/`, `docs/harness/`, `docs/history/`, 그리고 색인 자체. 번호 폴더·코드 지도·다른 위치의 정본(OpenAPI 포함) 변경은 영향 분석에 포함한다.
- `docs/superpowers/`의 설계서와 계획서, `docs/backlog.md`, `docs/backlog-archive.md`도 변경 목록에서 뺀다. 이들은 반영할 변경이 아니라 2단계에서 읽는 입력이다.
- 기준 커밋이 나오지 않으면 색인이 커밋된 적이 없는 것이다. 멈추지 않는다. 저장소에 커밋이 있으면 마지막 커밋 뒤의 변경을 범위로 삼는다(`git diff --stat HEAD`와 `git status --short`). 커밋이 하나도 없으면 작업 트리 전체가 범위다.
- git 저장소가 아니면 spec이 적은 경로만 본다.
- 색인의 문서 줄이 모두 `없음`인데 이번 변경 밖에 코드가 이미 있으면 초기화가 안 된 프로젝트다. 이번 변경만 문서로 만들고 나머지 줄은 `없음`으로 둔다. 스스로 전체 초기화를 하지 않는다. 리포트의 `## 검증`에 `- ❌ (참고) 문서 초기화가 아직 안 됐다. '문서 초기화'를 요청해야 나머지 코드가 문서에 들어간다`를 적고, `## 인박스 후보`에도 한 줄 올린다.

## 2. 입력 읽기

| 입력 | 어디서 | 읽는 범위 |
| --- | --- | --- |
| 이번 phase가 바꾸려 한 것과 결정 | spec의 설계서와 계획서 | 목표, 결정과 그 이유, 계획서의 Task 목록 |
| 무엇이 검증됐는가 | spec의 끝 검증 리포트 | 결함 표와 `## 검증` |
| 수락 기준 | 백로그 항목(`docs/backlog.md`) | 이번 phase의 항목 줄. 비고의 `요구사항 <ID>`로 SRS 줄을 찾는다 |
| PM이 실행 전에 쓴 요구사항 | PRD와 SRS의 `(계획됨` 표시가 붙은 줄 | 이번 phase의 항목이 가리키는 줄 |
| 다른 에이전트가 넘긴 것 | 장부에 적힌 구현 Task의 리포트 | `## 한 일`만 |

리포트는 길잡이로만 쓴다. 문서에 적는 사실의 근거는 코드에서 확인한다.

## 3. 영향 분석

바뀐 경로마다 추적표(`docs/10-traceability/rtm.md`)의 코드 칸과 코드 지도의 모듈 표에 대조한다. 결과를 리포트의 `## 영향 분석` 표에 쓴다.

- 추적표에 닿는 줄이 있다 → 그 요구사항 ID를 따라 SRS, UI 명세, 계약 문서, 테스트 케이스 장부에서 해당 줄을 찾는다.
- 닿는 줄이 없다 → 새 요구사항이나 새 모듈 후보다. 설계서와 백로그의 출처를 지정 작성자에게 넘기고, 없으면 불일치로 올린다.
- 추적표가 아직 없다 → 대조할 줄이 없다. 바뀐 경로마다 설계서와 백로그 항목에서 출처를 찾아 지정 작성자에게 넘긴다.
- 코드 지도가 없거나 설치 초안이다 → 이번 변경 밖에 코드가 없으면(새 프로젝트) 지정 작성자에게 이번 변경 근거를 넘겨 코드 지도를 채운다. 이번 변경 밖에 코드가 이미 있으면 색인에 `없음`으로 두고 문서 초기화 때 채운다.
- 고칠 문서가 정해지면 그 문서의 양식만 읽는다.

## 4. 지정 작성자의 반영과 확인

- 이력 전용 Task는 그 에이전트의 리포트로 끝낸다. 제품 현황이 바뀌면 발견자가 BL·정본 경로·절/ID·재현 근거·작성자를 기록한다. 예를 들어 QA가 API 응답 변경을 찾으면 QA 리포트를 계약 작성자에게 넘긴다. 아직 담당이 없으면 코디네이터에게 지정을 요청한다.
- PM은 PRD·SRS의 요구와 구현/검증 상태를, 다른 지정 작성자는 자기 절의 내용만 근거에 맞춰 반영한다. API·DB·ADR·런북의 설치 초안을 실제 정본으로 쓸 때 지정 작성자가 이름과 근거를 알리고 doc-steward가 색인을 연결한다. 색인에 다른 정본이 있으면 그 위치를 쓴다.
- doc-steward는 실제 파일·코드·검사 결과를 다시 대조한다. 내용 결함은 원작성자에게 돌려보내고, 이미 현행이면 대조한 위치와 결과를 남긴다. 인계만 끝난 BL은 반영 대기로 보고한다.
- 리포트의 `## 반영 확인` 표에는 영향받은 절마다 `| 정본 경로 · 절/ID | 지정 작성자 | 결과 · 근거 |`를 적는다. 결과는 `반영`, `현행 확인`, `반영 대기`다. 근거에는 해당 BL ID, 실제 보고 위치와 대조 결과를 남긴다. 예를 들어 `| api/orders.yaml · getOrder | api-owner | 반영 · BL-0001 qa.md 응답 재현과 api-owner.md 계약 테스트 결과 대조 |`처럼 쓴다. 백로그 없는 작업은 BL ID를 생략한다.

## 5. 추적표와 기록

RTM·테스트 케이스·변경 이력·WBS에서 영향받은 줄과 근거를 각 지정 작성자에게 전달한다. 변경이 없는 문서는 다시 쓰지 않는다. 하네스 개선은 하네스 변경 이력에 연결한다.

## 6. 점검

`references/audit.md`의 점검표를 이번에 고친 문서와 이번 phase에 담당 에이전트가 고친 정본의 변경 범위에 돌린다.

## 7. 색인 고치기

- 고친 문서의 줄: 정본 문서, 관련 ID, 마지막으로 갱신한 phase, 상태.
- 쓸 내용이 없는 줄은 `없음`으로 둔다. `해당 없음`은 초기화나 사용자 결정으로만 정한다. 동기화가 정하지 않는다.
- 머리의 "마지막으로 갱신한 phase"는 영향 받는 문서가 없어도 이번 phase로 고친다. 색인을 고친 커밋이 다음 동기화의 기준이 되기 때문이다.

## 8. 리포트

`SKILL.md`의 리포트 형식으로 쓴다. `## 검증`에 적는 줄:

- `grep -c "<phase 이름>" docs/DOCUMENTATION_INDEX.md` → 1 이상
- 점검표에서 이번에 돌린 줄마다 한 줄. 필수 반영 대기에는 BL·작성자·문서·절·근거를 갖춘 ❌를 남기고, 이번 변경 밖의 기존 문제만 참고로 분류
- 이번 변경 밖에서 발견한 불일치만 `- ❌ (참고) 불일치 <N>건: <ID들>`로 집계한다.
