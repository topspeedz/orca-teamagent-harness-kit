# 화면 UI 명세 양식

> 읽는 시점: `docs/03-ui-ux/ui-spec.md`를 처음 쓰거나 고칠 때. 화면이 없는 프로젝트에서는 읽지 않는다.

- 바탕 표준: 국내 화면 정의서 관행(화면 ID, 번호 붙인 구성요소와 설명 표), 화면의 다섯 상태, WCAG 2.2.
- 정본 위치: `docs/03-ui-ux/ui-spec.md`. 화면이 많아 30KB를 넘으면 화면마다 `docs/03-ui-ux/screens/<화면 ID>.md`로 나누고 이 파일에는 화면 목록과 흐름만 남긴다.
- 이 문서가 정본인 것: 화면의 구성요소, 상태, 동작. 요구사항 문장은 SRS가, 요청과 응답의 형식은 계약 문서가 갖는다.

## 채우는 법

- 화면 ID는 `SCR-###`, 화면 안의 기능 ID는 `UI-FUNC-###`이다. 기능 번호는 화면을 넘어 이어서 센다.
- 화면 구성 표의 번호는 화면 위에서 아래, 왼쪽에서 오른쪽 순서로 매긴다. 화면 그림이 저장소에 있으면 그 경로를 적고 같은 번호를 쓴다.
- 기능 표는 버튼이 있다는 사실이 아니라 동작을 적는다. 여덟 칸을 모두 채운다. 코드에서 확인하지 못한 칸은 "확인 필요"라고 쓴다.
  - `Trigger`: 무엇이 이 기능을 시작하는가
  - `Precondition`: 시작하려면 참이어야 하는 것
  - `Action`: 시스템이 하는 일. 호출하는 계약 ID
  - `Loading`: 기다리는 동안 보이는 것
  - `Success`: 성공하면 바뀌는 것
  - `Error`: 실패하면 보이는 것과 사용자가 할 수 있는 일
  - `Accessibility`: 키보드 조작과 상태 알림
  - `Test ID`: 이 기능을 확인하는 테스트 케이스 ID
- 다섯 상태는 화면마다 모두 적는다. 그 상태가 생길 수 없는 화면이면 "없음"과 이유를 적는다.
- 접근성 점검은 코드에서 확인한 것만 "충족"으로 적는다. 확인하지 못한 줄은 "확인 필요"다.
- 색, 글꼴, 간격의 값을 옮겨 적지 않는다. 값은 코드의 토큰 파일이 정본이고 여기서는 경로를 가리킨다.
