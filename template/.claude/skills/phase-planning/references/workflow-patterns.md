# 작업 흐름 패턴

> 읽는 시점: planner가 설계에서 흐름의 모양을 고를 때, 팀장이 팀 안의 Task를 나눌 때. 실제 phase는 여러 패턴을 섞는다(예: 파이프라인 안의 한 단계를 팬아웃/팬인으로).

| 패턴 | 쓰는 때 | 흔한 실패 | Orca에서 |
| --- | --- | --- | --- |
| 파이프라인 | 앞 산출물 없이는 못 시작할 때 | 사슬이 길어져 병렬이 사라진다 | Task의 `--deps`. 사슬은 4단 이내 |
| 팬아웃/팬인 | 편집 범위가 서로 겹치지 않을 때 | 모으는 Task 하나가 병목이 된다 | 독립 Task를 한 번에 띄우고, 모으는 쪽도 처음부터 나눈다 |
| 전문가 풀 | 요청 종류에 따라 담당이 달라질 때 | 분류가 틀리면 전부 틀린다 | 명단을 보고 해당 팀만 띄운다 |
| 생성·검토 | 결과에 판정 기준이 있을 때 | 끝나지 않는 왕복 | 평가자와 생성자를 분리하고 루프는 최대 2회 |
| 감독자 | 진행에 따라 배분이 바뀔 때 | 감독자의 컨텍스트가 불어난다 | 팀장. 리포트는 경로로만 받는다 |
| 계층 위임 | 한 팀의 Task가 3개 이상일 때 | 깊어지면 느려지고 맥락을 잃는다 | 코디네이터, 팀장, 팀원. 두 단까지 |

## 예

### 파이프라인

API 스키마 → 서버 구현 → 클라이언트 연결. 클라이언트 Task는 서버 Task의 응답 형식 파일을 읽어야 하므로 `--deps`로 잇는다. 넷째 단을 붙이고 싶어지면 단 하나를 둘로 나눠 옆으로 펼 수 있는지 먼저 본다.

### 팬아웃/팬인

화면 세 개를 고치는 일. 화면마다 Task 하나로 동시에 띄운다. 결과를 모으는 공용 파일 갱신도 화면별 절로 나눠 각 Task가 자기 절만 쓰게 하고, 모으는 Task 하나가 셋을 모두 기다리는 꼬리를 만들지 않는다. 제품의 live 문서(`docs/`의 번호 폴더)는 여기에 넣지 않는다. 6단계에서 `doc-steward`가 쓴다.

### 전문가 풀

요청이 "결제 오류 수정"이면 명단(`docs/harness/team-org.md`)에서 그 영역을 맡는 팀만 띄운다. 분류가 애매하면 띄우기 전에 planner가 `## 사용자 결정 필요`에 올린다.

### 생성·검토

구현 Task 뒤에 `code-reviewer` Task를 둔다. High가 나오면 수정 Task를 띄우고, 코디네이터의 최종 테스트가 수정의 재현 테스트로 확인한다. 재현 테스트가 없는 결함만 재검 Task로 확인한다. 두 번 돌고도 High가 남으면 멈추고 사용자에게 보고한다.

### 감독자

진행하면서 결함 수에 따라 수정 Task 수가 바뀌는 검증 묶음. 팀장이 리포트 경로만 받아 다음 Task를 띄운다. 리포트 본문을 팀장 컨텍스트에 붙여 넣지 않는다.

### 계층 위임

한 phase에서 제품 팀 Task가 다섯 개다. 코디네이터는 제품 팀장 하나를 띄우고, 팀장이 팀원 Task를 띄운다. 팀원이 다시 팀원을 띄우지 않는다.
