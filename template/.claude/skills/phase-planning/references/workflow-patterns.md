# 작업 흐름 패턴

> 읽는 시점: product-manager가 설계에서 흐름의 모양을 고를 때. 실제 phase는 여러 패턴을 섞는다(예: 파이프라인 안의 한 단계를 팬아웃/팬인으로).

| 패턴 | 쓰는 때 | 흔한 실패 | Orca에서 |
| --- | --- | --- | --- |
| 파이프라인 | 앞 산출물 없이는 못 시작할 때 | 사슬이 길어져 병렬이 사라진다 | Task의 `--deps`. 사슬은 4단 이내 |
| 팬아웃/팬인 | 편집 범위가 서로 겹치지 않을 때 | 모으는 Task 하나가 병목이 된다 | 독립 Task를 한 번에 띄우고, 모으는 쪽도 처음부터 나눈다 |
| 전문가 풀 | 요청 종류에 따라 담당이 달라질 때 | 분류가 틀리면 전부 틀린다 | 명단을 보고 해당 에이전트만 띄운다 |
| 생성·검토 | 결과에 판정 기준이 있을 때 | 끝나지 않는 왕복 | 평가자와 생성자를 분리하고 루프는 최대 2회 |
| 감독자 | 진행에 따라 배분이 바뀔 때 | 감독자의 컨텍스트가 불어난다 | 코디네이터. 리포트는 경로로만 받고 정산은 `settle` 한 명령이다 |

## 예

### 파이프라인

API 스키마 → 서버 구현 → 클라이언트 연결. 클라이언트 Task는 서버 Task의 응답 형식 파일을 읽어야 하므로 `--deps`로 잇는다. 넷째 단을 붙이고 싶어지면 단 하나를 둘로 나눠 옆으로 펼 수 있는지 먼저 본다.

### 팬아웃/팬인

화면 세 개를 고치는 일. 화면마다 Task 하나로 동시에 띄운다. 결과를 모으는 공용 파일 갱신도 화면별 절로 나눠 각 Task가 자기 절만 쓰게 하고, 모으는 Task 하나가 셋을 모두 기다리는 꼬리를 만들지 않는다. 에이전트가 담당하는 정본 절은 해당 구현 Task에 넣고, 같은 정본 파일을 편집하는 Task는 순서대로 배정한다.

### 전문가 풀

요청이 "결제 오류 수정"이면 명단(`docs/harness/agents.md`)에서 그 영역을 맡는 에이전트만 띄운다. 분류가 애매하면 띄우기 전에 PM이 `## 사용자 결정 필요`에 올린다.

### 생성·검토

구현 Task 전부 뒤에 시험 갱신 Task를 두고, 끝 검증(`verifier`)은 한 묶음으로 구현과 시험 갱신 Task에만 의존한다. 공통 판정 기준의 증거와 영향 근거를 갖춘 High가 나오면 수정 Task를 띄우고, 코디네이터의 최종 테스트가 수정의 재현 테스트로 확인한다. 재현 테스트가 없는 결함만 재검 Task로 확인하고, 재검은 결함 ID와 수정 diff만 본다. 재검이 아닌 검증을 수정 뒤에 걸지 않는다. 수정 사슬은 2단까지다. 두 번 돌고도 High가 남으면 멈추고 사용자에게 보고한다.

### 감독자

진행하면서 결함 수에 따라 수정 Task 수가 바뀌는 검증 묶음. 코디네이터가 리포트 경로만 받아 다음 Task를 띄운다. 리포트 본문을 코디네이터 컨텍스트에 붙여 넣지 않는다.
