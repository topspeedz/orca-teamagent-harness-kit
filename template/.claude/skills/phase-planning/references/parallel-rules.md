# 병렬 효율 규칙

> 읽는 시점: planner가 계획서의 `## DAG` 절을 쓸 때와 계획 승인 전, 팀장이 팀 안의 Task를 나눌 때.

## 규칙 여덟 줄

1. 의존은 산출물 의존만 인정한다. 의존마다 "뒤 Task가 앞 Task의 무엇을 읽는지" 한 줄로 적는다. 적을 수 없으면 의존이 아니다. "순서상 자연스럽다"는 의존이 아니다.
2. Task 하나에 산출물 하나와 완료 검사 명령 하나를 둔다. 산출물이 둘이면 Task를 나눈다.
3. Task마다 예상 시간(짧게, 보통, 길게. 계획서에는 low, likely, high 분으로 적는다)과 분할선(막혔을 때 나눌 경계)을 적는다.
4. 가장 긴 의존 사슬을 임계 경로라고 한다. 임계 경로 위에 있고 분할선이 있는 Task는 처음부터 나눈다.
5. 예상 시간이 워커 기동 비용의 두 배보다 짧은 같은 역할의 Task는 합친다. 기동 비용의 출발값은 3분이다.
6. 끝 검증과 수정은 처음부터 영역별로 여러 개로 계획한다. 모으는 Task, QA 한 명, 수정 한 명이 일렬로 서는 꼬리를 만들지 않는다.
7. 한 팀의 동시 워커는 4명 이하다. 전체 동시 수는 브리프의 슬롯 수를 따른다.
8. 출발값(3분, 두 배, 4명)은 회고 때 실측으로 고친다.

## 준비된 Task 단위 기동

폭은 계획이 정하고, 기동은 그 폭을 그대로 쓴다.

- 기동은 웨이브 단위가 아니라 준비된 Task 단위다. `worker_done`을 정산할 때마다 의존이 모두 끝난 Task를 빈 슬롯만큼 바로 띄운다.
- 코디네이터가 띄우는 Task는 의존과 함께 Orca에 등록되고, 앞 Task가 끝나기 전에는 Orca가 기동을 거부한다. 팀장을 두는 팀의 Task들은 팀 Task 하나로 등록되므로, 팀 사이의 의존은 팀 Task끼리 걸린다. 팀 안의 순서는 팀장이 지킨다.
- 남은 임계 경로가 긴 것부터 띄운다.
- 계획 없이 코디네이터나 팀장이 즉석에서 병렬을 만들지 않는다. 더 나눠야 하면 계획의 분할선을 따른다.

## 승인 전 점검

- 사유 없는 의존이 없다.
- 산출물이 둘 이상인 Task가 없다.
- 사슬이 4단을 넘지 않는다.
- likely가 기동 비용의 두 배(출발값 6분)보다 짧은 같은 역할 Task가 따로 서 있지 않다.
- 임계 경로 위의 분할선 있는 Task가 이미 나뉘어 있다.
- 끝 검증이 영역 둘 이상을 덮으면 검증 Task도 영역별로 나뉘어 있다.
- 병렬도 수치(작업 시간 합 ÷ 임계 경로 길이, 슬롯 수, 최대 동시 Task 수)가 DAG 절 끝에 있다.
