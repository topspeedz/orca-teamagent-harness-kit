# backlog-management

`docs/backlog.md`가 할 일의 정본이다. 무엇을, 누가, 언제 끝난 것으로 보는지를 이 파일 한 곳에서 답한다. 끝난 항목은 `docs/backlog-archive.md`로 옮긴다. 항목 형식과 상태 값은 이 스킬이 정하고, 다른 스킬과 에이전트는 옮겨 적지 않고 이 스킬을 가리킨다.

## 역할 나눔

| 누가 | 하는 일 |
| --- | --- |
| 기획 (`product-manager`) | 항목의 내용을 소유한다: 무엇을 왜, 수락 기준, 우선순위. 인박스를 정리하고 완료 항목을 보관 파일로 옮긴다. **백로그 파일의 구조를 고치는 유일한 역할이다.** |
| `planner` | 승인된 묶음의 항목을 Task로 나누고, 순서와 예상 시간과 배정을 정한다. 백로그는 읽기만 하고 결과는 계획서에 쓴다. Task마다 백로그 ID를 적는다. |
| 코디네이터 | 실행 중에 **상태 열만** 갱신한다. 해당 줄을 ID로 찾아 그 줄만 고친다. |
| 사용자 | phase의 범위와 계획을 승인한다. |

## 형식

`docs/backlog.md`:

```
# Backlog
(규칙 머리말)
| ID | 항목 | 역할 | 상태 | 비고 |      ← 활성 항목: todo, doing, blocked
## 인박스                              ← 한 줄씩. 다음 정리 때 판정한다
```

`docs/backlog-archive.md`: 같은 표 머리 아래에 `done` 행을 옮긴 그대로 둔다.

| 열 | 값 |
| --- | --- |
| ID | `BL-####`. 백로그와 보관 파일을 합친 최댓값 + 1. 보관으로 간 번호도 다시 쓰지 않는다. |
| 항목 | 수락할 수 있는 결과 하나를 한 줄로 |
| 역할 | `.claude/agents/`의 에이전트 이름. 둘 이상이면 리드를 앞에 적는다 |
| 상태 | `todo`, `doing`, `blocked`, `done` |
| 비고 | 라벨을 이 순서로: `우선순위 <필수 / 중요 / 있으면 좋음> · 복잡도 <값>(기술 n · 도메인 n · 불확실성 n) · 요구사항 <FR/NFR ID> · 선행 <BL ID 또는 없음> · 수락 기준: (1) … (2) …`. 확정된 RICE는 우선순위 뒤에 `RICE <점수>(R n · I n · C n%)`. 그 뒤에 근거(phase 이름과 결함 ID), 막힌 이유. 항목과 Task의 연결은 계획서가 가지므로 여기 적지 않는다. `_workspace/` 경로는 적지 않는다 |

다음 번호 찾기:

```sh
cat docs/backlog.md docs/backlog-archive.md | grep -oE "^\| BL-[0-9]{4}" | sort -u | tail -1
```

병렬 브랜치가 있으면 각 브랜치의 두 파일도 함께 본다. 같은 번호가 머지에서 부딪히면 대상 브랜치에 이미 있는 번호를 남기고 들어오는 쪽을 바꾼다.

## 항목의 단위

- 항목 하나는 수락할 수 있는 결과 하나다. 같은 결과의 리뷰, QA, 재검, 수정은 같은 번호를 쓴다.
- 여러 역할이 걸려도 한 결과면 한 항목이다. 역할 열에 리드를 앞에, 협업 역할을 뒤에 적는다.
- 백로그 행 수와 Task 수는 다르다. Task로 나누는 것은 planner의 일이다.
- 아래 중 하나면 항목을 나눈다: 결과를 따로 수락할 수 있다, 다른 승인이나 결정에 막힌다, 복잡도가 13이다.
- 나누는 기준, 복잡도, 우선순위의 방법은 [분해·복잡도](references/decomposition.md)와 [우선순위·묶음](references/prioritization.md)가 정본이다.

## 수락 기준

- 수락 기준의 정본은 백로그 항목이다. 계획서, spec, 리포트에 같은 기준을 다시 쓰지 않고 항목 ID를 가리킨다.
- 검증자가 그대로 검사할 수 있게 쓴다. 대상, 조건, 기대 결과가 들어간다.
  - 좋음: "`/login`에서 틀린 비밀번호를 넣으면 오류 문구가 보이고 제출 버튼이 다시 눌린다"
  - 나쁨: "로그인 오류가 잘 보인다"
- 항목마다 정상 흐름 기준 하나와 오류 흐름 기준 하나 이상을 쓴다. 오류 흐름이 생길 수 없으면 그 사유를 비고에 적는다.
- 수치를 지어내지 않는다. 근거가 없는 기준은 `## 사용자 결정 필요`로 올린다.

## 인박스

- 검증에서 나온 Medium 이하 결함과 실행 중 발견한 후속 작업은 새 항목이 아니라 `## 인박스`에 한 줄로 넣는다. 문서 동기화가 찾은 문서와 코드의 불일치(`DOC-<번호>`)도 같다.
- 한 줄 = 요약 + phase 이름 + 결함 ID. 원문은 리포트에 둔다. 이 파일은 git이 추적하므로 `_workspace/` 경로를 적지 않는다.
- 다음 정리 때 기획이 판정한다: 항목으로 올림, 기존 항목의 비고에 합침, 버림(이유 한 줄).

## planner에게 넘기는 것

- 새 요구에서 사용자가 확인한 묶음, 지정 ID 또는 위임받아 선정한 묶음을 넘긴다. 묶음은 브리프의 `## 백로그 항목`에 있고, planner spec은 브리프를 가리킨다.
- 완료 항목은 보관 파일로 옮겨 활성 파일을 작게 유지한다.

## 2단계: 항목화와 묶음 제안

새 요구는 PM이 PRD·SRS 작성 결과에서 이어 간다. 기존 백로그로 한 phase를 위임받으면 활성 항목의 확정 우선순위·선행 조건·연관성으로 진행 가능한 목표 하나와 묶음을 골라 선정 이유와 BL ID를 Planner에게 넘긴다. 이 경우 별도 묶음 승인은 없고 최종 계획·실행 승인에서 함께 확인한다. 사용자가 BL ID를 직접 지정하면 창구가 Planner에게 바로 넘긴다.

1. SRS의 `(계획됨` 표시가 붙은 요구사항, PRD의 `US`, 요구사항 리포트, 지금 백로그와 보관 파일을 읽는다.
2. 요구사항을 항목으로 나눈다. 이미 있는 활성 항목과 같은 결과면 그 항목에 합친다.
3. 항목마다 수락 기준, 복잡도, 우선순위를 비고 라벨로 적는다. 상태는 `todo`, 역할 열은 명단에서 그 영역을 맡는 팀의 에이전트, 모르면 `미정`.
4. RICE 추천값, 출처 없는 등급은 백로그에 쓰지 않고 리포트의 `## 사용자 결정 필요`에 올린다.
5. 리포트에 항목 표, 요구사항과 항목 대조 표, 묶음 제안(이번·다음·나중, 목표 한 문장, 복잡도 합과 지난 실적)을 둔다.
6. 리포트 `## 검증`에 실제로 돌린 확인 명령과 결과를 적는다. 예: `grep -c "^| BL-0001 " docs/backlog.md` → `1`.

## 실행 중: 상태 열

- 코디네이터는 상태 열만 고친다. 줄 번호가 아니라 `^| BL-#### |` 행을 찾아 그 줄의 상태 칸만 바꾸고 `grep -n "^| BL-#### "`로 확인한다. 병렬 Run이 행을 넣으면 줄 번호가 밀린다.
- QA·문서 확인 전에는 완료로 표시하지 않는다. 항목, 비고, 수락 기준, 행 추가와 보관은 PM의 일이다.

## 6단계: 완료 처리

코디네이터가 QA와 문서 확인 결과를 갖춰 PM에게 맡긴다. 이번 phase에 다룬 BL을 각각 판정한다.

1. 역할 열을 계획서의 배정으로 맞춘다(항목이 계획보다 먼저 생겨 `미정`이었을 수 있다).
2. BL마다 QA 통과와 doc-steward의 확인을 대조한다. 필수 절은 지정 작성자의 반영 또는 현행 확인이 있어야 한다. 이력 전용은 관련 리포트와 문서 영향 없음의 근거를 확인한다. 인계·반영 대기만으로 `done`을 기록하거나 보관하지 않는다. 사용자의 답이 없으면 phase는 열려 있다. 사용자가 명시적으로 이월하면 해당 BL에 남은 문서·절, 담당(없으면 `미배정`), 사유를 적어 활성 표에 미완료로 남긴다. 나머지 완료 항목만 정산한다. 비고에 phase와 확인 근거 ID를 남긴다.
3. `done` 행을 `docs/backlog-archive.md`로 원문 그대로 옮기고 활성 파일에서 지운다. 활성 파일에는 `todo`, `doing`, `blocked`와 인박스만 남는다.
4. 검증 리포트와 문서 동기화 리포트의 `## 인박스 후보`에서 넘어온 것(Medium 이하 결함, 후속 작업, 문서와 코드의 불일치)을 인박스에 한 줄씩 넣는다.
5. 인박스를 정리한다(위 `## 인박스`의 판정).
6. 리포트 `## 검증`에 옮긴 행 수와 확인 명령을 적는다. 예: `grep -c "^| BL-0002 " docs/backlog-archive.md` → `1`.

## 하지 않는 것

- 코드, 디자인, 계획서 편집.
- 승인 전 실행. 위임된 묶음도 최종 실행 승인에서 사용자가 조정할 수 있다.
- Task 나누기, 배정, DAG. planner와 `phase-planning`의 일이다.
- 사용자 승인 없이 범위를 넓히거나 정본 결정을 바꾸는 항목을 확정하기. `## 사용자 결정 필요`로만 올린다.
- 판정 없이 형식만 다시 쓰기, 오래됐다는 이유만의 삭제.
