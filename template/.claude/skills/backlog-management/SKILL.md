# backlog-management

`docs/backlog.md`가 할 일의 정본이다. 무엇을, 누가, 언제 끝난 것으로 보는지를 이 파일 한 곳에서 답한다. 끝난 항목은 `docs/backlog-archive.md`로 옮긴다. 항목 형식과 상태 값은 이 스킬이 정하고, 다른 스킬과 에이전트는 옮겨 적지 않고 이 스킬을 가리킨다.

## 역할 나눔

| 누가 | 하는 일 |
| --- | --- |
| 기획 (`product-manager`) | 항목의 내용을 소유한다: 무엇을 왜, 수락 기준, 우선순위. 인박스를 정리하고 완료 항목을 보관 파일로 옮긴다. **백로그 파일의 구조를 고치는 유일한 역할이다.** |
| `planner` | 이번 phase에 넣을 항목 묶음을 고르고, Task로 나누고, 순서와 예상 시간과 배정을 정한다. 백로그는 읽기만 하고 결과는 계획서에 쓴다. |
| 코디네이터 | 실행 중에 **상태 열만** 갱신한다. 해당 줄을 ID로 찾아 그 줄만 고친다. |
| 사용자 | phase의 범위와 계획을 승인한다. |

## 형식

`docs/backlog.md`:

```
# Backlog
(규칙 머리말)
| ID | 항목 | 역할 | 상태 | 비고 |      ← 활성 항목: todo, doing, blocked
## 인박스                              ← 한 줄씩. 다음 정리 때 판정한다
```

`docs/backlog-archive.md`: 같은 표 머리 아래에 `done` 행을 옮긴 그대로 둔다.

| 열 | 값 |
| --- | --- |
| ID | `BL-####`. 백로그와 보관 파일을 합친 최댓값 + 1. 보관으로 간 번호도 다시 쓰지 않는다. |
| 항목 | 수락할 수 있는 결과 하나를 한 줄로 |
| 역할 | `.claude/agents/`의 에이전트 이름. 둘 이상이면 리드를 앞에 적는다 |
| 상태 | `todo`, `doing`, `blocked`, `done` |
| 비고 | 우선순위, 수락 기준, 연결된 계획 Task(`계획 <Task ID>`), 근거(phase 이름과 결함 ID), 막힌 이유. `_workspace/` 경로는 적지 않는다 |

다음 번호 찾기:

```sh
cat docs/backlog.md docs/backlog-archive.md | grep -oE "^\| BL-[0-9]{4}" | sort -u | tail -1
```

병렬 브랜치가 있으면 각 브랜치의 두 파일도 함께 본다. 같은 번호가 머지에서 부딪히면 대상 브랜치에 이미 있는 번호를 남기고 들어오는 쪽을 바꾼다.

## 항목의 단위

- 항목 하나는 수락할 수 있는 결과 하나다. 같은 결과의 리뷰, QA, 재검, 수정은 같은 번호를 쓴다.
- 여러 역할이 걸려도 한 결과면 한 항목이다. 역할 열에 리드를 앞에, 협업 역할을 뒤에 적는다.
- 백로그 행 수와 Task 수는 다르다. Task로 나누는 것은 planner의 일이다.
- 아래 중 하나면 항목을 나눈다: 결과를 따로 수락할 수 있다, 다른 승인이나 결정에 막힌다.

## 수락 기준

- 수락 기준의 정본은 백로그 항목이다. 계획서, spec, 리포트에 같은 기준을 다시 쓰지 않고 항목 ID를 가리킨다.
- 검증자가 그대로 검사할 수 있게 쓴다. 대상, 조건, 기대 결과가 들어간다.
  - 좋음: "`/login`에서 틀린 비밀번호를 넣으면 오류 문구가 보이고 제출 버튼이 다시 눌린다"
  - 나쁨: "로그인 오류가 잘 보인다"
- 수치를 지어내지 않는다. 근거가 없는 기준은 `## 사용자 결정 필요`로 올린다.

## 인박스

- 검증에서 나온 Medium 이하 결함과 실행 중 발견한 후속 작업은 새 항목이 아니라 `## 인박스`에 한 줄로 넣는다.
- 한 줄 = 요약 + phase 이름 + 결함 ID. 원문은 리포트에 둔다. 이 파일은 git이 추적하므로 `_workspace/` 경로를 적지 않는다.
- 다음 정리 때 기획이 판정한다: 항목으로 올림, 기존 항목의 비고에 합침, 버림(이유 한 줄).

## planner에게 넘기는 것

- 백로그 전체가 아니라 후보 항목의 줄만 넘긴다. 창구나 기획이 후보 줄을 뽑아 planner spec에 넣는다.
- 완료 항목은 보관 파일로 옮겨 활성 파일을 작게 유지한다.

## 4단계: 계획의 Task를 항목에 연결

계획 승인 뒤 코디네이터가 띄운 기획 워커가 한다.

1. 계획서의 Task 목록과 후보 항목을 읽는다.
2. Task마다 백로그 ID를 정한다. 같은 결과를 내는 Task(리뷰, QA, 수정 포함)는 같은 ID다. 그 항목 비고에 `계획 <Task ID>`를 더한다.
3. 맞는 항목이 없는 Task는 새 항목을 수락 기준과 함께 쓴다. 새 항목이 맞는지 판단이 서지 않으면 산출물에 가정을 적고 `ask`로 묻는다.
4. 계획서에 수락 기준을 다시 쓰지 않는다. 계획서는 고치지 않는다.
5. 산출물에 `Task | 백로그 ID | 새 항목 여부` 표를 둔다. 코디네이터는 이 표로 상태 열을 맞춘다.
6. 리포트 `## 검증`에 실제로 돌린 확인 명령과 결과를 적는다. 예: `grep -c "^| BL-0001 " docs/backlog.md` → `1`.

## 실행 중: 상태 열

- 코디네이터는 상태 열만 고친다. 줄 번호가 아니라 `^| BL-#### |` 행을 찾아 그 줄의 상태 칸만 바꾸고 `grep -n "^| BL-#### "`로 확인한다. 병렬 Run이 행을 넣으면 줄 번호가 밀린다.
- 항목, 비고, 수락 기준, 행 추가와 삭제는 기획의 일이다.

## 6단계: 완료 처리

phase의 실행과 끝 검증이 끝난 뒤 기획 워커가 한다. 이번 phase에 다룬 행만 대상이다.

1. 상태를 확인한다. `done`의 근거는 검증 통과다. 근거 없는 완료 처리를 하지 않는다. 비고에 근거(phase 이름과 결함 ID)를 더한다. `_workspace/` 경로는 적지 않는다.
2. `done` 행을 `docs/backlog-archive.md`로 원문 그대로 옮기고 활성 파일에서 지운다. 활성 파일에는 `todo`, `doing`, `blocked`와 인박스만 남는다.
3. 검증 리포트에서 넘어온 Medium 이하 결함과 후속 작업을 인박스에 한 줄씩 넣는다.
4. 인박스를 정리한다(위 `## 인박스`의 판정).
5. 리포트 `## 검증`에 옮긴 행 수와 확인 명령을 적는다. 예: `grep -c "^| BL-0002 " docs/backlog-archive.md` → `1`.

## 하지 않는 것

- 코드, 디자인, 계획서 편집.
- 항목 묶음 고르기, Task 나누기, 배정, DAG. planner와 `phase-planning`의 일이다.
- 사용자 승인 없이 범위를 넓히거나 정본 결정을 바꾸는 항목을 확정하기. `## 사용자 결정 필요`로만 올린다.
- 판정 없이 형식만 다시 쓰기, 오래됐다는 이유만의 삭제.
