# srs-write

작업 단위는 `요구사항 정리`다. 색인에 지정된 SRS(기본 `docs/02-requirements/srs.md`), PRD, 요청·사용자 결정, `docs/harness/templates/product-docs/srs.md` 양식을 읽는다. PRD와 함께 쓰면 `prd-write`의 요청 대조 표를 이어 쓴다. 첫 실제 요구사항을 쓸 때 설치 초안 표시를 걷는다.

1. 기능(3.1 FR)과 비기능(3.2·3.3·3.6·3.7 NFR)을 조건과 기대 동작으로 적는다. 새 ID는 해당 접두어 최댓값 다음 세 자리다. 출처에 US, 검증 방법에 시험·시연·검사·분석 중 하나를 적는다. 결정이 없는 우선순위는 `정해지지 않음`으로 남긴다.
2. 새 동작에는 `(계획됨)`, 수용 기준에는 백로그 항목을 가리킨다. 이미 구현된 문장·수용 기준은 보존하고 `(계획됨: 바뀜 — 새 문장)` 또는 `(계획됨: 삭제)`를 덧붙인다. 아직 미구현인 줄은 제자리에서 고친다. 기존 동작의 줄이 없으면 새 줄을 만들고 현재 동작을 리포트에 적는다.
3. 인터페이스·계약 ID와 다른 절은 실제 정본과 확인된 근거가 생기면 작성자가 연결한다. QA 근거로 구현이 확인된 뒤 PM이 해당 표시·수용 기준을 현행화하고 doc-steward에게 변경 절을 전달한다. 제품 결정을 문서 확인자에게 넘기지 않는다.
4. 요청별 US·FR/NFR 연결과 각 ID의 존재·유일성을 확인한다. 모호한 부분은 열린 질문으로 구분하고 구현 가능성이 미확인이면 리포트에 남긴다. PM이 실제 정본과 ID를 넘기면 Planner가 해당 버전을 검토한다.
