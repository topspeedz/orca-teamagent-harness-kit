# prd-write

작업 단위는 `요구사항 정리`다. 브리프 원문·사용자 결정, 기존 결정 기록, 색인 `docs/DOCUMENTATION_INDEX.md`의 정본을 읽는다. 기본 PRD는 `docs/01-product/prd.md`, 작성 양식은 `docs/harness/templates/product-docs/prd.md`다. 첫 제품 사실을 채울 때 설치 초안 표시를 걷는다. 요구사항 작성의 바탕은 revfactory/harness-100의 46-product-manager(Apache-2.0)다.

1. 요청을 한 가지 요구씩 R1, R2로 끊고 원래 번호를 유지한다. 범위를 나누기 전에 이번 묶음 밖 요구도 전부 대조한다. 우선순위·팀 규모 같은 결정은 해당 줄의 근거로 쓴다.
2. 배경·문제·영향 범위, 목표, 성공 지표, 가정은 브리프가 뒷받침하는 값만 쓴다. 빠진 값은 `정해지지 않음`으로 두고 열린 질문에 올린다.
3. 요구마다 US를 연결한다. 새 번호는 같은 접두어의 최댓값 다음 세 자리다. 이유를 모르면 `이유 정해지지 않음`, 중요도는 근거가 있을 때만 적는다. 사용자 흐름·화면에는 확인된 정보만 넣고 제외한 요구와 사유를 남긴다. PRD에는 SRS의 계획됨 표시를 붙이지 않는다.
4. `요구 | 요청 원문 요약 | US | FR / NFR | 넣지 않은 사유` 대조 표를 리포트에 남긴다. 단독 PRD라면 FR/NFR에는 요청 범위를 표시한다. SRS도 요청되면 `srs-write`로 같은 표를 이어 쓴다. 요구마다 실제 ID 또는 제외 사유가 있는지와 수치·우선순위의 출처를 확인한다.
5. 여러 해석이 가능하면 추천안과 근거를 `사용자 결정 필요`에 남긴다. 이미 있는 결정과 부딪치면 창구에 올린다. 같은 문서를 나눠 쓸 때는 순차로 진행하고 남은 범위를 보고한다. PM 자가 점검 후 Planner가 해당 버전을 `product-review`로 검토한다.
