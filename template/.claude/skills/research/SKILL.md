# research

질문 하나에 리포트 하나를 돌려준다. 읽은 원문은 서브에이전트의 컨텍스트에 두고, 이 세션과 배정자에게는 확인한 결론과 출처만 가져온다. 읽기 전용이다. 쓰는 파일은 조사 리포트뿐이다.

## 절차

1. **질문을 나눈다.** spec의 질문을 서로의 답에 기대지 않는 하위 질문으로 나눈다. 한 하위 질문의 답이 다른 하위 질문의 범위를 정하면 둘은 독립이 아니다. 그런 것은 앞의 것을 먼저 맡기고 답을 받은 뒤 뒤의 것을 맡긴다. 하위 질문마다 "무엇이 확인되면 답이 된다"를 한 줄로 적는다. 질문이 하나로 충분하면 나누지 않는다.
2. **서브에이전트에 맡긴다.** 독립인 하위 질문은 세션 안의 서브에이전트(Claude Code의 Agent 도구, Codex의 subagent)에 한 번에 병렬로 맡긴다. 서브에이전트는 Orca 워커가 아니다. Orca 워커를 띄우지 않는다. 지시에는 아래 네 가지를 모두 넣는다.

   | 항목 | 적는 것 |
   | --- | --- |
   | 목표 | 그 하위 질문과 "무엇이 확인되면 답이 된다" |
   | 출력 형식 | 결론 한두 문장, 근거마다 출처 경로나 URL과 인용 원문, 확인하지 못한 것의 목록 |
   | 볼 출처 | 읽을 파일·폴더·문서·사이트와 그 순서. 사용자 비밀이나 프로젝트 정보를 외부 요청에 넣지 않는다 |
   | 범위의 끝 | 멈출 조건(읽을 출처 수, 확인되면 멈출 사실), 하지 않을 것(파일 수정, 범위 밖 질문) |

   파일과 페이지를 훑는 일에는 가벼운 모델을 지정한다. 판단이 필요한 비교만 기본 모델에 둔다.
3. **출처를 확인한다.** 결론을 받으면 근거마다 인용한 원문을 직접 열어 그 문장이 그 출처에 있는지 확인한다. 원문을 열어 확인하지 못한 것은 결론에 넣지 않고 `미확인`으로 적는다. 하위 질문끼리 답이 어긋나면 어느 쪽 출처가 더 직접적인지 적고, 정할 수 없으면 둘 다 남겨 `판단 필요`로 둔다.
4. **리포트를 쓴다.** spec이 정한 경로(기본 `_workspace/research/<phase>/NN_research_<주제>_v<N>.md`)에 아래 양식으로 쓴다. 보고는 spec의 `보고` 줄을 따른다.

```markdown
# <질문>

## 결론

<질문에 대한 답. 세 문장 이내>

## 하위 질문

| 하위 질문 | 답 | 출처 | 확인 |
| --- | --- | --- | --- |
| <하위 질문> | <답> | <경로 또는 URL과 절> | 확인 / 미확인 |

## 미확인

- <원문을 열어 확인하지 못한 주장과 그 이유>

## 판단 필요

- <출처끼리 어긋나 정하지 못한 것과 양쪽 출처>
```

## 하지 않는 것

- 제품 코드, 테스트, 문서를 고치지 않는다. 고칠 것이 보이면 리포트의 `판단 필요`나 인박스 후보로 적는다.
- Orca 워커를 띄우지 않는다. 일을 나눠 맡기는 팬아웃은 세션 안의 서브에이전트로만 한다.
- 설계안이나 계획을 쓰지 않는다. 선택지와 근거까지만 주고 고르는 것은 `product-manager`가 한다.
- 원문을 열지 않은 인용을 확인으로 적지 않는다.

## 대표 사례

- 정상: "결제 SDK 두 개의 환불 API 차이" 질문을 SDK별 하위 질문 둘로 나눠 병렬로 맡기고, 받은 인용을 각 SDK 문서에서 열어 확인한 뒤 하위 질문 표 두 행과 결론 두 문장으로 돌려준다. 문서에서 찾지 못한 수수료 조건은 `미확인`에 적는다.
- 실패: 서브에이전트가 요약한 인용을 원문을 열지 않고 `확인`으로 적었다. 배정자가 출처를 열어 그 문장이 없는 것을 찾았다. 바로잡는 법: 그 행을 `미확인`으로 바꾸고 원문을 다시 열어 확인한 것만 결론에 남긴다.
