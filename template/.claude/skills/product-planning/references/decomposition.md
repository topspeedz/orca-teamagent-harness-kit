# 항목화: 분해, 복잡도, 수락 기준

> 읽는 시점: `product-manager`가 작업 단위 `항목화`를 맡았을 때. phase의 2단계에서 요구사항 정리 다음에 돈다.

- 바탕: revfactory/harness-100의 46-product-manager(Apache-2.0)에서 story-point-estimator와 story-writer의 방법을 가져와 이 틀의 규칙에 맞게 다시 썼다. 사람 시간과 팀 속도로 재는 부분은 빼고, 시간은 `planner`가 Task마다 분 단위로 잡는다.

## 입력

SRS의 `(계획됨` 표시가 붙은 줄, PRD의 `US`, `prd-writer`의 리포트(요청 대조 표). 지금 백로그와 보관 파일.

## 요청과 대조

`prd-writer` 리포트의 요청 대조 표와 브리프의 요청 원문을 함께 본다. 원문의 요구인데 PRD·SRS에 줄이 없으면 항목을 만들지 않는다. 리포트의 `## 사용자 결정 필요`에 "요구사항 누락: 원문 <번호>"로 올린다. 창구가 `prd-writer`를 다시 띄운다.

단일 모드(요구사항 리포트 없이 요청이나 인박스 한 줄을 받은 작은 작업)는 이 대조를 하지 않는다. PRD·SRS 줄 없이 항목을 만들고 비고의 요구사항 라벨에 `요구사항 없음`을 적는다. 6단계에 `doc-steward`가 필요하면 줄을 쓴다.

## 항목의 단위

- 항목 하나는 수락할 수 있는 결과 하나다(`backlog-management`).
- 이미 있는 활성 항목과 같은 결과면 새로 만들지 않고 그 항목에 합친다.
- 뜻이 갈려 `정해지지 않음`이 남은 요구사항은 항목을 만들되 상태를 `blocked`로 두고 비고에 `막힌 이유: 사용자 결정 필요 <번호>`를 적는다. 묶음에 넣지 않는다.
- 요구사항 하나가 항목 여럿이 될 수 있고, 항목 하나가 요구사항 여럿을 다룰 수 있다. 어느 쪽이든 비고의 `요구사항` 라벨에 ID를 모두 적는다.

## 나누는 기준 다섯

큰 요구사항은 아래 중 맞는 기준으로 나눈다. 나눈 항목도 각자 수락할 수 있어야 한다.

| 기준 | 예 |
| --- | --- |
| 흐름의 단계별 | 결제: 수단 고르기, 정보 넣기, 처리, 확인 |
| 데이터 종류별 | 내보내기: JSON, CSV, XML |
| 사용자 유형별 | 로그인: 이메일, 소셜, 사내 계정 |
| 만들기·읽기·고치기·지우기별 | 상품 관리: 목록, 등록, 수정, 삭제 |
| 정상 흐름과 오류 흐름별 | 정상 처리, 오류 처리, 경계 값 |

## 복잡도

세 차원을 각각 매기고 가장 큰 값을 항목의 복잡도로 한다.

| 차원 | 보는 것 |
| --- | --- |
| 기술 | 바뀌는 코드의 범위(파일과 층의 수), 기술 난이도(알고리즘, 동시성, 보안), 테스트 난이도 |
| 도메인 | 업무 규칙의 수, 예외 경우, 승인이 필요한지 |
| 불확실성 | 조사가 필요한지, 외부 의존(API, 라이브러리, 인프라), 요구사항이 분명한지 |

값은 1, 2, 3, 5, 8, 13 가운데 하나다.

| 값 | 복잡도 | 불확실성 | 예 |
| --- | --- | --- | --- |
| 1 | 아주 낮음 | 없음 | 문구 변경, 설정값 수정 |
| 2 | 낮음 | 아주 낮음 | 간단한 화면 요소 추가 |
| 3 | 보통 | 낮음 | API 하나의 만들기·읽기·고치기·지우기, 간단한 화면 |
| 5 | 중간 | 보통 | 복잡한 업무 규칙, 외부 API 연동 |
| 8 | 높음 | 높음 | 새 기능 모듈, 인증 |
| 13 | 아주 높음 | 아주 높음 | 구조 변경, 큰 재구성 |

- 13이면 위의 기준으로 나눈다. 나눌 수 없으면 비고에 사유를 적는다.
- 불확실성이 8 이상이면 조사 항목을 따로 만들고 원래 항목을 그 뒤에 둔다. 조사 항목의 수락 기준은 "답할 질문과 그 답을 적은 문서"다. 조사 항목의 우선순위는 그 항목이 돕는 원래 항목과 같다.
- 낙관하지 않는다. 테스트, 리뷰, 오류 처리까지 들어간 크기로 매긴다.
- 값은 시간이 아니다. "이틀"이 아니라 "5"다.

## 수락 기준

- 대상, 조건, 기대 결과가 들어간 한 문장이다. 검증자가 그대로 검사할 수 있어야 한다(`backlog-management`의 좋음·나쁨 예).
- 항목마다 정상 흐름 기준 하나와 오류 흐름 기준 하나 이상을 쓴다. 오류 흐름이 생길 수 없는 항목은 그 사유를 비고에 적는다.
- 수치를 지어내지 않는다. 근거 없는 기준은 `## 사용자 결정 필요`로 올린다.

## 백로그에 쓰는 모양

표의 열은 그대로다. 비고 칸에 라벨을 이 순서로 적는다.

```
우선순위 <값> · 복잡도 <값>(기술 n · 도메인 n · 불확실성 n) · 요구사항 <FR/NFR ID> · 선행 <BL ID 또는 없음> · 수락 기준: (1) … (2) …
```

- `선행`: 이 항목보다 먼저 끝나야 하는 항목. 조사 항목 뒤의 원래 항목은 조사 항목을 적는다.

- RICE 점수가 확정되면 우선순위 라벨 바로 뒤에 `RICE <점수>(R n · I n · C n%)`를 넣는다([prioritization.md](prioritization.md)).
- 그 뒤에 근거와 막힌 이유를 적는다.
- 역할 열: 명단 `docs/harness/team-org.md`에서 그 영역을 맡는 팀의 에이전트를 적는다. 알 수 없으면 `미정`으로 둔다. 6단계 완료 처리 때 계획서의 배정으로 맞춘다.
- 상태는 `todo`다.

## 리포트 절

`02_product-manager_backlog_v<N>.md`:

```markdown
## 한 일

## 항목

| BL | 한 줄 | 요구사항 | 우선순위 | 복잡도 | 새 항목 여부 |
| --- | --- | --- | --- | --- | --- |

## 요구사항과 항목 대조

| 요구사항 | 다루는 항목 |
| --- | --- |

## 묶음 제안

## 사용자 결정 필요

## 검증
```

- 요구사항과 항목 대조 표에서 `(계획됨` 표시가 붙은 요구사항마다 한 줄이다. 빈 줄이 있으면 끝난 것이 아니다.
- `## 검증`에 적는 줄: 대조 표의 빈 줄 수(0), 새 항목마다 `grep -c "^| BL-#### " docs/backlog.md` → 1, 복잡도 13인 항목 수와 그 사유.
