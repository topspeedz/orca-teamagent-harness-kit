# Task spec 양식

워커를 띄울 때 넘기는 spec이다. 첫 줄은 `[역할: <에이전트>]` 또는 `[역할: <에이전트> · 리드]`다.

```
[역할: <에이전트>]
Task: <Task ID> <이름>

목표: <한두 문장>

먼저 읽을 것:
- <경로와 범위>
- 메모 `<이 spec 옆의 <Task ID>.memo.md>`가 있으면 가장 먼저 읽는다. 등록한 뒤에 정해진 사용자 결정이나 앞 시도가 실패한 원인이 적혀 있다.

편집 범위: <경로>. 그 밖의 파일은 만들거나 고치지 않는다.
금지: <하지 말 것>
배정: <에이전트> / <작업 단위> (<런타임> <model>/<effort>)

완료 기준: <검증자가 그대로 검사할 수 있는 값>
검증이 기대는 설정값: <파일:키, …> (없으면 `없음`)
막히면: `ask`로 올리고 턴을 끝낸다. 사용자에게 직접 묻지 않는다.
보고: `worker_done` 본문 세 문장, 수정한 파일 목록, 리포트 경로 `_workspace/<팀>/<phase>/NN_<에이전트>_<산출물>_v<N>.md`. 리포트의 `## 검증` 절에 검증 줄을 ✅나 ❌로 적는다. 돌리지 못한 것도 ❌다. 완료 기준 밖의 줄은 `(참고)`로 시작한다.
```

## 쓰는 법

- 사용자가 이 Task에 다른 model·effort를 지시했을 때만 `배정` 줄 아래에 `사용자 예외: <원문>` 줄을 넣는다. 원문 그대로 적고 기동 스크립트에 `--override-reason "<원문>"`을 넘긴다. 이 줄이 있는데 `--override-reason`이 없으면 기동이 거부되므로 평소에는 넣지 않는다.
- `배정` 줄은 모델 표에서 찾은 값이다. 팀장 spec(첫 줄 `· 리드`)의 배정 줄은 `배정: <에이전트> / 리드 (<모델 표의 `리드` 줄 값>)`이고, `--lead`로 띄울 때 `--unit`은 쓰이지 않는다. spec, 표, 기동 인자가 서로 다르면 기동이 거부된다.
- `완료 기준`은 검증자가 그대로 돌릴 수 있는 명령과 기대 출력이다. 구현 Task는 이 기준을 재현하는 테스트를 먼저 쓰고 실패를 확인한 뒤 구현한다.
- **`완료 기준`은 이 Task의 편집 범위 안의 상태만 잰다.** 워커들은 작업 폴더 하나를 같이 쓰므로, 범위 밖의 상태에 기댄 기준은 다른 Task가 일하는 동안 충족할 수 없다. 변경 확인은 `git diff --stat -- <편집 범위 경로>`처럼 자기 경로로 좁히고, 테스트는 이 Task가 바꾼 파일에 관련된 것만 넣는다. 저장소 전체 검사, 전체 테스트, 같은 묶음의 다른 Task가 만들 파일에 기대는 검사는 넣지 않는다. 그것은 코디네이터가 끝에 한 번 돌린다. 범위 밖에서 본 오류는 리포트에 `(참고)`로 적는다.
- 새로 만드는 파일은 추적되지 않아 `git diff`에 나오지 않는다. 그런 경로는 `git status --short -- <경로>`로 본다.
- 편집 전 사본이 필요하면 `_workspace/_run/<phase>/bak/<Task ID>/`에 두고, 지울 때는 자기 Task의 폴더만 지운다. 폴더를 같이 쓰면 먼저 끝난 Task가 남의 사본까지 지운다.
- `먼저 읽을 것`과 `편집 범위`는 기억으로 나열하지 않는다. `grep -rln <심볼, 파일 이름, URL 조각>`의 결과로 채우고, 그 명령도 spec에 적는다. 손으로 나열하면 목록 밖의 파일이 빠지고 워커가 되물어 온다.
- `검증이 기대는 설정값`에는 이 Task의 시험이 기대는 설정 파일의 키를 적는다(예: `web/config/seats.json:fov`). 시험은 그 값을 숫자로 베껴 쓰지 않고 그 파일에서 읽어 비교한다. 이 줄에 적힌 키를 바꾸는 Task는 같은 키를 적은 다른 Task와 그 시험을 `grep -rln <키 이름>`으로 찾아 `편집 범위`에 넣는다. 값을 베껴 쓴 시험이 남으면 뒤 Task의 완료 검사가 남의 결함으로 미달한다.
- 글자 그대로 들어가야 하는 문구에 이모지 같은 비ASCII 문자가 있으면, 완료 기준의 비교는 명령에 다시 친 문자열로 하지 않는다. spec 파일과 대상 파일을 Node로 읽은 값끼리 비교한다. Windows의 파이프는 그런 글자를 양쪽에서 똑같이 빼서 "일치"가 거짓으로 통과한다.
- 워커는 사용자에게 직접 묻지 않는다. 막히면 `ask`로 코디네이터나 팀장에게 올린다.
- 워커는 커밋하지 않는다.
- 기다리는 단계를 `sleep`으로 쓰지 않는다. Claude Code가 단독 `sleep`을 막는다.
- Codex 워커에게는 기동 스크립트가 작업 방식 여섯 줄을 spec 끝에 붙여 넘긴다(`register`로 등록할 때와 `--spec-file`로 띄울 때). 문장은 `worker-intake-context.mjs`가 정본이라 양식에 쓰지 않는다. Orca에 직접 만든 Task를 `--task`로 띄울 때만 스크립트가 붙이지 못하므로, `node .claude/scripts/orca-launch.mjs codex-rules`가 찍는 줄을 Task spec에 넣는다.
- 등록된 Task의 spec은 바꿀 수 없다. spec 파일을 고쳐도 워커에게는 가지 않는다. 등록한 뒤에 전할 것(게이트로 받은 사용자 결정, 앞 시도의 실패 원인)은 메모(spec 옆의 `<Task ID>.memo.md`)에 적는다.
