# Task spec 양식

워커를 띄울 때 넘기는 spec이다. 첫 줄은 `[역할: <에이전트>]`다.

```
[역할: <에이전트>]
Task: <Task ID> <이름>

목표: <한두 문장>

먼저 읽을 것:
- <경로와 범위>
- 메모 `<이 spec 옆의 <Task ID>.memo.md>`가 있으면 가장 먼저 읽는다. 등록한 뒤에 정해진 사용자 결정이나 앞 시도가 실패한 원인이 적혀 있다.

편집 범위: <경로>. 그 밖의 파일은 만들거나 고치지 않는다.
백로그: <해당 BL ID와 실제 선행 Task>
직접 협의: <상대 역할·목적·현재 수신 경로. 호출 불가 또는 배정·범위 변경이면 배정자에게>
문서 영향: <이력 전용, 또는 정본 경로·절/ID·지정 작성자·인계 근거>
금지: <하지 말 것>
배정: <에이전트> / <작업 단위> (<런타임> <model>/<effort>)
쓰는 스킬: <`change-review` / `qa-verification`>
결함 ID: <H-1, A-H-2처럼 쉼표로 구분>
수정 diff: <파일 경로>
이미 아는 것: <인박스 항목>

완료 기준: <검증자가 그대로 검사할 수 있는 값>
검증 환경값(설정값): <파일:키 = 값, …> (없으면 `없음`)
막히면: `ask`로 올리고 턴을 끝낸다. 사용자에게 직접 묻지 않는다.
보고: `worker_done` 본문 세 문장, 수정한 파일 목록, 리포트 경로 `_workspace/<작업 폴더>/<phase>/NN_<에이전트>_<산출물>_v<N>.md`. 리포트의 `## 검증` 절에 검증 줄을 ✅나 ❌로 적는다. 돌리지 못한 것도 ❌다. 완료 기준 밖의 줄은 `(참고)`로 시작한다.
```

## 쓰는 법

- 공개 API 변경은 구현자가 재현 결과와 계약의 연산·기대값·실제값을 리포트에 남긴다. 계약의 해당 절 작성자만 정본을 편집한다. 구현자가 작성자이기도 하면 그 경로를 편집 범위에 넣는다. 다르면 인계 대상을 명시하고 작성자 반영 뒤 QA가 재검한다. 같은 정본의 쓰기는 순서대로 배정한다.

- 사용자가 이 Task에 다른 model·effort를 지시했을 때만 `배정` 줄 아래에 `사용자 예외: <원문>` 줄을 넣는다. 원문 그대로 적고 기동 스크립트에 `--override-reason "<원문>"`을 넘긴다. 이 줄이 있는데 `--override-reason`이 없으면 기동이 거부되므로 평소에는 넣지 않는다.
- 승인 전은 현재 모델 표에서, 승인 후는 해당 Task의 승인 버전에서 `배정` 값을 읽는다. 등록 spec에는 승인 기본값을 적는다. 기동 직전 위임된 모델·effort가 달라지면 해당 시도 기록과 영수증에 최종 요청·적용값을 남긴다.
- `쓰는 스킬:`은 검증 Task(`verifier`)에만 넣는다. 중간 변경 리뷰와 보안·돈이 걸린 변경 리뷰는 `change-review`, 재검은 `qa-verification`, 끝 검증은 둘 다다. 워커는 여기 적힌 스킬만 읽는다.
- `배정` 줄의 작업 단위는 모델 표에서 배정을 찾는 이름이다. 할 일과 범위는 `목표`, `편집 범위`, `완료 기준`이 정한다. 워커는 작업 단위 이름을 지시로 읽지 않는다.
- `완료 기준`은 검증자가 그대로 돌릴 수 있는 명령과 기대 출력이다. 구현 Task는 이 기준을 재현하는 테스트를 먼저 쓰고 실패를 확인한 뒤 구현한다.
- **`완료 기준`은 이 Task의 편집 범위 안의 상태만 잰다.** 워커들은 작업 폴더 하나를 같이 쓰므로, 범위 밖의 상태에 기댄 기준은 다른 Task가 일하는 동안 충족할 수 없다. 변경 확인은 `git diff --stat -- <편집 범위 경로>`처럼 자기 경로로 좁히고, 테스트는 이 Task가 바꾼 파일에 관련된 것만 넣는다. 저장소 전체 검사, 전체 테스트, 같은 묶음의 다른 Task가 만들 파일에 기대는 검사는 넣지 않는다. 그것은 코디네이터가 끝에 한 번 돌린다. 범위 밖에서 본 오류는 리포트에 `(참고)`로 적는다. `AGENTS.md`의 `## 명령` 절에서 줄 끝에 `(전체 테스트)`가 붙은 명령이 `완료 기준`에 있으면 `register`가 등록을 거부한다.
- **이 Task에 관련된 테스트가 혼자 써야 하는 자원(GPU, Blender MCP 등)을 쓰면, 구현 Task와 수정 Task의 `완료 기준`에는 그 테스트를 넣지 않고 그 자원 없이 도는 간단한 코드 테스트를 넣는다.** 문법, 타입, 린트, 단위 테스트처럼 합쳐도 문제가 없는지를 보는 것이다. 이 Task들은 병렬로 돌아서, Task마다 그 자원을 쓰는 테스트를 돌리면 자원 하나를 두고 서로 막힌다. 그 자원을 쓰는 테스트는 구현이 모두 끝나 합쳐진 코드에서 끝 검증 Task 하나가 한 번 돌린다(`coordinator`의 검증 배치). 이때 `금지` 줄에 "<그 명령>을 돌리지 않는다"를 적는다.
- `결함 ID:`는 수정 Task와 수정 뒤의 검증 Task에만 넣는다. 수정 뒤의 검증 Task는 재검 Task, 그리고 이 phase에서 수정 Task가 뜬 뒤에 띄우는 검증 Task다. 기동 스크립트는 계획의 `rounds`가 수정, 검증, 재검으로 표시한 Task만 검사하고, `rounds`가 없는 계획은 검사하지 않는다. 장부 `## 결함 원장`의 ID를 쉼표로 구분해 적는다. 수정 Task의 ID는 원장에서 High이고 상태가 `열림`이거나, 장부 `## 결정`에 그 ID의 `수정 포함 승인` 줄이 있어야 한다. 줄이 없거나 조건이 맞지 않으면 기동이 거부된다.
- `수정 diff:`는 수정 뒤의 검증 Task에 `결함 ID:`와 함께 넣는다. 값은 수정 Task가 바꾼 내용을 담은 diff 파일의 경로다. 둘 중 하나라도 없으면 기동이 거부된다. 계획 노드에 `afterFix`가 있거나 장부 `## 결정`에 그 Task의 `전 범위 검증 승인` 줄이 있으면 예외다. 예외가 아닌 Task의 `완료 기준`은 "결함 ID마다 원래 재현 절차를 다시 돌린다"로 고정한다.
- 수정 Task는 결함의 증거로 받은 실패 테스트를 고치지 않는다. 고쳐야 하면 그 사유를 리포트에 적는다.
- 시험 갱신 Task는 구현이 모두 끝난 뒤 돌린 전체 테스트의 실패를 받는다. spec에 받은 실패마다 둘 중 하나로 처리한다. 옛 기대값이면 시험을 고치고, 기대값이 바뀐 근거가 된 계획이나 수락 기준의 줄을 리포트에 적는다. 근거를 댈 수 없으면 고치지 않고 리포트의 `## 결함` 표에 High로 적는다. 그 시험이 증거이므로 증거 칸은 `관찰`로 시작한다.
- `이미 아는 것:`은 검증 Task에만 넣는다. 인박스 항목 가운데 이 Task가 검증하는 편집 범위의 파일을 가리키는 것만 적는다. 끝 검증의 spec에는 장부 원장에서 이미 열린 결함 ID도 여기에 적는다.
- 새로 만드는 파일은 추적되지 않아 `git diff`에 나오지 않는다. 그런 경로는 `git status --short -- <경로>`로 본다.
- 편집 전 사본이 필요하면 `_workspace/_run/<phase>/bak/<Task ID>/`에 두고, 지울 때는 자기 Task의 폴더만 지운다. 폴더를 같이 쓰면 먼저 끝난 Task가 남의 사본까지 지운다.
- `먼저 읽을 것`과 `편집 범위`는 기억으로 나열하지 않는다. `grep -rln <심볼, 파일 이름, URL 조각>`의 결과로 채우고, 그 명령도 spec에 적는다. 손으로 나열하면 목록 밖의 파일이 빠지고 워커가 되물어 온다.
- `검증 환경값(설정값)`: 구현사항 및 기능별 검증을 할 때에는, 그 기능을 구현할 당시 혹은 구현 이후 개발자가 자주 검증했을 때의 환경값(설정값)을 명시해 놓도록 한다. 여러 기능이 하나의 설정값에 영향을 미치거나 연속되게 함께 쓰여야 하는 경우, 서로 이 값을 다르게 테스트하거나 구현하고 있다면 문제가 발생하는 것이니, 꼬이게 만든 쪽이 알 수 있게 하여 함께 Fix하게 한다. 본인이 꼬이게 했으면 본인이 고친다. 다른 Task가 꼬이게 했으면 `ask`로 코디네이터에게 올려, 그 값을 바꾼 담당이 고치게 한다.
- 글자 그대로 들어가야 하는 문구에 이모지 같은 비ASCII 문자가 있으면, 완료 기준의 비교는 명령에 다시 친 문자열로 하지 않는다. spec 파일과 대상 파일을 Node로 읽은 값끼리 비교한다. Windows의 파이프는 그런 글자를 양쪽에서 똑같이 빼서 "일치"가 거짓으로 통과한다.
- 워커는 사용자에게 직접 묻지 않는다. 막히면 `ask`로 배정자(코디네이터 또는 창구)에게 올린다.
- 워커는 커밋하지 않는다.
- 기다리는 단계를 `sleep`으로 쓰지 않는다. Claude Code가 단독 `sleep`을 막는다.
- Codex 워커에게는 기동 스크립트가 작업 방식 여섯 줄을 spec 끝에 붙여 넘긴다(`register`로 등록할 때와 `--spec-file`로 띄울 때). 문장은 `worker-intake-context.mjs`가 정본이라 양식에 쓰지 않는다. Orca에 직접 만든 Task를 `--task`로 띄울 때만 스크립트가 붙이지 못하므로, `node .claude/scripts/orca-launch.mjs codex-rules`가 찍는 줄을 Task spec에 넣는다.
- 등록된 Task의 spec은 바꿀 수 없다. spec 파일을 고쳐도 워커에게는 가지 않는다. 등록한 뒤에 전할 것(게이트로 받은 사용자 결정, 앞 시도의 실패 원인)은 메모(spec 옆의 `<Task ID>.memo.md`)에 적는다.
