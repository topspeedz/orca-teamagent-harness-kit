# 테스트 실패와 제품 결함 판정

## 어떤 테스트를 언제 돌리나

1. 계획에는 변경할 동작, 영향받는 호출 경로, 수락 기준, 확인할 입력과 기대 결과를 적는다. 프로젝트에서 이미 합의한 출시 차단 조건이 있으면 출처를 적는다. 실행 전에는 실패의 심각도를 배정하지 않는다.
2. 구현 담당은 바뀐 동작을 관찰할 수 있는 가장 작은 테스트를 실행한다. 경계를 바꾸면 호출자와 소비자 사이의 계약도 확인한다. 화면 조작이나 기기 의존성이 수락 조건이면 해당 환경에서 입력부터 결과까지 확인한다.
3. 끝 QA는 합쳐진 코드에서 수락 기준을 확인한다. 코디네이터가 전체 테스트를 한 번 돌리고 코드 버전, 환경, 명령, 실패한 테스트와 원본 결과 경로를 남긴다. 같은 코드·환경·범위의 결과는 재사용한다.
4. 수정 뒤에는 원래 실패와 영향받는 인접 경로를 먼저 확인한다. 입력 순서나 환경에 의존하는 실패는 원래 묶음과 조건을 재현한다. 원래 실패가 통과로 바뀌었는지와 인접 기능이 계속 통과하는지를 따로 기록한다. 공통 코드 변경으로 영향 범위를 한정할 수 없거나 프로젝트의 필수 게이트가 수정본 전체 실행을 요구하면 코디네이터가 그 범위까지 넓힌다. 사용자가 정한 범위를 따르고, 마지막 전체 결과의 코드 버전과 이번 재검 범위를 함께 보고한다. 이전 필수 실패는 해결 증거나 명시적인 사용자 결정이 있을 때까지 열린 항목으로 둔다.

## 실패한 테스트 한 건을 받았을 때

| 확인할 사실 | 처리 |
| --- | --- |
| 요구사항이 바뀌어 기대값이 낡았는가? | 변경 근거가 된 수락 기준의 줄과 원래 실패를 남기고 해당 테스트를 갱신해 실행한다. |
| 이번 변경에서 처음 깨졌는가? | 기존 결과가 있으면 같은 환경·범위의 변경 전 결과와 대조한다. 원인이 불분명하고 판정이 달라질 때만 같은 조건으로 재현하거나 별도 작업 폴더에서 기준 버전을 확인한다. |
| 재시도 때만 통과하거나 검사 환경에 문제가 있는가? | 첫 실패와 재시도 결과를 모두 기록한다. 환경 오류, 기존 실패, 간헐 실패는 근거가 있을 때만 그렇게 분류한다. |
| 사용자나 호출자가 어떤 결과를 받았는가? | 수락 기준의 입력, 기대와 실제, 영향받는 동작·범위·우회 방법을 확인한다. 같은 원인이 확인된 실패는 한 결함 ID에 테스트 이름들을 연결한다. |
| 제품 영향이 아직 불분명한가? | 리포트의 `## 남은 것`에 `영향 미확인`, 실패 원본, 미확인 동작과 다음 확인 방법을 적는다. 끝 QA나 최종 보고에 인계한다. 최초 결과는 실패로 남긴다. |

## 심각도와 완료 판정

| 등급 | 필요한 근거 |
| --- | --- |
| High | 핵심 작업을 완료할 수 없거나, 구체적인 입력과 상태에서 보안 경계 위반·데이터 손실·서비스 중단 같은 중대한 피해가 발생할 수 있거나, 사전에 합의한 출시 차단 조건을 위반한다. 영향 범위와 증거 또는 해당 조건의 출처를 적는다. |
| Medium | 사용자가 잘못된 결과나 기능 저하를 겪지만 영향 범위가 제한되거나 현실적인 우회 방법이 있다. |
| Low | 기능은 정상이고 국소적인 시각·문구·정리 차이가 남는다. 접근이나 조작을 막는 차이는 실제 영향에 따라 다시 판정한다. |

필수 검사 실패·미실행은 등급과 별도로 완료를 보류한다. 원인이 환경이면 검사를 복구하고, 기대값이 낡았으면 시험을 고치고, 제품 결함이면 위 기준으로 등급을 정한다. 자동 수정 대상은 근거를 갖춘 열린 High다. 그 밖의 수정은 기존 사용자 승인 경로를 따른다.

### 설계 근거

- Chromium CQ는 변경 영향 범위의 테스트를 선택하고, 실패 시 같은 설정에서 재현한 뒤 변경 전 결과와 비교한다. 이 킷은 원인이 불명확할 때 그 비교 방식을 사용한다. [Chromium CQ](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/infra/cq.md)
- Firefox는 결함이 사용자에게 미치는 범위와 우회 가능성을 등급 사례로 설명하고 새 결함의 등급을 비워 둘 수 있다. 이 킷은 조사가 끝날 때까지 영향 미확인을 허용한다. [Firefox Defect Severity](https://firefox-source-docs.mozilla.org/bug-mgmt/guides/severity.html)
- Anthropic은 에이전트의 수행 기록과 환경에 남은 실제 결과를 구분한다. 이 킷은 워커 보고를 수락 기준의 관찰 가능한 결과와 대조한다. [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- SWE-bench는 수정해야 할 시험의 실패→통과와 기존 시험의 통과 유지를 따로 채점한다. 이 킷은 재현 사례와 인접 회귀 사례를 해당 수정의 검증 범위로 잡는다. [SWE-bench 평가 하네스](https://www.swebench.com/SWE-bench/api/harness/#swebench.harness.grading.get_resolution_status)
- pytest는 실패한 사례만 다시 실행하는 방법과 전체 실행을 구분한다. 수정 확인에 쓴 범위와 마지막 전체 실행을 따로 기록한다. [pytest 재실행 지침](https://docs.pytest.org/en/stable/how-to/cache.html)
